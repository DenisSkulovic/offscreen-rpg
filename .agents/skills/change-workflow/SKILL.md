# Documentation and implementation Change workflow

**Lifecycle map:** [How we work](../../../WORKFLOW.md) explains when to use an Undertaking, Design, Change or Task, the documentation-before-code gate and how this skill fits into the overall method. This skill owns the detailed Change procedure, not a second life-cycle definition.

## Dedicated parent commission shorthand

If the owner gives a Cursor **parent chat** one direct Change assignment such as `do DXK01`, `work on DATA06`, or `finish FORK01`, treat the named Change as an end-to-end commission. The parent does **not** need the owner to repeat “create a dedicated Change branch from the selected target / orchestrate subagents / update docs / archive / integrate to that reference branch” each time. Apply the [dedicated Change commission contract](../../references/bounded-parent-orchestration.md#0-dedicated-change-commission-owner-shorthand): isolate Git ownership, execute bounded T-ID batches, keep going through internal checkpoints, reconcile documentation, close and archive the packet, integrate to the Change's recorded reference branch (the Undertaking branch where selected), verify the join, and report that branch's final SHA. Do not automatically start the successor Change.

**Start with the [independent work-unit standard](../../references/change-work-unit-standard.md).** A **Change** is an independently reviewable, bounded outcome that substantively revises **canonical product/technical documentation** (kind: `documentation`) or modifies **executable source/tests/configuration** (kind: `implementation`). A major editorial rewrite, exact claim-owner split or factual contract reconciliation can be a legitimate documentation Change even with zero code diff. Unratified design discussions, pure evaluations and trivial typo/link fixes still should not generate Change tickets.

**Current route:** [`work/QUEUE.md`](../../../work/QUEUE.md) owns the only **global Current work** selection (an open Change, a standalone Task, or none). A direct owner commission naming a Change to a dedicated isolated Cursor parent is an explicit parallel-work authorization for that chat; it does not require mutating the global selector before work starts and does not authorize adjacent Changes. [`work/changes/README.md`](../../../work/changes/README.md) catalogs Changes but does not select them. Operational no-diff actions with independent scheduling/receipts belong in [`work/tasks/`](../../../work/tasks/README.md), not fake Changes. [Taxonomy](../../../work/WORK-TAXONOMY.md). **Create** packets under [`work/changes/open/`](../../../work/changes/open). **Retire** Done/Cancelled packets to `work/changes/archive/YYYY-MM/<program>/` (see work-unit standard); append the compact index under `work/changes/ledger/`. New packets use [`CHANGE.md`](assets/CHANGE.md), plus [`PLAN.md`](assets/PLAN.md) only for meaningful multi-step execution. Old `docs/history/initiatives/FEATURE.md` dossiers are initiative/proposal/history context, never automatic implementation orders.

**Target-first portfolio modernization:** Before auditing, author an explicit end-state target independently of the existing code, then compare actual source to it. Read [target-driven renewal](../../rules/target-driven-renewal.md). A portfolio/refactor Change is not Ready without a target criterion → audited gap → bounded diff → falsifiable proof. Do not optimize for whatever code smells happened to be noticed first.

**Planner-first readiness rule (owner-selected 2026-11-19):** When planning a Change for Cursor, follow the [planner-investigation standard](../../references/planner-investigation-standard.md). The **planner, especially ChatGPT**, must inspect actual current source/test and affected authority/integration seams, settle algorithm/state/ID/transaction/branch/canon/retry decisions and prepare a verified source map **before** writing a Ready implementation Change. A 2–5-file child route card is a compressed entry to a broader completed investigation, not a restriction on planner research. For complex persistence/distributed work, store a source-backed mapping in `PLAN.md` or canonical technical docs so the executor does not rediscover architecture. If unresolved design remains, resolve it now or explicitly mark `PLANNER BLOCKER`/Proposed and a narrow investigation; don't hand Cursor an open-ended design problem masquerading as implementation. For trivial VERIFY/PATCH-S, perform only proportionate narrow investigation.

**Planner-owned companion files:** for STATE/CONTRACT/RELEASE/PROOF work, use the optional [packet profiles](../../references/change-packet-profiles.md): `SOURCE-MAP.md` (verified symbols/call graph), `EXECUTION.md` (chosen boundary/state transitions), `PROOF.md` (positive and diagnostic negatives). Do not require these for ordinary PATCH, and do not ask the Cursor executor to produce them instead of implementing. Cursor reads the short `CHANGE.md` route first and only linked deep sections needed. `PLAN.md` remains a checkpoint. Existing agent/DEPTH classes do not change.\n\n## 1. Select a measurable documentation or code outcome

First establish the real product/developer objective. Distinguish what is **already selected**, what is **already implemented**, what needs human decision/acceptance and what an editorial or executable delta can safely change. One Change should be small enough to implement, verify, review and close without reopening an entire initiative.

- **Kind and concrete delta required:** for implementation, name the actual source/test/config boundary; for documentation, name the canonical document headings, exact reader inference to fix, preserved claims and dependency routes. An unratified discussion or pure test run with no planned authoritative edit is not a Change.
- **Scope:** one cohesive outcome and the dependencies genuinely needed to prove it. Split unrelated deliverables, risky permission domains or design-dependent outcomes.
- **No arbitrary size cap:** cost depends on conceptual scope, source fanout, dependencies, evidence and potential harm, not lines or prompts alone.

Do not make a new folder for a trivial typo or link fix; a direct bounded owner edit with the appropriate checks is fine. Do not create duplicate folders for the same unfinished outcome.

## 2. Resolve intent and authority before implementation

**Product docs are the bible; technical docs are the second layer; code is their artifact.** Consult the relevant product/technical specification headings—they are authoritative, not the temporary Change packet. Trace actual source and tests narrowly, and compare with the proposed scope. **Stale file paths or old implementation approvals are not evidence.** A Change that will move behavior **or normative documentation meaning** without planning its related impact is malformed. Fix the packet before execution.

For a significant architecture/design decision, use [role orchestration](../../roles/README.md), appropriate professional knowledge and an independent critical lens when warranted. The purpose is to settle _alternatives and constraints_ before Cursor implements, not to spawn a meeting factory.

A proposal remains Proposed until scope, current owner, relevant safeguards, proof and user permission are clear. Provider calls, DB migrations, hosted actions and broad checks require their separate permissions.

A new Ready packet declares `planned-impact.v1` before execution: product, technical, code, and related dispositions, each `changed` with an owner path or `unchanged because` with a concrete reason. **A documentation Change explicitly states that code remains unchanged because the expected outcome is a semantic or structural document improvement**, and must still name an adversarial reading/negative case. That table is prospective. The seven-column reconciliation ledger remains the retrospective proof. Legacy Ready packets stay readable and get an upgrade warning until selected.

## 3. Write a self-contained executor handoff

`CHANGE.md` records the one outcome, authorities, baseline, intended **document and/or source** delta, exclusions, success and discriminating negative acceptance. For `documentation`, describe the exact before/after claim map and affected inbound/outbound links. For `implementation`, name code/tests and their verification. For portfolio changes it must also link a **pre-existing area target criterion** and a **source-grounded audit finding**, not merely say "this file could be cleaner." Its purpose is a cheap transfer between ChatGPT design, source-connected Claude investigation and Cursor implementation.

Use `PLAN.md` **only** for meaningful multi-step execution, including a substantial split/relocation needing inbound link migrations. Describe dependency-ordered outcomes and exactly one current checkpoint. Keep later slices coarse and rewrite the checkpoint rather than appending a diary.

Use [cursor-handoff](../cursor-handoff/SKILL.md) for an economical executor prompt; it must not send entire initiative histories or let Cursor redefine product intent. A documentation handoff grants **Markdown/skill ownership edits only**, not executable source modification.

### Bundle scheduling and parallel Cursor execution

**Mandatory parent checkpoint:** [bounded integration batches](../../references/bounded-parent-orchestration.md). A user-approved program is not one endless Cursor parent turn. Keep Composer T-IDs cheap; integrate, test, reconcile and commit after a cohesive batch (normally 2–5 small T-IDs or one high-risk join), then report. Only the parent stages shared-checkout changes. Never treat a child receipt as a Done Change or postpone closure until the user asks.

For a batch of planned Changes, **attempt a dependency/ownership graph before defaulting to serial execution**. Use the canonical [batch execution contract](../../references/change-work-unit-standard.md#batch-execution-and-parallel-change-orchestration-2026-11-19). Mark independent pairs and shared-resource serialization explicitly in the work queue. When the owner approves an Active batch and the client supports subagents, let one coordinating Cursor chat delegate disjoint Ready Changes in parallel, preferably with isolated worktrees/branches. It waits at dependency gates, not at arbitrary Change-number boundaries. No agent may edit a shared canonical heading, cluster/operator, migration, lockfile or working tree concurrently. The coordinator alone integrates, runs global checks and closes reconciliation ledgers. Subagents return brief actual evidence receipts; proposed changes are not authorized merely by being in the batch.

## 4. Implement only when authorized

One owner applies the approved **editorial or executable** delta, inspects diff, runs safe proportionate checks, and evaluates expected *and negative* behavior. Documentation Changes verify claim preservation, exact relative links/heading anchors, and independent reviewer comprehension; executable tests are not mandatory when no code was touched. No automatic unrelated refactors, new provider spend, staging DB reset, **unapproved** agent swarms or new feature invention.

If code or source inspection reveals that the accepted contract is wrong/incomplete, **return that decision to the owning product/technical decision role**, then resume only after explicit ratification. An editorial Change cannot silently ratify a new shared-play, time, security, privacy or spending policy. A green fixture is not proof of connected gameplay.

## 5. Converge, record evidence and retire

**Perform this at each accepted batch join, not after an endless run of T-IDs.** If a Change reached its original accepted outcome, reconcile and archive it in that integration window. If not, record which T-IDs landed, the *exact* residual normal/negative/live proof and next owner. If a packet grew beyond its independently useful scope, split honestly without downgrading already-selected acceptance or hiding a genuine safety/production gate. A partial verified patch can be committed while its Change remains open. See [bounded parent workflow](../../references/bounded-parent-orchestration.md).

Record what landed, tests/inspection actually run, affected revision, remaining risk and exact next action.

**Before `State: Done` / Cancelled or clearing `Current work`:** complete the affected-claim ledger for every authority under **Authority and baseline**, and for every known contract dependent of a changed selected claim. For documentation Changes, the revised Markdown owner and inspected source SHA (or explicit `no source behavior changed`) are valid proof inputs. A passing guard does not mean the product, technical, and code texts are factually aligned. Each row names the heading, whether the ratified target changed or is unchanged, the inspected source path and SHA, the evidence tier, the negative proof, and the map update or `N/A`. `unchanged` needs a concrete reason, not "not needed". `not run` with a remaining blocker cannot be Done. A pure internal tool may record `no product/technical behavior impacted` instead of editing product pages. **A documentation-only Change must prove semantic accuracy and status/authority preservation, not merely claim a clean Markdown-link check.** For every changed row and any spec-vs-code drift, run [documentation-reconciliation](../documentation-reconciliation/SKILL.md) steps 1–5 **on those owners only**. **Leaving permanent docs more stale than the landed code is a critical failure—the Change is not Done.** Do not rewrite product or technical authority merely to rationalize the diff; escalate product conflicts. `pnpm wiki:change-guard --mode close` checks the ledger shape, declared paths and known dependents for both Change kinds; if a docs-only synthetic fixture reveals a guard incompatibility, fix that narrow executable tooling issue under a separately authorized implementation Change. It reports `needs independent owner review` rather than deciding that a product rule was satisfied. Edit order inside the Change may vary; the documentation pass is still mandatory. Source-adjacent README/map updates follow [documentation.md](../../rules/documentation.md) when an owning path, wire contract, status claim or important invariant actually moved.

**Then archive the packet:** `git mv` from `work/changes/open/<leaf>/` to `work/changes/archive/YYYY-MM/<program>/<leaf>/` (month from leaf date prefix; program bucket from slug). Rewrite inbound Markdown links that still point at the old path. Update the `work/changes/README.md` catalog and clear the selected Change in `work/QUEUE.md` if it was active; do not leave a second selector. Do **not** leave Done/Cancelled folders in `open/`. Use `scripts/repo-tools/archive-changes.mjs` when batching.

A completed Change leaves the **hot** route (`open/`); `archive/` retains the execution packet, whether it changed Markdown or executable code. Don't preserve a duplicate living implementation history when its decisions have a durable owner.

Owner-retained and dormant legacy dossiers require explicit preservation. Before deleting/moving any old folder, inspect its unique decisions, inbound links and approval boundaries. See the [dated legacy audit](../../../work/designs/open/legacy-initiatives-index/AUDIT-2026-11-11.md).

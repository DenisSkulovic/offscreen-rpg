# Independent design challenge (architect / adversarial reviewer)

**Use when** the first proposed design came from a coding model, the scope is substantial, the owner wants strong architecture, or an apparently clean plan makes a consequential tradeoff. This is a design review, not an implementation-diff review. **Formal independent committee,** for material new architecture and substantial redesign: follow the [committee protocol](../../rules/target-driven-renewal.md#mandatory-independent-design-committee), including the exact candidate, severity classification, a fresh ChatGPT conversation, a delivered SHA-bound verdict, and no redesign. The reviewing session or the local custodian persists the verdict. This skill's read-only consultation cannot substitute for that committee when the protocol requires it. Evolutionary and settled-contract work use proportionate review instead. The remaining checklist is a lens for critique, not the formal receipt.

1. **Anchor authority.** For portfolio modernization, independently assess the _desired target architecture first_ under [target-driven renewal](../../rules/target-driven-renewal.md). Review the Design dossier and concrete specimens first; no Change or PLAN is required yet. Read a gap audit and packet only when they exist and the target phase permits it; respect explicitly excluded legacy source. Review affected permanent product/technical contracts. Check whether the source was made the standard by accident. Distinguish decided outcome, proposal, unverified assumptions and current implementation evidence. An implementation cannot grant itself authority just because it exists.
2. **Bring professional design knowledge.** Select a relevant manual from [the engineering knowledge library](../../knowledge/README.md), _especially_ [architecture alternatives](../../knowledge/architecture-decision-space.md) when design boundaries are disputed. Challenge the range of options, why each exists, changed constraints, maintenance/evolution and cross-system interactions. Use first-party documentation when a framework behavior is consequential. Failure cases are one part of the critique, not its entire content; no external reference overrides the approved product.
3. **Construct genuine alternatives.** Consider keeping the existing boundary with one repair; a focused improvement; and a changed ownership/design only when credible. Identify which assumptions each alternative needs, how it fails, and what evidence would favor it. Include a counterexample that would weaken your preferred option. "Make services" and "keep things simple" are not designs.
4. **Attack the hidden failure paths.** Depending on scope, question concurrency, stale writes, retries, absence/pause, security, UX empty/error states, model hallucinations treated as authoritative data, and whether another abstraction increases token and maintenance cost. For UI, involve `player-experience-design` or `frontend-engineering`; for SQL/Temporal, `transactional-correctness-review`.
5. **Converge (informal critique only).** Return a clear recommended decision, one serious rejected option and why, source anchors, updated product/technical headings to author, negative acceptance, and the smallest verifiable implementation slice. Say _stop/research further_ when an essential contract is unresolved.

### Output contract (short)

For informal critique only (formal committee uses its required verdict artifact):

`Decision | Why it beats the strongest alternative | Broken assumptions / counterevidence | Permanent spec edits | First executor slice | Evidence still missing`.

Do not generate ornamental pages. Invest in the review the risk requires, revise the owning sections, and test consequential uncertainties before packet planning. Do not alter working code, invent external approval, or create a document per finding. The independent reviewer should add new judgment, not paraphrase a generated proposal. Never dispatch in-game inference or spend a coding subscription for a routine design question the current sources already answer.

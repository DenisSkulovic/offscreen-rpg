# Target-first engineering renewal

**Owner decision 2026-11-26: implementation and heavy acceptance have different owners.** Cursor implements the selected design, constructs specified deterministic proof tools, runs focused unit/contract tests, changed-file quality checks and proportionate cheap local integration checks, and commits a coherent implementation receipt. The design/planning ChatGPT and human owner own heavy acceptance: broad builds/suites, infrastructure lifecycle and fault/recovery runs, multi-service/browser/end-to-end exercises, release upgrades, long-running or costly probes and other substantial operational proof. ChatGPT selects exact commands, target, prerequisites, expected outcomes, timeouts, stop/cleanup and evidence; the human runs the bounded batch in their terminal and returns results for ChatGPT to interpret and record. Prefer one reproducible scripted batch over repeated paid-agent terminal orchestration. No heavy acceptance by Cursor unless the owner explicitly delegates that named proof; elapsed time alone is not a hard cutoff, and essential focused negative tests are not skipped to save tokens. The planner partitions the existing acceptance matrix by executor before commission (or at the next checkpoint of an in-flight Change). This changes who runs proof, not its required tier, safety, or integration gate.

When Cursor completes source work and its assigned cheap checks, it commits on the Change branch, reports exact SHA, owned paths, tests/results, known failures, remaining acceptance commands and resource/collision state, and stops at **IMPLEMENTED — ACCEPTANCE PENDING** (an open Change checkpoint, not a new lifecycle category or Done). Preserve the linked worktree and do not merge, archive or retire while mandatory heavy acceptance is pending. ChatGPT/owner take over proof without re-dispatching Cursor merely to run commands; fix ordinary source defects through a bounded implementation follow-up, and return architecture contradictions to the planner. Record acceptance against the exact tested SHA, then the named integration custodian reconciles current main, checks affected proof on any changed seams, integrates, reconciles documentation/evidence and retires clean work. Cursor may perform mechanical join/retirement after receiving the accepted proof receipt, or close cheap-only Changes autonomously when every required gate is met. No extra ceremonial approval or duplicate test sweep. This explicit responsibility split supersedes older unconditional whole-Change Cursor acceptance/closure language; never infer live mutation permission, waive essential gates, or claim unrun proof.

**Trigger:** audits, design and significant Changes intended to raise this repository to portfolio-grade engineering quality. Applies to React/Next.js, UI/UX, backend, data, infrastructure, security and related modernization. **Not a mandate** for a trivial bug fix or for gameplay feature work whose already approved product/technical contract supplies the target.

## Governing rule

**Define the desired, reviewable end state first. Then inspect the current system as evidence of the gap. Then authorize implementation Changes whose acceptance advances that end state.** The current source is a baseline and a constraint, **not the design brief or the standard of excellence**. A list of smells or files to split is not an architecture.

No portfolio-modernization Change is **Ready** unless its destination is named by an explicit target criterion and the proposed code delta demonstrates how it closes a material part of the audited gap. Reject vague verbs such as "improve," "modernize," "clean up" and "make scalable" without an outcome, negative case or target trace.

## Design-led engineering: mandatory material-design gate (2026-11-26)

Design deeply, challenge the design, exercise actual tools and learn with the owner, then implement against a feasible proof plan. The goal is a simpler, comprehensible, reproducible system, not better-organized generated code or more packets.

### Desired-state reconciliation is the governing mindset

Capture the spirit and purpose of the system before optimizing its mechanics. Treat desired architecture as a declarative reference point: establish the vision, independent requirements, external contracts and researched design criteria; then compare actual state and choose the smallest justified reconciliation. A requirements-discovery pass may inspect current behavior, operator documentation, callers and boundary evidence before target design, but explicitly distinguish intentional requirements from accidental implementation details, arbitrary tuning and inherited abstractions. Do not let a current file tree or existing algorithm become the design brief. Freeze or version the target before detailed gap analysis; revise it only for an articulated new constraint, evidence or owner decision, never merely to make existing code look acceptable.

Clean-slate **thinking** does not require deletion of source. Preserve the baseline, history, working behavior and durable data; defer inspecting replaceable internals where anchoring is harmful. Actual deletion/replacement is a later engineering decision justified by the gap and migration risks, not a prerequisite for independent design. Prefer retaining proven, comprehensible pieces that satisfy the target; as quality matures, expect more evolutionary reconciliation. Do not equate fewer files, more files, rewriting or reuse with quality. Every retained and newly introduced mechanism must have a reason; discard only what is demonstrably unnecessary, wrong or cheaper and safer to replace.

### External research is an engineering input, not optional decoration

For substantial designs involving frameworks, platforms, protocols, libraries or professional practices, actively research current external sources **before selecting the approach**. Model training and confident recollection are hypothesis generators, not sufficient authority for version-sensitive behavior, recommended architecture or tuning. Start with official version-matched manuals, tagged source, release artifacts, API references, maintainers' examples and relevant standards. Compare credible industry implementations and independent practitioner evidence where it informs tradeoffs; distinguish reference examples from requirements and production claims. Investigate native capabilities and established libraries before inventing custom machinery. For frontend, research actual framework and ecosystem patterns against the selected experience; do not recreate established accessibility, interaction or state-management primitives without justification.

Record source URL, version/tag or date, relevant finding, design implication and unresolved caveat in the dossier. Follow consequential claims into actual API/schema/template/source when documentation is ambiguous. Use local experiments against the selected version when feasible; a web citation is not runtime proof. Avoid arbitrary numerical settings: identify consumer demand, limits, resource costs, failure behavior and measurement plan; prefer supported defaults as a provisional baseline only when compatible with known requirements. If online access is unavailable, disclose the gap and gate decisions that depend on it rather than substituting invented facts. Do not browse for its own sake on trivial settled fixes.

### Select the design posture

- **Clean-slate target:** appropriate when internals are untrusted, disposable, overgrown, or fundamentally misaligned. Record purpose, required behavior and external constraints; explicitly identify the legacy subtree excluded from initial study. Read current agent rules, adjacent systems, interfaces, authoritative requirements and actual environment facts, not the excluded internals. Do not copy its directory tree, abstractions, algorithms or tests as design inputs. Respect an explicit owner instruction not to read a subtree; use boundary evidence instead and disclose remaining unknowns. Reopen excluded internals only with owner permission when needed for safe cutover.
- **Evolutionary design:** appropriate when working behavior, proven data, compatibility, migration cost or sound architecture warrants preservation. Inspect existing implementation after establishing the target and preserve only justified pieces.
- **Focused fix:** already-settled contract with a small defect. No new design dossier or multi-pass ritual unless evidence reveals a material architecture question.

At kickoff explicitly select a provisional posture and justify it briefly from the problem, owner instructions and known constraints. Separate consumer/boundary discovery from inspection of replaceable internals; for an evolutionary renewal, establish independent target criteria before judging inherited implementation choices. Revise the posture if evidence warrants it. Treat initial architectural preferences as hypotheses until requirements, credible alternatives and consequential upstream behavior have been investigated.

No existing code has inherent architectural authority. Neither deletion nor reuse is automatically virtuous. Existing data, externally observable behavior, security, financial and correctness guarantees remain constraints; replacement does not authorize their destruction.

### Work in the design space, not the packet queue

Use one substantive dossier in `work/designs/open/<area>/`. Start with intent, non-goals, constraints and questions. Grow files as useful: architecture and responsibilities, alternatives/decisions, concrete configuration or interface specimens, experiment plan, findings and independent review. These are examples, not mandatory filenames or document quotas. Record actual first-party versions/source references for consequential external behavior. Prefer the vendor's supported mechanisms, native declarative configuration, ordinary tools and simple composition over bespoke glue. For each script or abstraction, name the real unmet requirement it serves; challenge whether deleting it, using a Helm value or native controller, or a small command is better.

Iterate repeatedly: design → independent critique → revise → concrete specimen → authorized experiment → observations → revise. Review architecture as a whole, then individual boundaries, operations/failure and maintainability; a packet readiness audit is not a substitute. Ask what can be removed. Use exact configuration, manifests, example interfaces and commands to make design falsifiable. Do not claim a simulated run or fixture proves vendor behavior. Collaborate with the owner in coherent, bounded terminal experiments when local runtime is unavailable; interpret real outputs, use read-only checks first, bound mutations, record failures as evidence and update source rather than manually nursing the live environment.

### Gate before implementation planning

For substantial design, no implementation Change packet or Cursor dispatch until the dossier records:
1. A coherent end state and why it meets the actual requirements, including meaningful alternatives and rejected complexity.
2. Concrete specimens and boundaries; lifecycle, failure, security, data and operational contracts sufficient to implement, with [verification architecture and acceptance tiers](#design-verification-with-the-system) selected before formal defense.
3. A recorded, passed designer self-defense and a passed [independent committee review](#mandatory-independent-design-committee) within the [formal architecture defense](#mandatory-formal-architecture-defense-and-convergence) for the specific scope and target revision, including substantive revisions where warranted and experimental evidence for consequential uncertain assumptions. An unavailable decisive result gates the affected decision; do not waive it by calling the defense complete. Repeat until material questions are settled.
4. Source-grounded integration/cutover map: affected consumers, compatibility, state and permission ownership, what to preserve/replace/remove, proof and rollback/refusal. For clean-slate design this comes **after** the independent target, respecting source exclusions; no guessed callers.
5. Owner acceptance of material decisions and reconciliation into permanent product/technical owners, distinguishing selected target from implementation and proof.

A narrow experiment may precede acceptance with explicit scope and authorization; it is not production implementation or implicit ratification. Do not manufacture packets to show progress. A real blocker remains in Design; dependency-gated execution of already settled contracts is not a design blocker.

### Select execution by economics and fit

Direct ChatGPT implementation plus owner-operated terminal feedback is a legitimate route for coherent declarative infrastructure, small tools/configs, prototypes and other scoped work within available access. Use a Change branch and relevant ownership, evidence and documentation requirements; no obligation to construct a paid-agent handoff. For broad application migrations, many disjoint edits, local builds or tool limitations, bounded Cursor Changes remain useful **after** the design is settled. Hybrid is often best. Do not assume the direct route always wins; compare total cost, rework, risk, owner learning and owner-operated interaction overhead. Record the route and scope. No background or unavailable execution claims.

For infrastructure, the deliverable is the repository and its reproducible lifecycle. Manual terminal actions are diagnostic or explicitly authorized maintenance, never hidden prerequisites. Distinguish existing-cluster provisioning, repeat ensure, upgrade, workload proof, and fresh clone/cold cluster acceptance. Fix the source of setup and control defects, then rerun the normal public path. Prefer scripted rerunnable proof for recurring checks; do not pay a model to execute a checklist that a deterministic tool can own. Local disposability requires explicit scope; never infer permission to destroy foreign or valuable state.

## Adaptive design workshop: choose the investigation, not a universal sequence

The planner owns a **living investigation plan**, not a predetermined number of documents, passes or hours. An unambiguous owner request to begin or continue redesigning an area commissions the design workshop: ordinary non-destructive source/boundary investigation, upstream research, provisional specimens and design-dossier writes on an isolated design branch within that scope. It does not commission implementation, canonical promotion, destructive actions, live mutations or paid execution; respect explicit exclusions and narrower requests. At kickoff, identify the intended outcome, scope/exclusions, current authority, environmental assumptions, highest-risk unknowns, candidate evidence methods and next review, then **begin substantive investigation in the same turn**. Orientation and a proposed route alone are not normally a deliverable. Use available tools to obtain actual findings, test initial hypotheses against evidence, compare relevant alternatives and record substantive progress in the design dossier. Complete applicable cold-start reads before drawing decisions that depend on them; an unavailable read or unresolved authority is an explicit limitation, not presumed compliance. At the first substantive checkpoint, create or resume the scoped design branch and persist the findings already established (source anchors, upstream versions, provisional choices, evidence limits and next investigation). Verify the commit and return its link. Do not create empty ceremonial dossiers or duplicate existing active work. If repository writes are unavailable or the investigation has not yet yielded substantive findings, disclose the concrete reason and preserve the useful findings in the response; do not imply a commit exists. Reorder, add, merge or omit steps as findings warrant; record material changes of direction. Continue through useful, authorized design work without repeated permission to proceed. Return at a meaningful workshop checkpoint: discoveries and their implications for the owner, a consequential choice needing discussion, a necessary owner-operated experiment, a concrete access/evidence blocker, or completed scoped design work. Keep the owner involved in the learning and material decisions; do not turn autonomy into silent, wholesale design ratification or an obligation to finish the entire workshop in one turn. Keep a short dossier entrypoint with current selected/proposed decisions, evidence gaps, acceptance state and the next useful action. Historical evidence and verdicts retain their dated context; update the current summary and supersession links at material checkpoints instead of making readers reconcile contradictory historical statements. A substantial workshop may span multiple chats and a dedicated design branch; commits preserve intermediate decisions, not automatic acceptance. Use the actual integration baseline, reconcile changes in adjacent contracts before promotion, and keep speculative artifacts off runtime paths. A design branch is not a deployment branch. Do not merge merely to make a specimen accessible: use a branch checkout/worktree or immutable file retrieval. A direct implementation may follow on an appropriately commissioned Change branch; a design merge is neither required for experimentation nor sufficient for execution.

### Choose the design lens by the problem

| Area | Questions that drive the workshop | Useful specimens and discriminating experiments |
| --- | --- | --- |
| Platform infrastructure | Native controller vs glue, resource identity, topology, persistence, secrets, lifecycle ownership, permissions, timeouts, recovery | Pinned vendor artifact, values/manifests, actual render and inventory, read-only cluster/catalog discovery, disposable install/reuse/failure, cold-cluster proof |
| Monorepo package / library | Domain responsibility, public and private exports, dependency direction, runtime vs type-only imports, ownership of state and effects, error/concurrency contracts | Proposed tree, package manifest and export map, representative types and consumer code, dependency graph, compile/import negative tests, in-memory and real adapter contract proof |
| Backend application / distributed service | Composition root, transport and auth, commands vs queries, transaction boundaries, retries/idempotency, shutdown and observability | Request/response and sequence specimens, schema/transaction sketches, thin vertical slice, concurrent requests, crash/replay and denial tests |
| Frontend application | User journeys and semantic information hierarchy before component structure, state authority, routing/rendering/hydration, accessibility, responsiveness, visual direction | Competing compositions with identical scenario data, actual browser prototypes and screenshots, keyboard/mobile/long-content trials, loading/error/race/hydration checks; follow the relevant experience-design dossier |
| Data / persistence | Entity identity, invariants, cardinality, query workloads, ownership, concurrency, retention and migration | Example datasets, DDL and queries, EXPLAIN on representative data, constraints and concurrency experiments, migration/rollback and isolation proof |
| Cross-cutting redesign | Dependency seams, compatibility, operational and user-visible transition, independent integration slices | Consumer matrix, old-to-new map, representative end-to-end slice, migration rehearsal and regression/negative proof |

These are lenses, not six mandatory recipes. Select multiple when a problem crosses boundaries. Do not blindly transfer infrastructure practices to UI or package design. Use existing specialist knowledge and authoritative upstream sources where relevant; verify version-specific assumptions against the actual installed or pinned artifact.

### Make design concrete before spending on execution

A specimen is an intentionally provisional artifact answering a named question: interface code, representative consumers, directory tree, manifest, SQL, mockup, executable prototype, test fixture or sequence diagram. Keep it inside the design dossier (or an explicitly isolated disposable sandbox); label what is executable, illustrative or observed, its dependencies and how to reproduce it. It may become production source only after explicit review of correctness, ownership, maintainability, integration and proof. Do not build a shadow production subsystem in the design directory.

Maintain a small decision/evidence register: question → plausible alternatives → decisive evidence or experiment → observation → decision/revision → remaining uncertainty. For material assumptions prefer an experiment that could disprove the favored option over one that merely demonstrates a happy path. Record version/SHA, target, command or fixture, expected discrimination, actual result, permission and limits. Distinguish unavailable evidence from failed evidence; don't repeatedly run unchanged experiments. When the owner operates the terminal, combine independent checks into one coherent bounded batch with expected observations, timeouts and stop conditions. Capture independent successes and failures as structured receipts while skipping dependent unsafe stages; interpret results together before requesting another run. Compare suspect inherited failures against the immutable baseline instead of repeatedly patching unrelated code. Avoid repeated fetch/run/paste cycles for speculative one-line changes; batch source-grounded fixes and check what can be checked with available tools before asking the owner to execute. Promote recurring checks into deterministic verification tools when useful; one-off probes need not become permanent scripts.

### Design verification with the system

Design the means of proving the target alongside its interfaces and failure behavior, not after implementation. Before formal submission, establish a feasible verification route: actual environment/tool versions and available access; source and runtime fixtures; identity, isolation, ownership, permissions and resource admission; setup, executable entrypoints, observations, fault injection, bounded stop and cleanup; evidence location and limits. Resolve consequential uncertainties with a small feasibility experiment where needed. An unimplemented harness is not itself a blocker if its design is concrete and feasible; make its construction an early implementation task. Reuse existing verification infrastructure rather than inventing a framework per Change. Test the harness itself (including refusal and setup failure). Distinguish native public-entrypoint proof from adapted test routing or injected dependencies; never weaken production fences to make a test convenient.

Freeze a compact acceptance matrix with the target: claim/invariant → normal and discriminating negative → proof tier and environment → required result → integration classification. Essential safety, functional correctness and affected compatibility gates must pass at the agreed evidence tier. Extended assurance may be deferred only with a reasoned risk assessment, explicit owner acceptance, named follow-up/evidence owner and a visible NOT RUN state; unrelated future engineering remains outside the selected slice. Classify by consequences, not test difficulty: a crash, concurrency or transport scenario needed to establish a critical invariant belongs in essential safety. Neither a green happy path nor owner impatience can override a known material safety/correctness defect or missing indispensable proof. New material evidence may reopen a gate; explain the newly discovered invariant or failure, update the matrix, and avoid silently adding closure requirements or downgrading inconvenient tests. See [integration and closure](../../WORKFLOW.md#9-verification-review-and-the-next-loop).

### Mandatory formal architecture defense and convergence

**Owner decision 2026-11-26: formal defense is a mandatory, substantive design gate, not optional review polish.** After a coherent target, representative specimens and integration investigation exist, deliberately change from advocate to skeptical examiner. Treat the proposed architecture as a thesis to be defended before a technically competent committee. The obligation is to find a defensible design, not to vindicate the initial proposal. No material design may be promoted, implementation-planned or dispatched without a recorded defense verdict for the exact scope/revision. A small fix under an already settled contract is not subject to artificial ceremony.

The designer must independently formulate the strongest credible objections, including a simpler/no-change alternative and a scenario that would invalidate the core premise. Test actual contracts, source, pinned upstream behavior and concrete specimens; choose discriminating experiments where evidence is missing. Do not merely list generic risks or congratulate the design. Examine requirements coverage, alternative choices and economics, smallest sufficient mechanism, authority/dependency boundaries, concurrency and failure paths, security/data integrity, resource costs, migration and rollback/refusal, operator/user ergonomics, maintainability and verification. Adapt depth and lenses to the domain. Walk representative successful and adverse end-to-end scenarios; distinguish source evidence, executable fixture, live observation, inference and unknown. Ask whether you would actually recommend the design under its constraints if you had not authored it.

Record a durable defense artifact or section containing target revision/scope, examiner identity (self-defense is not an independent reviewer), strongest objections and counterexamples, evidence and reasoning, verdict per material claim (defended / revise / evidence-gated / reject), actual changes made and references to revised artifacts, remaining decisive questions and falsifiable acceptance. Give an overall verdict: **DEFENDED**, **REVISE AND RE-DEFEND**, or **EVIDENCE-GATED**, optionally by independently bounded slice. Do not manufacture a numerical score, fixed number of passes, fictional committee, or pretend unavailable tests passed. If a material objection stands, revise or abandon the architecture, update all affected specimens/contracts, then repeat the defense against the revised target. If a decisive experiment is unavailable, name what would resolve it and block the affected scope, not unrelated settled slices. A defense may be passed for a bounded structural slice while a separate capacity or migration decision remains gated. Do not equate this with owner acceptance, implementation proof or packet-readiness review.

Review from distinct perspectives: fit to intent, alternative architecture, smallest sufficient mechanism, boundary and failure behavior, real consumer ergonomics, and operator/maintainer experience. For each abstraction or module ask: what invariant or responsibility does it own, who needs it, what happens if removed, and why can't an existing native mechanism handle it? Review the whole composition and representative paths, not just the neatness of individual files. An adverse finding can change the target, discard a specimen or reopen an earlier question. Do not pretend a self-review is a separate human or model review; record who reviewed and which counterexamples were tested.

Convergence requires a passed self-defense and independent committee verdict for the selected candidate and scope. Material architecture choices are decided, representative artifacts agree, consequential uncertainties are either evidenced or explicitly gated, source integration/preservation map is complete for the selected slice, and acceptance is falsifiable. It is not a document count, token budget, arbitrary review count or absence of all future questions. Reopen design when repeated local repairs reveal a wrong premise, a new abstraction without a named need, a cross-boundary contradiction, or failure to explain the intended architecture simply. Stop the paid repair loop; return exact evidence to the planner. Do not reopen for ordinary bounded implementation defects.

### Mandatory independent design committee

**Owner decision 2026-11-26: every substantial design must pass a fresh-chat committee after the designer's self-defense and before owner acceptance, canonical promotion or implementation planning.** The designer rehearses, challenges and revises until willing to defend a specific bounded target. The owner then opens a separate ChatGPT conversation as committee. A second persona in the same conversation is not sufficient. This is an independent conversation review, not a claim of different model training or independent human certification.

Formal submission requires a passed self-defense and one coherent normative target with its integration map and feasible proof matrix. An owner-requested early independent consultation is allowed, but label it **CONSULTATION**, not a formal defense or acceptance attempt; it carries the same committed receipt obligation and cannot pass the formal gate. Do not schedule repeated formal reviews of knowingly premature candidates.

The designer freezes the candidate by commit SHA, identifies the actual integration baseline, design branch, dossier path and precise review scope, and gives the owner a short launch prompt. Do not supply persuasive summaries, expected answers or preselected objections; the committee reads the actual dossier and independently follows source, external evidence and relevant canonical contracts. The designer pauses edits to that review scope while the committee works. No delegation to paid implementation agents.

**Committee mandate:** read current repository rules from the integration branch (including this rule even if the design branch predates it), verify branch/HEAD and baseline, inspect the proposed architecture, specimens, relevant source and evidence, and formulate the strongest credible objections independently. Test alternatives, necessity, safety, failure, integration, economics, proof feasibility and falsifiability as appropriate to the domain. Be demanding but fair: do not manufacture objections, reward documentation volume, or require unrelated implementation proof. Trace material findings to actual evidence, distinguish demonstrated defects from plausible risks and unknowns, identify the exact decision each blocks, and explain what would satisfy the objection. The committee is not the designer and does not silently repair the proposal or make changes to production source.

**Committee deliverable and mandatory completion condition:** before returning the terminal response, the committee itself must commit and push every verdict (positive, negative, evidence-gated, or owner-requested preliminary review). This is part of the assigned review, requires no second owner prompt, and is not optional when the candidate is premature. A chat-only verdict is REVIEW INCOMPLETE. Commit a durable verdict into the same design branch under the dossier (e.g. `committee/pass-01.md`, increment for later submissions). Include reviewed candidate SHA, integration baseline SHA, scope, reviewer identity/role and date, evidence consulted and limitations, ranked material findings with source anchors and counterexamples, required closure evidence, and overall and scope-specific verdict: **DEFENDED**, **REVISE AND RE-DEFEND**, or **EVIDENCE-GATED**. Optional nonblocking improvements are clearly separate. A positive verdict requires affirmative reasons, not merely absence of findings. Use a create-only verdict path and expected-head CAS push; if the candidate HEAD changes before the write, stop and report the conflict rather than overwrite, force-push or certify an unreviewed revision. No edits outside the verdict artifact, no main merge, runtime mutation, paid calls or implementation commission. After pushing, read back the branch HEAD and the actual verdict file at the committed SHA; return that verified SHA and link to the owner. If permissions, expected-HEAD conflict or tooling prevent a write, report REVIEW INCOMPLETE with the concrete blocker and preserve existing work. Never invent a receipt. If review evidence is insufficient, record that limitation in the committed verdict and gate the affected scope. A preliminary or rejected candidate does not waive the commit obligation.

The designer reads the actual committed verdict, maintains stable finding identifiers and dispositions (open, resolved with evidence, superseded with reason, or separately gated), addresses every material objection with evidence or an explicit reasoned rebuttal, revises affected artifacts and self-defends the new candidate. A failed formal defense or materially changed formal candidate requires another fresh-chat committee review; subsequent reviews check prior findings against changed evidence without redoing unrelated closed investigations, while remaining free to identify new material objections; repeat until the selected scope has an affirmative verdict on the actual candidate revision. Do not demand repeated review for unrelated scopes or purely clerical verdict/index bookkeeping. An approved slice cannot silently absorb a gated one. Owner acceptance remains separate and follows the committee gate; neither a committee verdict nor its commit grants execution permission.

Minimal owner launch prompt (fill exact identifiers, not arguments for the design):

> You are the independent architecture defense committee. Review repository <repo>, integration baseline <SHA>, design branch <branch>, candidate <SHA>, dossier <path>, scope <scope>. Read the current integration-branch agent rules and follow the mandatory independent design committee protocol. Be ruthless about actual architectural weaknesses, fair about evidence, and commit your verdict to the design branch. Do not redesign or implement.

### Execution and learning economics

Before commission compare direct planner edits, Cursor execution and hybrid by scope cohesion, tool access, local build needs, integration risk, owner learning and anticipated rework, not file count alone. Choose the fewest independently meaningful Changes and smallest safe tasks after architecture convergence. Each packet is a projection of settled design onto real source, not a new place to decide architecture. Avoid duplicate architecture prose and speculative packet waves; preserve parallelism where genuinely independent. For the owner, explain the architecture and evidence as the workshop progresses, including why each experiment matters, rather than handing over an opaque finished tree.

At close, record useful process feedback: which assumptions were overturned before coding, which escaped into implementation, avoidable retries/complexity, observed spend or time only if actually available, what was proven and what remains. Improve the canonical method when a lesson generalizes; leave component-specific recipes with their owning design/runbook/evidence. ## Three distinct artifacts, in this order

1. **Target design, independent of source defects:** develop one area-level target in the active Design dossier, then promote accepted guarantees into `docs/technical/` or another existing authoritative home. Identify purpose, boundaries and responsibilities, user-visible and developer-visible promises, state/data/identity lifetimes, integration contracts, failure/recovery, accessibility, security, performance observability, verification/maintainability, and explicit non-goals. State architectural choices, credible rejected alternatives, constraints and what would justify revisiting them. Express acceptance as scenarios, not adjectives or fashionable libraries. Mark proposed decisions until owner-reviewed.
2. **Gap audit against that target:** inspect real source/tests/configuration at an identified commit. Map existing paths to target criteria, using evidence levels: source-observed, fixture/test-exercised, live-observed or unknown. Separate defects from intentional differences, missing evidence, and future product work. Rank by criticality, prerequisite dependencies and portfolio demonstration value. No "smell of the day" backlog.
3. **Selected execution route (bounded Changes when delegated):** each significant `CHANGE.md` links a target criterion and audit finding, explains baseline → desired delta → preserving invariants → falsifiable success/negative cases. Order by dependencies so each slice improves the _same chosen architecture_ rather than letting an executor redesign it. Set `Ready` only after actual owner authorization and source revalidation; a batch of proposed packets never authorizes coding.

## What good and bad progress look like

- **Good:** design a coherent frontend data/state model, audit all relevant entrypoints for mismatches, then change one authorized boundary while retaining one overall direction.
- **Bad:** randomly extract a large hook, add a query library, rewrite CSS, change render strategy and call those independent improvements without a chosen architecture or user-facing guarantees.
- **Good:** select a simple architecture over an elaborate one when it meets the target more reliably. **No library/technology earns inclusion merely because it looks good on a CV.**
- **Bad:** promise "zero defects," "fully optimized" or "production-grade" without workload, test environments, empirical evidence and remaining limitations.

## Required review gate

A reviewer or planning agent should reject an implementation plan when any of these is missing:

- A target end state with **named criteria** chosen before the source-gap assessment (or a documented explicit change to that target).
- A grounded baseline: exact code owner, observed failure/deficit and evidence limit, without treating unrun tests as passed.
- A credible competing design and its cost/trade-off, informed by the appropriate `.agents/knowledge/` manual and current official framework documentation when relevant.
- Specific mapping from target criterion → gap → Change → proof, with preserved working behavior, risk and rejected adjacent work.
- A viable migration path for cross-cutting work and a stop condition preventing opportunistic unrelated "cleanup."

If the audit proves the target is already satisfied, write **no Change** for that criterion. If the target is disputed, resolve the design **before** giving the work to Cursor. A target may be revised by an explicit owner-reviewed decision and its consequences, not by discovering that existing code would be inconvenient to change.

# E2 | Defended architectural direction (native evidence gates remain)

## 1. Collection topology and scope

Dev-first. Preserve release parsed manifests, pins, readiness behavior and existing telemetry policy exactly until separately authorized release enrollment. One Prometheus server, one Grafana, same datasource UIDs `offscreen-metrics`, `offscreen-logs`, `offscreen-traces`; no federation. Use dev profile overlay values for Prometheus/Grafana analogous to the existing Collector overlay. Preserve base values as predecessor inputs. Fresh dev install converges to E2; occupied E1 requires explicit upgrade. Ordinary ensure must not silently upgrade.

| Signal | Mechanism | Required interpretation |
| --- | --- | --- |
| Kubernetes object state | Bundled kube-state-metrics (KSM) chart 9.1.0, appVersion 2.20.0, enabled in dev Prometheus release | Cluster-wide node, namespace, Pod, Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, PVC and resource requests/limits/status. No Secret/ConfigMap collectors, arbitrary labels or annotations export. |
| Container resource metrics | Explicit authenticated kubelet resource and cAdvisor jobs on both nodes (G2 construction candidate: resource is sole CPU/RAM source; cAdvisor conditional network) | CPU rate, working-set memory, network only where safely attributable and proven; exclude empty/POD infrastructure containers from workload sums, avoid double-counting network across containers. No assumption completed or pending Pods have resource samples. |
| Node resource metrics | Explicit kubelet `/metrics/resource` job and KSM node capacity/allocatable/state | Node CPU/memory where supported by pinned Kind; node capacity vs pod use clearly labeled. No claim of host Windows or WSL metrics. |
| Component health | Prometheus native explicit endpoint jobs; see coverage table | Every installed component accounted for; Kubernetes readiness is different from scrape health and domain health. |
| Existing operational signals | Preserve Collector self-metrics and existing OTLP ingress/processing/export | Existing synthetic/dev proof retained; do not loosen filters or introduce new OTLP lanes. |

Use the bundled KSM rather than a new chart/operator. Set `fullnameOverride: obs-kube-state-metrics`, one replica, Recreate strategy, `prometheusScrape: false`, dedicated chart ServiceAccount and cluster RBAC, no proxy/sidecar/autosharding/custom resource collection. `collectors` is exactly `nodes,namespaces,pods,deployments,replicasets,statefulsets,daemonsets,jobs,persistentvolumeclaims,persistentvolumes`; disable label/annotation allowlists. Use the chart's `image.sha` (renders repository:tag@digest; compare exact expected rendered string as well as resolved runtime digest). Enable only necessary chart self-monitor endpoint (8081) without ServiceMonitor/ScrapeConfig CRs. One static KSM target `obs-kube-state-metrics:8080/metrics`, one self target on 8081; verify rendered Service ports. Filter sample families to those needed by the contract, including KSM list/watch health. Do not store arbitrary exported object labels or container IDs. Explicitly allow named pod UID, namespace, node, phase, owner kind/name, container name and resource/unit/status labels only as needed per metric family; no broad relabel copying. Do not enable chart's broad default Kubernetes scrape jobs wholesale (they default to annotation-based discovery, metadata copying and kubelet TLS verification bypass). Dedicated explicit jobs with fixed paths/ports, bounded allowlists and trusted target discovery. Prefer native metric endpoints over custom pollers. Use one standalone read-only Redis exporter Deployment/Service owned by the dev Prometheus release via its `extraManifests` (or equivalently chart-native declared resources if render confirms this interface); do not modify Redis Pod shape or restart its disposable cache just to monitor it. New native pinned exporter image is a prerequisite; no `latest`/floating fallback. No additional Helm release for these two helpers.

Node exporter is not selected for E2: its default host mounts/host namespaces would change the E1 trust boundary and Kind node system metrics must not masquerade as physical-host metrics. Kubelet resource metrics cover the immediate node CPU/memory requirement; node disk/OS metrics beyond proven kubelet series remain explicitly unsupported. Revisit a scoped node exporter only if the owner needs that extra coverage. Do not enable Alertmanager, Pushgateway, reloader sidecars or arbitrary pod scraping.

## 2. Permission and collection contracts

Dedicated identities. KSM gets only `list/watch` for the selected collectors (including PVs); Prometheus gets a dedicated cluster Role/Binding for Pod `list/watch/get` only when per-instance service jobs are selected, plus node permissions only when E2-R is selected. Retain `rbac.create: false` on the parent chart and declare exact permissions as release-owned extraManifests. For per-instance platform scrapes use `role: pod` discovery with explicit namespace lists; selectors bound actual discovery, not API authorization. A narrowly scoped Role in each platform namespace would reduce API visibility but cannot be installed into an absent optional namespace and introduces separate platform lifecycle coupling. Choose the bounded cluster-wide Pod metadata/spec read privilege for this trusted-local cluster, equivalent in resource type to KSM Pod read, rather than cross-namespace Role creation or namespace creation by monitoring. Do not claim tenant isolation or that Pod contents are hidden. No broad workload-controller read grant to Prometheus. Fixed singleton Services use cluster-local DNS; no discovery rights needed for them. Restrict multi-instance discovery to known platform namespace, exact native labels/container name and declared metrics port or fixed port verified on that container. Keep non-ready running targets visible; do not filter failure away. Static job names; stable cluster, environment, namespace, component and instance labels. No user annotation-controlled URL, port, credentials or path; no generic labelmap. Reject duplicate target identity and scrape paths. Never grant Secret/ConfigMap read, mutation, wildcard, impersonation, exec, proxy, or CSR approval to monitoring accounts. Token auto-mount only for KSM and the Prometheus identity that needs discovery. Grafana/exporter retain no API token. Local trusted cluster is not tenant isolation; internal HTTP endpoints permitted only for fixed approved native metrics (no credentials transmitted). No public Service, ingress, hostPort, host mount, host network or external remote-write. Do not widen Collector access.

**E2-R trust decision:** direct kubelet HTTPS on 10250, Kubernetes node discovery restricted to the two fixed dev nodes, `get nodes/metrics` plus `list/watch/get nodes` for discovery. Use projected service-account token file and verified serving CA/SAN, never admin kubeconfig, never `insecure_skip_verify`. Use verified node InternalIP with IP SAN or verified node DNS if reachable and certified; use one stable node label and separate `/metrics/cadvisor` and `/metrics/resource` jobs. Do not infer kubelet certificate trust from API server CA availability. The actual live serving chain/SAN and bearer authorization are evidence-gated. Native follow-up proved node-local public serving roots, DNS verification and restricted bearer access on both nodes. Candidate scoped refinement: bind verified local Docker/Kind public anchors to the exact cluster/node identities and E2 Prometheus Helm artifact; explicit owner selection and affected review before construction, no auto-rotation or trust from installed manifests. See [G2 construction candidate](../../../changes/open/observability-infrastructure-visibility/NATIVE-INPUTS.md#g2-construction-freeze-candidate--direct-https-and-cluster-bound-trust). If that trust path is unavailable, E2-R refuses; a future separately approved cluster-owner serving TLS remedy remains possible. No blanket CSR approver or implicit restart/recreation. `nodes/proxy` is rejected (GET can authorize command execution, not read-only); a metrics-server-only approach does not expose the required per-container history. No automatic fallback to plaintext or insecure TLS. See [EVIDENCE.md](EVIDENCE.md).

Initial local policy: scrape every 30s, timeout 10s; one scrape per target/path; use explicit metric family allowlists where safe, no arbitrary annotation labels. Initial per-target sample limits KSM/cAdvisor 20,000, other jobs 5,000; target limits 4 for each node job, 100 for each explicitly bounded component discovery job; label limit 40, name/value length limits 128/512; adjust only from measured native evidence (report limit errors, never silently truncate). Keep 7d/3GB metrics retention, 5Gi PVC and 72h logs/traces. Seven days is a configured upper time bound, not guaranteed effective history: increased ingestion may hit the 3GB cap earlier. Measure actual TSDB growth/effective history during representative use before proposing any storage expansion. These are initial engineering budgets, not measured maxima. Retain Prometheus existing 512Mi memory limit initially and record actual consumption; 512Mi is an initial test budget, not a guarantee. Keep its Recreate strategy (one writer to retained RWO TSDB). Helpers initially request 50m CPU/64Mi RAM, limit memory 128Mi each; measure before acceptance. Admit existing 4GiB host floor plus actual declared additional requests and rollout headroom under the existing memory authority; require sufficient node allocatable headroom too. If qualification cannot fit, stop and return measured budget correction. Do not preempt active work. Preserve memory admission and do not preempt active work. Use no high-cardinality generated test labels.

## 3. Component coverage register

Dashboard coverage is an explicit register of fixed dev components, not a generic `up` table. Required service metrics for installed data-plane components below, subject to the bounded gates in EVIDENCE.md before affected Change readiness. Fixed coverage register is separate from observed series. No mandatory domain metrics for every system Pod: inventory/resource coverage is the universal requirement. Absent optional components have no invented green status. KSM covers all their Pods even when richer metrics are unsupported. Use distinct target and service health indicators, not scrape success as business health.

## 4. Grafana operator experience

Provision repository-owned dashboard JSON via vendored Grafana chart `dashboardProviders` and `dashboards.offscreen.<name>.json`. One provider `offscreen`, path `/var/lib/grafana/dashboards/offscreen`, `allowUiUpdates: false`, `disableDeletion: false`, folder Offscreen. Keep JSON as the source in `dashboards/`; construct deterministic Helm `--set-file dashboards.offscreen.<name>.json=<absolute repo asset>` arguments in the shared release descriptor consumed by render/install/upgrade. Chart creates `obs-grafana-dashboards-offscreen` ConfigMap and mounts it natively (template inspected); no duplicate inline JSON or generated file committed. Existing chart checksum annotation rolls Grafana when dashboard JSON changes. Set home path via `grafana.ini.dashboards.default_home_dashboard_path`, using the actual mounted `overview.json` path. No sidecar, token, remote dashboard/plugin downloads or UI-only edits required. Keep admin Secret/datasource UIDs and stateless Grafana. Select `offscreen-overview` as provisioned home dashboard using supported native Grafana config; no anonymous login. Native dashboards are read-only canonical artifacts (UI exploration is welcome, changes require Git). All panels query existing datasource UID and proven metric names; distinguish no data, stale target, zero value. Variables cluster (single dev), namespace, workload and node derive from actual metrics, all with clear defaults, drill links preserve scope/time. No dynamic freeform cardinality labels.

| UID / Dashboard | First useful panels |
| --- | --- |
| offscreen-overview | Ready nodes/total, Pod phases/total, unhealthy workload count, CPU cores and memory vs allocatable, resource use by namespace, installed component coverage table, latest scrape freshness, links to details |
| offscreen-kubernetes | Every namespace/pod incl completed jobs, desired/available replicas, restarts and OOM reasons, CPU and memory time series per running container, requests/limits, pending and unscheduled, PVC state/capacity where emitted |
| offscreen-nodes | Node state, pressure, CPU/memory vs capacity/allocatable, top namespaces and workload use; no unsupported host disk panel masquerading as zero |
| offscreen-postgres | CNPG health, transactions, connections, locks, replication applicability, storage |
| offscreen-temporal | Server request/latency/error rates by role; task/persistence metrics where actually emitted |
| offscreen-storage | SeaweedFS health/native metrics and PVC inventory, with explicit unsupported panels omitted/annotated |
| offscreen-messaging-cache | Redis availability/hit ratio/memory/evictions and RabbitMQ aggregate queue depth/message rates/connections/alarms |
| offscreen-observability | Prometheus job status and freshness, scrape errors/limits, active series, Collector ingestion/drop/export, Loki/Tempo/Grafana self-health where emitted; link to existing Explore logs/traces |

Use a fixed dashboard freshness rule: for 30s jobs, a current successful target is `up == 1` with sample age at most 90s; missing series or stale samples are not healthy. `up` is scrape availability only. Inventory health requires a fresh KSM source and successful list/watch for required resources; a zero count from unavailable KSM is unknown. Expected optional component absent only when observed inventory supports absence with healthy collection and no known degradation; label this as an observed inventory result, not strongly consistent API absence. KSM can serve cached objects during delayed or interrupted watches even while scrapes succeed. List/watch signals reduce uncertainty but cannot prove every cached object is current; show confidence/unknown on known degradation and use native kubectl for decisive absence checks. Parked requires existing workload with desired replicas zero, not missing Pod data. Component domain health has separate metrics, and panels use no-data/unsupported states rather than `or vector(0)` on missing series. Node allocatable memory and container working set are separate measures; don't sum both kubelet resource and cAdvisor for same resource, don't claim pod working set equals total node use. For CPU use cores (`rate` over 5m), for memory bytes, percentages only with a valid nonzero denominator; network only once per Pod interface with loopback/duplicate sandbox exclusions and native evidence. Omit unverified disk/network panels rather than invent values.

Minimum overview is not just charts: each fixed component row must show inventory present/absent and target enabled/expected vs observed, readiness, metric freshness, and declared coverage limitations. Optional absence is distinct from scrape failure; zero-ready Pods with existing replicas is distinct from deliberately parked workloads; stale samples and missing jobs never show healthy. Derive fixed component names from versioned dashboard/coverage declarations with PromQL against KSM and target metrics; no new status database. Test dashboard JSON, unique UIDs, variable expansion, query semantics and actual data. Document operator route and native kubectl cross-checks in existing runbook.

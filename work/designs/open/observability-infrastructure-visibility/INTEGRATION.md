## Occupied installation transition (required before live acceptance)

1. Preserve E1 variant inputs independently from target E2 inputs. Exact E1 dev desired Collector is the occupied predecessor (owner observed revision 2); revision number alone is not identity. Older base Collector installations must complete their existing supported transition first, not be adopted as E2. Resolve desired and historical variants independently, preserving existing Collector upgrade semantics. E2-I/R/S are construction scope boundaries, not a runtime selector; one approved immutable desired dev bundle. Classify absent, exact E1, exact E2, known owned intermediate pending, foreign/mixed and unreadable separately. Release never follows this path.
2. Under existing exclusive custody, re-observe identity/context/namespace UID, exact Helm manifests/history, admitted workload images, named RBAC absence/collisions, storage and memory. Stop old/incompatible observability mutators before upgrade and verify shared lock/pending semantics; do not rely solely on Git integration. Read-only forwards may require quiescence under existing custody. Record exact pre-upgrade data-plane state and positive synthetic markers in each backend. Existing pending/foreign/unknown state refuses without mutation.
3. Persist a validated pending record **before** mutation, bound to cluster/namespace UID, exact E1 and E2 artifact identities, affected release revisions, phase and preservation set. Select a distinct versioned E2 pending operation kind with fixed phases `prometheus-intent`, `grafana-intent`, `final-verification`; initial intent before first Helm invocation, durable phase update only after previous exact postcondition, final clear only after final proof. Record no credentials or payload. Generalize only required schema and verifier; old readers must continue to refuse any unknown pending record. Use existing supervised Helm mechanism. No `--force`, deletion/recreate, uninstall, PVC changes, adoption or `--reuse-values` implicit merge. Native render and exact explicit values/args are authoritative.
4. Upgrade only Prometheus first: existing server Deployment/Service/PVC identity retained; Pod/ReplicaSet identity may change as part of rollout. Add precisely owned helper workloads and RBAC; wait for exact desired Prometheus phase, ready selected core scrape pipeline and retained metrics marker (bounded scrape convergence; absent optional platform is not required to be up). Confirm both unchanged release artifacts and storage identities before next write. Loki, Tempo, Collector and Grafana unchanged at this phase. Then upgrade only Grafana: retain its admin Secret, Service, datasource UIDs, release history and Deployment; expected Pod roll allowed. Other unchanged workloads, manifests and data remain intact. Confirm final structural identity, actual coverage and persistence; then clear own pending record through existing proven custody protocol. Repeat on exact E2 is no mutation. Grafana dashboard failures do not permit deleting storage or other services.
5. Partial failure, timeout, lost identity, interrupted process or ambiguous Helm state stays fenced and reports phase, observed state and permitted next action. No automatic destructive rollback or pending deletion. Select NO automated resume or rollback for E2. Report pending/manual recovery required with phase, last proven postcondition, exact observed differences and custody path. Known intermediate must never be classified ready or treated as fresh install. Future owner-directed recovery requires a separate bounded design/commission and preserved pending evidence; never delete or rewrite a pending record to re-enable ensure. No recovery command promised here. Tests must exercise failed/unknown writes and old/new mutual refusal. Finalization is one live exclusive operation; a crash after successful Helm but before final clear still leaves pending. Fresh install and normal repeat ensure continue to use existing lifecycle and must reject unexpected objects.

Data guarantees: preserve namespace, admin Secret, all three PVCs/PVs/bindings and stored metrics/logs/traces, existing Helm history and unrelated release identities. For upgraded components permit only expected manifest and rollout changes. Existing unupgraded backend Pods should not be deliberately restarted; if independent restart invalidates observation, re-observe/refuse rather than infer preservation. Keep existing retention, no credentials in receipts. Query historical marker within retention before/after upgrade; identity alone is not data proof. Bounded telemetry interruption during rollout is expected and must be reported, not promised lossless.

## Service-owner prerequisites and joint sequencing

Observability does not own node certificates, object-store rollout, Redis ACLs or service configuration. E2-R may use the existing serving certificates only if the native trust gate passes. Otherwise a separately owner-authorized cluster-owner operation is necessary; no node recreation or live CSR changes under observability custody. For SeaweedFS, select port 9327 on the existing dev mini process, same image, data path, S3 port, Secret, PVC/PV and service identity. Exact 4.54 source confirms the flag; existing owner verifier requires exact workload shape and must be evolved with the chart. Occupied migration must be explicitly authorized, acquire the object-store owner's existing guard/custody, classify exact predecessor and target, prove retained data with an existing bounded object marker and native chain/readiness proof; a controlled single Pod restart is expected and requires no active consumers. No delete/recreate of storage, no concurrent object-store ensure, no release mutation. If the object-store lifecycle does not safely admit the transition, retain inventory-only coverage and owner-ratify that smaller scope before E2 join; later independent enrollment remains open. The observability upgrade never invokes this mutation. Same principle for other metrics endpoints if not already exposed. No new provider calls or service workloads solely to manufacture a positive dashboard.

Use existing `pnpm obs:connect --queries` (loopback only), Grafana Explore or Prometheus API, and native kubectl. Example queries (verify actual metric labels against native source):

```promql
count by (job) (up)
count by (job) (up == 1)
count by (namespace) (kube_pod_info)
count(kube_node_info)
sum by (namespace) (rate(container_cpu_usage_seconds_total{container!="",container!="POD",pod!=""}[5m]))
sum by (namespace) (container_memory_working_set_bytes{container!="",container!="POD",pod!=""})
```

No fabricated dashboard numbers. A successful query is not necessarily a useful result: verify nonempty current series, units, expected identity and absence semantics. Capture actual coverage, not just screenshots. Source-only design artifact validation does not establish any of these native gates.

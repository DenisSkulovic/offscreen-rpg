# Source audit | pre-first-scene staging, profile loading and publication

**Status:** source-grounded investigation, 2026-11-20, *not an accepted contract or executed test*. Inspected the user-supplied `09d5820bcafedbed7cf969fe228ee84f44ff2405` snapshot, with GitHub `main` at `bff0f8c26c8c8a87746a3408fe99131898aeec45` before this note was written. Current `main` adds only this design dossier after the supplied code snapshot. If implementation changes, re-audit.

**Focus:** Not how to make the wizard attractive, but what durable, inspectable and permitted sources exist between pressing Play and publishing passage 1.

## Executable path today

| Boundary | Observed code | Consequence for design |
| --- | --- | --- |
| Draft form | `packages/db/src/schema/drafts.ts` stores `title`, `characterName`, `premise`, `storytellingDirection` and `storyteller` as separate fields. Premise SQL length is at most **6,000 characters**. | Replacing forms with arbitrary length freeform creative intent is a storage, schema, task-capture and user-limit change, not a UI-only refactor. Do not promise literally unlimited prompts. |
| Opening admission | `packages/application/src/storyteller/openings.ts` requires nonempty `draft.premise` and selected `draft.storyteller`; captures strict resolved JSON profile, optional start reference and bounded package knowledge inside a task. | A preset cannot simply skip form fields until the opening admission path accepts a fully specified *launch intent* and resolves default creative guidance. |

| Source material before opening | `loadStartPackageKnowledge` in `packages/application/src/storyteller/canonical-knowledge.ts` reads a *pinned start package* into bounded catalogue and selected bodies. | First opening can see some source-package documents, but not its own campaign-owned, writable and persisted workbench. |

| Source package materialization | `packages/documents/src/start-instantiation.ts` clones eligible source entries into a campaign manifest with deterministic IDs and provenance. | Checkpoint limits | `packages/application/src/stories/start.ts` stages a non-mechanical `absent` checkpoint or a quiescent mechanical `campaign` checkpoint in supported cases. Mechanical starts with obligations/active effects do **not** universally get a scene-1 checkpoint through that branch. | **Do not claim the existing code already pairs every opening with a valid checkpoint.** Launch redesign must explicitly define eligible openings and honest unsupported fork boundaries. |

An uncertain paid dispatch is not permission to try the model again. |

## Precise existing fact versus tempting misreading

- `STORYTELLER_PROFILE.md` **can be imported** as an authored Markdown `creative-guidance` document with suitable manifest metadata. **It does not automatically replace or override** the currently compiled strict JSON `task.profile`.
- The current start bundle's `START.md` is a source orientation. The bootstrap's generated `START.md` is a separate campaign orientation. Their mounted names already avoid collision only in a particular ordering.
- `premise.md` is currently assembled from fielded draft values at Start; it is **not** the precise original unedited multi-page Story Prompt. It uses `authority: canon`. A dedicated verbatim **user-intent** source needs semantics distinct from facts that are true in the fictional world.
- Descriptive document proposals are supported in ordinary continuation publication. That is not evidence of a general-purpose writable opening agent.
- The document store's physical CAS objects include JSON envelopes containing Markdown bodies. Converting storage bytes into standalone `.md` blobs alone would not address the model's missing Workdesk capabilities.
- `story_scene_checkpoint` is a SQL selector for a stored immutable checkpoint, not a Storyteller scratchpad. Pre-play drafts should never be represented as a fake scene-0 checkpoint.

## Immediate implications

1. Make a single **Launch** the externally visible operation, with captured prompt/source/profile/policy identities, even if internal creative responsibilities are multiple.
2. Use a **staged pre-play source/workdesk namespace** for any documents before the first published scene. A content hash is durable; only an admitted SQL selector makes it campaign-live.
3. Give required entry documents a **deterministic resolver** and budget treatment outside ordinary relevance-based catalogue selection.
4. Treat profile-as-Markdown as a creative source contract; let typed authority metadata, provider resources, clock, security and mechanical adapters remain explicit.
5. Plan a schema/API migration for freeform prompts and generic/nonhuman starts. No implementation authorization or quality claim follows from this audit.

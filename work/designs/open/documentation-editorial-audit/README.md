# Canonical wiki content refoundation | editorial program

**Status:** Proposed editorial design and source-grounded audit, 2026-11-18. **No code authorization; no selected Change; no automatic ratification.** This is a planned *content* workstream, not a new graph/CI/tooling initiative. Existing WIKI09–11/HK work may be assumed available for the *target workflow*, but current main is not claimed to have implemented them.

## What changed in our diagnosis

A reliable navigation graph does not make a passage clear, a requirements sentence well scoped, or two canonical articles semantically consistent. The 2026-11-17 lean source contains 73 product/technical Markdown pages (70 substantive after the three README hubs), about 129,339 whitespace-separated words, and 25 pages exceeding 2,000 words. The corpus has real high-quality thought. It also mixes normative targets, implementation snapshots, historical decisions, imaginative benchmarks, examples and unresolved policies in ways that deserve substantive editorial work.

**Goal:** make a newly arriving human or coding agent able to answer, from one locally owned claim and a small number of precisely linked dependents: (a) what is intended and selected, (b) what is only proposed or illustrated, (c) why the rule exists, (d) what failure it forbids, (e) what current implementation has actually proven, and (f) what other claims need review if it changes.

Do not optimize for shorter text, more links, or a passing arbitrary style score. Preserve the imaginative product experience and exact hard technical invariants while eliminating hidden authority/coverage ambiguities.

## The main judgment

**Keep the canonical product/technical ownership architecture; substantially rewrite selected text inside it, and selectively split documents whose responsibilities diverge.** An intact page is not automatically good prose. An oversized page is not automatically defective. A proposal in docs/technical is not an accepted contract merely because of its directory. A source-status correction is not license to overwrite accepted product intent.

This is intentionally *not* a single 129k-word rewrite. Each editorial wave has a change map, accepted-claim preservation notes, negative examples, proof of source/heading/link repair, and a second reader review. Existing docs remain the only binding owners until each proposed revision is separately ratified/merged.

## Dependency on preceding program

[Documentation impact architecture](../documentation-impact-system/README.md) addresses process and semantic edge graph; **this program addresses the content quality of the nodes themselves**. WIKI09–11 help monitor impact after adoption; they cannot decide what an unclear sentence was meant to promise. This editorial work uses those tools when available and can be reviewed manually without inventing a new code-bearing Change packet.

## Important division of labor

- **Editorial owner:** repairs grammar, structure, navigability, concrete examples and duplicated explanations without inventing product policy.
- **Product decision owner:** ratifies changes to player promises, shared-play policy, autonomy, spending grants, privacy or other normative product behavior.
- **Technical authority owner:** specifies exact implementation contract subordinate to the product decision; verifies code/evidence truth.
- **Independent reviewer:** actively attempts to find a counterexample, missing dependency or changed meaning before Done.

No coding-agent permission is created by this dossier. The queued [WIKI09–11 packets](../../../changes/README.md) and HK work remain their own separately selected work.

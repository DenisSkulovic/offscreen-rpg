## 1. Target and boundary

Owner direction (2026-11-28): move in short design/code/acceptance cycles across the internal plumbing before real RPG product flows. Infrastructure installation is the lower layer; application-level execution, agent runtime, persistence and delivery are the next layer. Small supported capability sets must still be correct. E1 is clean-slate for the new host boundary and evolutionary for its integration with the existing platform and Agent Core. Its target is a small reusable Node-side Temporal host, demonstrated by two provider-free consumers, with actual history, recovery and observable execution. No general-purpose workflow engine or production workflow migration.

| Included in E1 | Deliberately excluded |
| --- | --- |
| One grouped technical workspace `packages/platform/temporal-runtime` (`@offscreen/temporal-runtime`) | Relocating or renaming legacy `@offscreen/workflows`, changing existing app closures or queues |
| Native client/Worker connection custody and one serial, replaceable Worker lifecycle | Generic start/dispatch framework, registry DSL, multi-Worker manager, production topology, server installation |
| A plain synthetic Workflow and the existing Agent Core qualification host as the two consumers | Real providers, database writes, outbox, domain effects, money, user data, migration/versioning of live histories |
| Explicit start identity, bounded Activity retry, settled completion, duplicate refusal and replay/Worker replacement proof | Exactly-once external effect claims, crash during external effects, generic cancellation/signal/update API |
| Dev Temporal history and developer-lane correlated traces, plus accepted E2 infrastructure views | New observability platform configuration, generic SDK auto-instrumentation, application metric families, production telemetry |

The current gap is not missing Temporal infrastructure. The existing Agent Core runtime is source-accepted, but its maintained native qualification is outstanding; it also has a local host implementation mixing test policy, lifecycle and fixture registration. A plain native control gives us a reference independent of the AI SDK. Both consumers need the same host custody and can use it without either importing the other's Workflows. Deliver that small reusable capability, not merely a renamed test.

## 3. Selected architecture

Domain/agent owners define Workflow entrypoints, deterministic decisions, Activity interfaces and their domain admission. Host composition owns concrete Activity/plugin registration and native client configuration. Temporal owns execution history, dispatch, timers and retry decisions; it is not the owner of committed application facts or spend. Shared `temporal-runtime` owns technical custody, not business process semantics. The SDK remains directly visible to callers. No shared Workflow sandbox entrypoint: the package is Node-only and must never enter a Workflow bundle.

The E1 workspace has a single public Node root. Its small selected interface is `openTemporalHost({address, namespace}) -> Promise<TemporalHost>` with native `Client` exposed read-only, `startWorker(options)`, `stopWorker()`, `close()`, and an observable worker termination promise returned by `startWorker`. The options are native Worker options excluding connection/namespace (owned by host); require explicit nonempty taskQueue and caller-owned Workflow registration. Caller owns workflow start options, workflow IDs, queue choice, Activity policies and plugins. No implicit namespace/address, env lookup, retry policy, interceptors, model or Activity registry. The two connections are owned, never exposed as caller-closeable resources. Native client is borrowed; caller must not close its connection. Only the explicit test harnesses invoke this API in E1. No network on import.

One active Worker per session; `startWorker` creates and starts it and returns its run termination handle without claiming ready/polling. Lifecycle operations are serialized by synchronous admission state: overlapping start/stop/close operations refuse (except repeated stop of the same Worker generation or repeated close shares its in-flight/settled result); start after close or failure refuses. No start while running, no automatic restart. Successful stop requests native graceful shutdown and awaits run completion before permitting a new Worker; starting the next generation resets its stop receipt; a failed run stays a failure even if shutdown then succeeds. Capture asynchronous rejection immediately and make it observable to the consumer, not an unhandled rejection or silent stored error. Closing a healthy host stops/awaits the Worker first, then attempts each connection close independently; partial acquisition closes already acquired resources; retain primary and cleanup failures. If Worker quiescence cannot be established, fail custody and do not close a still-borrowed native connection or start another Worker; terminate only the owned bounded qualification process on operator-approved deadline. No claim of recovery from an uncertain cleanup. Caller owns operation deadlines and must race scenario waits against unexpected Worker termination. No OS signal handler, daemon, cluster operation, runtime installation or global SDK shutdown in the shared package. Use native options and no extra dependencies except pinned SDK/config/toolchain. Detailed TypeScript signatures and tests freeze in the Change packet; no undecided authority model.

The plain fixture lives under `temporal-runtime/test/`, not its exports. Use one deterministic `executionProbeV1(mode)` with enum `normal | retry-once | hold-after-activity`; reject other modes before dispatch. A single synthetic Activity returns a fixed literal. `retry-once` fails attempt 1 with a typed retryable ApplicationFailure, succeeds attempt 2 using native attempt identity, with no external effect. Explicit Activity start-to-close 5s, schedule-to-close 15s, maximumAttempts 2, initialInterval 1s; no Workflow retry policy. In hold mode a signal releases a durable condition only after the Activity result is recorded and a later Workflow task settled; caller replaces Worker on the same queue, signals the same run and verifies one actual Activity invocation. Workflow execution timeout 60s; no unbounded waits. Fresh UUID-based Workflow IDs with an `execution-probe-e1-` prefix; conflict FAIL and closed reuse REJECT_DUPLICATE, compare exact first run before/after both duplicate start attempts. Refusal is not generic idempotent business admission. Test host and fixture only; no production route. Existing Agent Core Workflow, mission ID policy, synthetic plugin, Activity retry restrictions, admission and cancellation behavior unchanged. Replace its connection/Worker lifecycle implementation, not its fixture semantics or scenario assertions; retain native replay API. A graceful Worker replacement tests rehydration, not hard kill, server failover or ambiguous Activity completion.

### Strict qualification namespace admission (H01 correction)

The existing Temporal infrastructure owner (`infra/platform/temporal/namespaces.mjs`) adds a separate strict qualification entrypoint. Keep `createTemporalNamespace()` and ordinary describe/registration callers unchanged, including their intentional already-exists tolerance. The strict route is a single bounded operator operation, not a runtime public API, and shares the existing owner command transport. Exact additive signature and invocation belong to the first construction packet. No new Kubernetes permissions or direct SQL.

Validate explicit dev profile, verified existing cluster identity/owner, fresh random valid `offscreen-agent-poc-` name with nonempty suffix, fixed one-day retention, and operator authorization before mutating. Use a fresh namespace name reserved for this qualification attempt; no concurrent owner-authorized maintenance of that name or cluster replacement during admission. Recheck the bound target identity before admission/use; refuse any drift. Observe the exact name with the existing owner describe transport; only an unambiguous namespace-specific absence (not a Kubernetes/transport/malformed failure) permits one create command. Require explicit successful registration (`ok`, zero exit, no timeout/missing/transport failure); **any** non-success, including either already-exists spelling previously tolerated by the ordinary helper, refuses. Do not use the tolerant helper for the strict create. Only after acknowledged success, perform bounded exact-name describe and require valid nonempty namespace ID, matching name and 86400-second retention. Unreadable, malformed, absent or mismatching verification refuses; a later describe never upgrades ambiguous creation to ownership. Record the verified namespace ID with the bound cluster and owned attempt receipt; both consumers admit only that successful qualification namespace identity and dedicated fresh queues. No automatic adoption, retry of create, repair, or deletion on any uncertain outcome. Record potentially created residual namespace for operator awareness; do not start execution or clean up foreign state. Existing namespace retention/deletion rules remain unchanged.

| Strict observation / result | Disposition |
| --- | --- |
| Exact absence, one acknowledged create success, verified name/ID/retention and unchanged cluster identity | Admit owned qualification namespace |
| Existing name at initial describe | Refuse before create |
| Ambiguous initial describe, generic not found, transport or malformed result | Refuse before create |
| Already exists during create (including same-name race), timeout, missing command, nonzero or ambiguous success | Refuse; no retry or subsequent adoption |
| Acknowledged creation but failed/absent/malformed identity or retention verification, or cluster identity drift | Refuse; record residual, no execution |

## 1. Locking: narrow the claim rather than build a scheduler

Observed:
- infra/platform/temporal/install.mjs::main uses util-linux flock, persistent ~/.local/state/offscreen-rpg/platform-locks/<context>-temporal.lock, 30s wait, child locked-ensure. ensureTemporal calls prepareFreshTemporalPersistence then Helm. Admission reads MemAvailable multiple times. An outer defaultPlatformRunner in infra/environments/platform-plan.mjs has 1200000ms temporal / 600000ms ordinary phase timeout, so the inner comment about no second timeout is not end-to-end true. Killing a supervisor alone does not prove its worker has exited.
- tools/dev-environments/src/domain/dev-worktree-registry.mjs::withExclusiveFlockLockFile/acquireSlotOperationLock use inherited descriptor flock and close in finally; registry and per-slot operation locks distinct. dev-lifecycle.mjs obtains slot lock and passes launcherHoldsOperationLock to avoid recursion.
- common commands assertPlatformTarget validates explicit Kind context, kubeconfig cluster/loopback port and baseline namespace ownership; readPlatformObject distinguishes absent from unreadable. Reuse.
- platform-plan runEnsurePreflight/runPlatformPlan do not establish a host-wide lock in inspected functions; other owners not exhaustively audited. Kind release lib.sh has MemAvailable and volume guard.

Decision: no distributed lock, reservation service, new Kubernetes controller or Redis lock. Reuse Linux flock primitive and persistent host-local paths. For structural PostgreSQL slice, one exclusive PG context lock for cooperating PostgreSQL installer and topology mutations, scoped to context and held through bounded reconciliation, and read-only plan/status do not take it. Treat local lock as coordination, not RBAC or fence against independent kubectl. Re-observe target/namespace/Cluster and capacity inside lock; native create-only and CAS remain required. Include Temporal persistence and dev tenant provisioning in same context coordination only when migrating those consumers, with explicit lock order and no recursive acquisition. Existing consumer-specific locks remain. Do not silently change unrelated lifecycle owners. Existing active worktrees running older tools will not participate: document quiescent upgrade/maintenance requirement.

Host-wide admission: previous defense counterexample is real, but a PostgreSQL-only host lock cannot guarantee workstation headroom against Tilt, Kind, Temporal or other allocations. MemAvailable is observation, not reservation. A lock released immediately after API mutation also fails because Pods allocate later. Do not introduce a fictional global guarantee. For structural slice preserve current admission policy, serialize PG resource-increasing operations across both contexts using one shared PostgreSQL mutation lock instead of separate context locks plus host lock (simpler, no lock ordering within slice). Hold from fresh admission to readiness or bounded failure, do not block read-only observation. This deliberately sacrifices parallel PG mutation, not parallel dev workloads. Revisit only if measured contention justifies finer granularity. This supersedes the initial context-lock proposal within this section; no second nested PG lock in slice. If a mutation outcome is unknown, release only after worker completion, report unknown; subsequent admission re-observes existing objects and pending allocations, refuses unresolved target operation. No claim to reserve all host resources. A true host-wide reservation/admission change belongs to environment composition and is evidence-gated, outside structural slice. Consumer onboarding later requires explicit compatibility order; no automatic global lock migration.

Supervisor/lifetime: inspect actual runner ownership before implementation. Use bounded child operations and one coherent outer deadline covering lock wait, acquisition, reconciliation and cleanup; do not SIGTERM only flock supervisor and assume lock or children cleared. Existing descriptor mechanism is candidate, but synchronous child may outlive parent on abrupt kill; choose supervised process group / inherited lock custody with focused crash tests. No unbounded retry or auto-delete. Exact mechanism remains design blocker for source commission; re-defense after source mapping. 

## 2. Application migration is not PostgreSQL infrastructure

Source: packages/db/src/migrate.ts creates dedicated pg Client, pg_try_advisory_lock(683291351), validates journal then migrates via Drizzle with schema drizzle/table __drizzle_migrations; migrations/runner.ts validates ledger before/after and closes Client. dev-slot-migrate.mjs opens separate admin Client, checks current_user/current_database, invokes applyMigrations with another Client, and separately verifies runtime login and public.offscreen_dev_schema_gate. Thus migration peak two migration connections plus runtime auth, not one; existing role limit 2 fits these identified clients without spare. dev-sql-tenant-grants.mjs::applyDevTenantMigration executes migration prep, calls migration runner, broad grants, verifies history, creates/upserts gate, grants SELECT and revokes INSERT/UPDATE/DELETE in separate awaited admin queries. The advisory lock ends before grants and gate publication; slot lock coordinates local callers but not independent migration invocations. Gate is in public, journal is in separate drizzle schema. Actual runtime auth is required by verifyRuntimeGate, so earlier proposed fresh NOLOGIN until entire migration adapter succeeds is circular.

Revision: preserve existing application migration contract for structural PG slice; no change to roles, login timing, gate, grants or schema. For later tenancy slice, explicitly split migration schema work/privilege publication from runtime authentication: provision closed/NOLOGIN resources, baseline ACL, open DB, enable migration role; migrate with existing journal integrity; publish protected gate and grants atomically before enabling fresh runtime role; verify actual runtime login and gate after enable, then project. Warm tenants must never be disabled merely for ensure. Application migration owner, not PG platform, owns this sequencing and metadata. Keep public gate compatibility for current runtime readers, avoid granting it write access even transiently: candidate move to protected schema with compatibility read-only view or explicit exclusion and no broad default public-table grants. Decide after full reader/DDL/default privilege audit. No automatic grant of public functions; verify journal schema denial. Extend database-level serialization across migration and publication (one session ownership or coordinated adapter using same lock without deadlock); do not nest acquisition from different connections. Need deliberate implementation contract and tests later, not part of PG structural slice. Actual negative login/DDL/gate write proof required. Capacity model correction: two migration Clients observed, runtime probe adds one runtime connection.

## 3. Revised bounded candidate

Structural slice: retain chart/identity/pins/configured numeric values for parity, replace duplicate dev/release install and shared topology observation, use guarded create, same-UID readiness, honest unknown outcomes, explicit native topology CAS and one PG mutation lock. Do not tighten baseline ACL or change application/Temporal policy during this slice. Existing access issues recorded separately, not fixed incidentally. Preserve existing consumer entrypoints until exact call/test closure. This is a coherent useful outcome independent of migration and resource tuning. Existing security drift must be surfaced, not certified as safe. No claim of production security or capacity.

Counterarguments:
- Why single PG lock? Local human-driven infra mutation is rare; holding it across readiness costs concurrency only for PG mutation, removes multi-lock admission race among participating PG writers, simpler than reservation ledger. It does not serialize ordinary application queries or slots. Bound wait and operation. If later contention is significant, reopen.
- Why not move all locks into common now? Other platforms/slot lifecycles have distinct ownership and current source contracts; migration of all is unneeded and dangerous. Reuse primitive, avoid cross-platform rewrite.
- Why defer application security? It requires explicit data/permission and migration changes; bundling with structural parity makes failures harder to attribute. Separate tracked gate, no loss of existing protections, no false declaration that security is solved.
- Why not use no lock? CAS fences one Cluster but cannot serialize multi-resource create or admission across contexts; native controller cannot see local host policy. One cooperating PG writer is meaningful.

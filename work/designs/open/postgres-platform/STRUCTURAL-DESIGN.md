# Structural PostgreSQL renewal | current proposed specification

Status: revised after committee pass 02; not submitted. Source baseline 73b3154025e94ad2f827cdb03eda4b389e19ac35; integration main 396245893f52410b7b86deb5c626c66bd4683810. This is the authoritative proposed structural design. Prior versions available in Git, including eb488ab3. No implementation commission.

## 1. Select a smaller architecture, not a more elaborate control plane

The initial structural delivery is shared baseline installation and observation, not a replacement of every PostgreSQL mutator. Retain chart, pin, config, topology model, explicit CAS scaling, baseline/owned topology procedures, presentation and CLI, tenant and Temporal policy. Share actual native observation and baseline install between dev and release, reuse topology identity checks rather than rewrite them. Extend existing readiness helper with UID and production sleep. No generalized database lifecycle or operation engine. No new public CLI, journal, recovery daemon, distributed lock, global host reservation or custom process supervisor. Preserve numeric values and ACL/credentials/data. A separate topology operational hardening decision remains open; never claim this slice fixes every prior concurrency defect.

Why this wins against the previous broad proposal: baseline ensure has a stable declarative target and no legitimate update to an existing durable Cluster. Restricting its write vocabulary removes the need to recover arbitrary desired-state changes. Existing topology mutation has a different contract and must not be silently replaced. Do not pretend that splitting scope removes need to coordinate simultaneous old topology/tenant/install commands: explicit local maintenance window for installation when no other structural/tenant/Temporal mutator is active, owner responsibility until shared coordination is separately proved. Running applications need not stop for a read-only healthy reuse, but do not claim a formal host-wide guarantee. Source implementation of read-only observation can be isolated; production mutation acceptance remains gated on selected lock/tool proof.

## 2. Operation semantics (C02/C05)

References: Kubernetes API concepts https://kubernetes.io/docs/reference/using-api/api-concepts/ (conditional JSON Patch/resourceVersion); SSA https://kubernetes.io/docs/reference/using-api/server-side-apply/ (create-or-update, field ownership not resource ownership); Linux flock https://man7.org/linux/man-pages/man2/flock.2.html and https://man7.org/linux/man-pages/man1/flock.1.html (open file description / command mode). These establish documented primitives, not exact pinned tool runtime proof.

Baseline Namespace/Cluster create: exact deterministic name and manifest, POST/create only. If response lost, return failure with outcome unknown. Never update/delete/adopt; next explicit ensure observes same target. If existing compatible and healthy, reuse as observation, not proof that preceding attempt succeeded. If absent, an explicitly repeated baseline create of same pinned declaration competes on same name; at most one object can exist concurrently, losing create cannot overwrite winner. This reasoning assumes no external deletion/name reuse and unchanged pin/profile during recovery; enforce maintenance scope and prohibit configuration changes after unresolved incident without owner inspection. Unknown creator identity cannot be proven from name alone; existing baseline labels and compatibility are local ownership policy, not cryptographic proof. Foreign collision refuses. Partial known baseline namespace with absent Cluster can be resumed only if expected ownership and healthy operator verified. No automatic retry within invocation.

Operator install: previous SSA is an upsert and cannot be defended as create-only. Prefer pinned manifest create-only (validate ordered artifact and exact resource inventory, actual install experiment required). If all expected resources absent, authorized create, no force. If response lost, inventory again; all expected compatible and ready => reuse, none => explicit repeat same pinned create, subset => refuse ordinary ensure and explicit owner-authorized maintenance to create only verified missing resources after compatibility review; never reapply full artifact or delete operator. Exact inventory and recovery command remain evidence-gated. No adoption of foreign preexisting objects. Do not assume API multi-object create is atomic.

Topology CAS: retain existing UID/RV/count test and replace spec.instances only. On lost response same UID+desired spec means desired state observed, not proof of causality; old spec alone cannot exclude late commit. A subsequent opposite request that becomes a no-op does NOT invalidate old CAS. A fresh successful conditional write advances RV, but not guaranteed for a no-op patch; do not propose a fake fencing write without testing actual semantics. Therefore C02 remains open for arbitrary topology mutation/recovery. Separate design must decide whether a target-scoped durable marker or native fencing is needed; no universal pending-intent file in baseline installation. Existing topology path remains untouched by initial installer consolidation except additive shared observation/readiness helpers with compatibility wrappers. No guarantee that the old topology receipt is corrected by this slice.

Cross-context resource admission: existing memory checks are estimates, not reserves. No universal global refusal marker. Pending Cluster readiness and partial operator state must refuse additional installation in affected context; cross-context host allocation still a local operational risk, not a newly promised invariant. Manual owner quiescence is a documented constraint for new install/scale maintenance, not hidden automation. This is less ambitious than prior structural proposal and must be explicitly reviewed by committee.

## 3. Process custody (C01)

Retain ordinary util-linux flock as cooperating local install serialization; prefer reuse of existing dev registry inherited-descriptor primitive instead of a custom supervisor. Candidate: open persistent ~/.local/state/offscreen-rpg/platform-locks/postgres.lock, flock -x -w 30 3, close in finally; pass inherited fd 3 to direct mutating kubectl children. No nested shell/supervisor, no detached worker. Exact kubectl descriptor retention still requires actual tool experiment; no claim of crash-safe lock before it passes. Existing outer 600s timeout conflicts with readiness cap 600s; choose one finite total worker deadline, derive outer timeout from total plus lock wait and process-exit margin, do not let outer SIGTERM silently imply completion. Direct bounded child execution with SIGKILL on timeout, stage cap clipped to remaining time, real sleep. Do not remove outer bound entirely or introduce unrelated platform runner redesign. Specific budget and subprocess proof remain gated. C01 not closed.

## 4. Compatibility matrix (C03, partial)

Reuse existing topology/model.mjs::assessLiveClusterIdentity and assessLiveOwnedClusterIdentity field vocabulary. Common observation compares actual rendered declaration, not duplicate constants. Profile contexts, namespace names, ownership labels, baseline Cluster names preserved. Require nonempty namespace/Cluster UIDs, no deletionTimestamp; namespace owner label exact (dev offscreen.dev/owner=offscreen-dev; release offscreen.rpg/lab=disposable), dev Cluster label exact; release current chart deliberately has no Cluster owner label, so do not introduce mandatory label or claim strong provenance. Release ownership is exact namespace label + name + compatible spec under local maintenance authority. Owned experiment contract stays unchanged. Require exact pinned spec.imageName, bootstrap.initdb database/owner/localeCType/localeCollate, storage class and semantic size (normalize Kubernetes quantity, not string equality); explicitly allowed count any positive safe integer, healthy reuse preserves actual count. Native omitted enableSuperuserAccess is false per tagged CNPG source; true refuses. Resource requests/limits and configured PostgreSQL parameters compare semantic quantities or explicit strings; report mismatch and refuse ordinary ensure, no silent tuning. Unspecified operator-default fields are not blanket compared to rendered omission; exact security/extra config list still requires pinned schema review. Operator inventory, readiness and default normalization not fully settled. Do not mark C03 complete.

## 5. Composition and concrete behavior

Keep public entrypoints and adapters initially. Existing chart produces Namespace and Cluster documents, pinned image overlay and profile values unchanged. Desired implementation: shared baseline installer/observer functions behind dev-bootstrap and release-install compatibility surfaces, shared identity/ready helpers, existing topology modules remain. Remove duplicate internals only after source references/tests mapped. No proposed new tenant folders in this slice. SPECIMENS.md and earlier ARCHITECTURE/DEFENSE documents are historical or later-scope research, not normative here. Current concrete manifest is the actual chart/profiles/development.yaml and release.yaml plus _helpers.tpl; no new manifest fields for baseline. Expected normal operation: confirm explicit context -> render -> observe operator and baseline -> healthy compatible no write; fresh install -> create only verified absent operator objects -> observe CRDs/deployment/webhook -> create namespace and Cluster only absent -> verify same UID readiness and actual writable primary using existing readiness path. Unknown failure -> sanitized receipt, no auto repair; preserve durable objects.

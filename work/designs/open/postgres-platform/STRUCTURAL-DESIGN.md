## Operation custody (C01): selected candidate

Use one workstation-local kernel flock for all new structural PG mutators, persistent path ~/.local/state/offscreen-rpg/platform-locks/postgres.lock, never unlink a lock file. Linux/WSL same user/workstation only. No distributed lock or all-host reservation claim. Quiesce older mutators and consumer provisioning during migration to this contract; later consumer coordination is separately designed. Read-only plan/status do not lock. Existing slot and Temporal locks are not replaced. No nested PG lock.

Use util-linux flock --exclusive --wait 30 --no-fork FILE node <worker> ... at the actual mutation entrypoint (not a lock-owning supervisor spawning a detachable worker). --no-fork exec replaces flock with the worker, retaining the locked descriptor. Worker itself performs the bounded operations; no shell wrapper, background children or nested installer. Critical distinction: --no-fork alone does NOT protect against worker SIGKILL while kubectl survives. Therefore do not claim custody solely from parent lifetime. Select explicit inherited FD custody instead if native executable cannot expose its descriptor reliably: open persistent lock file in worker, acquire flock -x -w 30 3 using inherited fd 3, retain open file description and pass same descriptor as fd 3 to every mutation subprocess via spawnSync stdio array, close only in finally. This second form is the selected implementation candidate, superseding the first command example; it mirrors dev-worktree-registry.mjs::withExclusiveFlockLockFile and adds child inheritance. No forked mutation worker or subprocess wrapper; use direct kubectl, no shell. Child must not close inherited descriptor prior to exit: actual kubectl behavior requires discriminating local proof. If inherited custody cannot be demonstrated, stop and choose a tested alternative, not a claim of safety.

Outer platform-plan defaultPlatformRunner currently times out ordinary phases at 600s, while readiness itself is 600s. Replace PG mutation phase outer timeout with no independent killing timeout, invoke direct worker and rely on a single worker monotonic absolute deadline; retain unrelated phase policy. Each native command receives min(stage cap, remaining deadline), bounded output and killSignal SIGKILL for local direct process timeout, with no detached mutation subprocess. No unbounded spawnSync waiting on SIGTERM. Lock acquisition bounded 30s; initial candidate operation deadline 1200s after lock acquisition (existing Temporal outer budget precedent, not measured PG SLA), each wait/read command clipped to remaining time; real poll delay clipped to remaining time. Existing 600s readiness cap remains upper bound within total. No new mutation after deadline; final receipt may mark unknown. No cleanup of durable resources. Parent abrupt death can still leave child running; inherited custody proof must include SIGKILL parent and competing lock attempt. Local child termination does not cancel API-side reconciliation. Do not change global command behavior for other platforms.

Evidence needed: small disposable local subprocess fixture, using exact selected Node and util-linux versions, checks fd inheritance and kernel lock held until last mutating child exits, lock wait, worker timeout, parent SIGKILL and child exit. Then exact kubectl version fd retention test with a harmless blocked/read-only request (no cluster mutation). Do not certify C01 until this passes. Official references to verify: util-linux flock(1), Linux flock(2) open file description semantics, Node child_process spawnSync/stdio/killSignal. No tests run yet.

## Unknown outcome and subsequent admission (C02): proposed contract

A local lock serializes cooperating writers, not server-side reconciliation. Introduce no permanent registry merely to track a successful topology request. Native spec/status can identify a known in-progress reconciliation, but cannot prove that an API request whose response was lost will never arrive late. Therefore preserve a minimal durable uncertainty fence, not a general operation ledger: one host-local pending intent file under the same lock directory, atomically written before each potentially mutating API call, containing only profile/context, target kind/name/namespace, known UID/RV, intended mutation kind and desired count or manifest identity, operation ID; no Secrets or raw commands. fsync file and directory before issuing write; atomic rename; single writer under PG lock; refusal on malformed/unreadable marker. Remove only after verified outcome and reconciliation (or definite pre-write refusal), fsync directory. If process dies before request, conservative marker remains. No auto-expiry or retry. Explicit owner-authorized recovery examines marker and same target, does not resend mutation. If known same UID and desired spec observed, wait for stable readiness, verify no other drift, record observed result (not proof of causality), then clear marker. If target absent, old spec remains, identity replaced or unreadable, do not infer request failed; keep fence and require explicit maintenance resolution based on API/audit evidence or authorized quiescent recovery. No automatic adoption or deletion. Unknown create without returned UID: matching object is not ownership proof; require explicit inspection and authorization. For operator multi-object SSA, partial inventory blocks ordinary ensure; no implicit repair.

Before resource-increasing mutation, under PG lock inventory both explicit contexts and all managed baseline/owned PG Clusters (including pending/terminating). Distinguish verified absent Kind cluster from inaccessible context. If any existing PG Cluster is unhealthy/pending/terminating or inventory cannot be verified, refuse new resource-increasing mutation; ordinary read-only diagnostics available. Scope to PG, not other workload allocations. Pending desired count may allocate after command returns: observe readiness before clearing marker. Even after success, memory limits are not reservations; report admission estimate, not global guarantee. Foreign resources do not become managed via label adoption; their resource consumption is observed in host memory only. An unresolved marker blocks all new structural mutations across both contexts; status reports its sanitized identity and reason. No new public recovery CLI in this design until exact safe recovery authorization and caller semantics are reviewed. Explicit maintenance can inspect marker and state; clearing must be an authorized operation with evidence, never rm as normal procedure.

This is a deliberate revision of prior no-ledger preference: a single crash-surviving uncertainty fence is justified by a delayed API request counterexample that native state alone cannot disambiguate. It is not a second reconciler. Need re-defend whether conservative recovery is operationally proportionate; design exact recovery command and marker durability test before committee pass.

## Shared scenario and architecture
Mission M: a Storyteller investigates a pinned Library root R, reads a prior promise, optionally delegates one continuity question, stages a draft in private Workdesk, returns typed proposal. Not every mission needs all these operations. A domain admits M under current user, tenant, campaign root, grants, funding ceiling and immutable profile/version references. Capture admitted definition and inputs; current grants are rechecked at protected effects. Start one named Workflow with idempotent admission/start reconciliation (transaction/outbox candidate; exact algorithm open). Worker replica is not agent identity. Workflow builds deterministic runtime from recorded input and Activity results; external I/O only in Activities. Workflow is execution progress owner, not canonical game/Library, custody ledger or commercial authority. SQL status projection must not become a second loop controller. Domain publication validates current root and proposal under authority transaction independently of SDK finish reason.

Example sequence: load admitted manifest -> construct SDK loop with bounded tools/model proxy -> model A -> authorized read -> model B -> optionally child mission -> stage draft -> final typed proposal -> authority accepts/rejects. SDK handles message sequencing; no fixed mandatory rounds. Domain callbacks and tool definitions are Workflow-safe; actual DB/S3/network operations run outside sandbox. Profile identity, document context, tool registration and granted resources differ. Replaying captured context is not permission for new reads or dispatch.

## Vercel: generation-first, minimal agent abstraction
Workflow uses generateText multi-step loop (documented integration), optionally ToolLoopAgent if verified compatible. Supply captured instructions, bound model proxy, explicit stop conditions, tools whose execute callbacks proxy guarded Activities, schema and deterministic prepareStep. prepareStep can alter messages, settings, model and available tools between calls, but cannot query DB without Activity and must not bypass route admission. Worker AiSdkPlugin accepts ProviderV4; TemporalLanguageModel.doGenerate serializes modelId/options and invokes model Activity. Worker resolves provider.languageModel(modelId), prepares file URLs, calls doGenerate, strips raw request/response bodies in returned metadata. Guarded Worker model is candidate seam, actual bytes must be captured at dispatch; restrict URL prep (occurs before model adapter) and unsupported modalities. SDK/tool loop owns message/results, not application-defined agent identity. No requirement to use its Agent class for a mission. Direct inference can reuse same provider primitives outside Workflow via guarded inference owner. Workflow-side direct model object is proxy, not actual provider client. SDK-native subagent APIs are optional; a tool invoking an admitted child Workflow is sufficient.

Advantages: broad model normalization and direct inference reuse, explicit per-step control, low abstraction commitment. Costs: implement our own mission composition, delegation policy and lifecycle semantics; no claim ToolLoopAgent or every v7 harness feature works under integration. Need v7-specific APIs (isStepCount per current docs; older stepCountIs snippets not normative). Set SDK retries explicitly and independently govern physical dispatch. Candidate initial specimen uses documented generateText, no streaming or hosted tools.

## OpenAI Agents: agent-first runner
Workflow instantiates Agent definition (name, instructions, tools, output schema, model string), invokes TemporalOpenAIRunner. SDK controls run state, turns, tool calls, handoffs and final output; ActivityBackedModel serializes ModelRequest and modelName, uses proxyActivities (or optional local Activity; initial proposal regular Activity). Worker ModelProvider.getModel resolves model and calls getResponse. Custom Model can bind guarded inference, but translating every provider into OpenAI Agents ModelResponse/input item semantics may duplicate provider normalization if our direct inference uses another SDK. Do not assume direct inference should use full runner. No ambient provider defaults, hosted tools, server-side conversation or external trace export. Need explicit current grant/budget enforcement on Worker regardless of runner hooks/guardrails. Workflow-safe context may carry trusted metadata, but plugin model request and tool Activity bridge do not by themselves establish mission identity; see common binding below.

Native asTool and handoff semantics are potentially useful; handoff transfers control and not same as bounded research child. Initial design keeps parent controller, invokes admitted child Workflow via tool. R4 docs/source version skew around agentAsTool vs intercepted asTool must be matched to release. No implicit inherited authority. Native sessions/RunState must not become second durable execution store.

Advantages: agent-oriented API, tool/approval/structured output features. Costs: provider abstraction shape, additional runner policy options, version-specific propagation/tracing. Prefer only if those agent-specific primitives eliminate meaningful application glue beyond Vercel or Strands. ## Strands: lifecycle-driven agent
Workflow instantiates TemporalAgent with explicitly named model, tools and Activity options, invokes it. TemporalAgent extends Agent, creates TemporalModel and disables SDK retryStrategy. During initialization plugin loads Worker model metadata (model id, context window, stateful flag); rejects certain stateful manager combinations. Agent runs lifecycle hooks and tool executor. Model Activity receives modelName/messages/options (and modelState for stateful variant), resolves model factory cached by name for process lifetime. Implement registered stateless guarded model; derive mission scope from Activity execution, never mutable cached tenant context. Explicit Activity tool/hook bridge for external effects; pure hooks for deterministic policy. Disable MCP/vended tools initially; require custom model and no default Bedrock path. Native conversation managers and interrupts may add value, but compaction must preserve source references and never alter canon; no need to build until shown. Child invocation uses same explicit admission pattern rather than relying on as-tool settings.

Advantages: richer lifecycle controls than bare loop, native Temporal integration explicitly disables nested retry loop, agent-centric and custom provider support. Costs: separate provider message/event abstraction and dependency footprint, process-cached model safety, version availability uncertain. Model state must not leak across tenants or routes. Evaluate ability to share Vercel provider adapters without incompatible provider v3/v4 conversion; don't adopt both just to avoid writing adapters.

## Reserve architectures, not merely reserve brands
Google ADK: construct Runner + agent(s) and in-memory session in Workflow; model proxy and explicit Activity tool; graph nodes offer deterministic branching but may add node retry, session and handoff semantics. Worker BaseLlm provider resolves name. Outside Workflow TemporalModel falls back to registry: deny bypass in composition. Version mismatch 2.5 vs <2.4 remains. Useful only if graph/ADK-specific semantics needed or primary gates fail.
LangChain/LangGraph: createAgent with middleware atop graph runtime; graph checkpoints own inner progress while Temporal schedules coarse mission Activity, or replace Temporal for agent progression. Coarse Activity must resume exact graph thread after crash, not restart from prompt. Need external effect ledger, checkpoint/lease concurrency, cancellation and status reconciliation. Not simply Temporal replay of each model call. No native TS bridge established. Alternative deterministic Workflow embedding unproved, do not build custom integration casually.
Mastra: use agent.generate/stream within Mastra workflow step; Temporal integration for workflow steps established at docs level, per-agent round bridge not established. If durable agent resume owns progress, use that as inner authority, not duplicate checkpoints. Broad memory/model routing/observability runtime overlap and adapter footprint; revisit only for material benefit.
Deep Agents: high-level harness composes LangGraph/LangChain with workspace/backend/skills/compaction/subagents. To fit Library need constrained virtual backend, default tool removal and explicit root/canonical publication policy. Its checkpointing has same durability choice as LangGraph. Valuable as pattern library, possible later domain harness if justified; do not run two agent loops nested by default.
Custom: Workflow while loop owns sequencing, provider primitives borrow SDK where useful; manually handle tool results, message order, model-specific continuation, approvals, stop/cancel and parallel execution. Only fallback if supported SDK seams fail. Temporal is not itself an agent loop library.

## Most consequential shared seam: trusted identity and custody
Native plugin wire examples include modelName/modelId and request, not our admitted mission or grant. Candidate regular Activity interceptor or Worker model wrapper reads trusted Activity execution metadata and looks up admitted Workflow->mission binding. For tool calls use Workflow-captured context plus independent validation against binding, not model-supplied tenant or grant. No reliance on process globals, model prompt, provider model name encoding, or SDK trace context as identity. One Workflow per admitted parent/child mission makes mapping unambiguous. Candidate stable logical Activity identity: namespace + workflow execution run id + activity id; exclude retry attempt counter. Validate actual Temporal identity semantics and scope before selection; Continue-as-New/new Workflow run creates new identity and cannot resume unresolved effect by accident. Persist application attempt ID and request fingerprint on first admission; reconcile retry to same record. Distinct SDK-generated Activities for repeated logical step must also be blocked by mission-level uncertainty gate; Activity ID alone does NOT deduplicate cross-Activity retries or child dispatch. Prevent concurrent new calls while unresolved attempt if policy requires; define serialized or atomic allocations for parallel effects. Exact schema and transition algorithm future design.

Four crash windows: (1) before durable dispatch authorization: safe to reattempt admission; (2) authorized/marked dispatch but send unknown: conservative hold, not exactly-once claim; (3) response and settlement durably recorded but Activity completion lost: return recorded normalized response, no provider resend; (4) Activity result recorded: Temporal replay uses result. Preserve response or durable reference in same correctness boundary as settlement; current grant checked before exposing sensitive result anew, distinguish replay from new reads. A cancellation or network timeout is not proof of non-delivery. Use retry policy only for safe operations and custody-aware recovery, not auto resend. Activity execution may time out while process still running; use fence and nonduplicating state transitions. Avoid SDK/provider/gateway fallback/automatic retries unless individually proven.

## Workflow history economics
Activity requests/results become history payloads. Each round may transmit accumulated messages; 8 rounds with 4k initial tokens + 1k extra per round has 60k cumulative input tokens (illustration, not a measured workload), and history also stores outputs/tools. Bound mission length, tool outputs and context; inspect actual encoded bytes and server limits, privacy/codec and retention. Externalize large artifacts by immutable reference only where runtime supports resolving safely; don't write custom context persistence merely to reduce history. Start with nonstreaming short missions; Continue-as-New or compaction only if measured need and unresolved effects reconciled. Agent identity and canonical documents survive independent of history retention.

## Comparative decision
Primary preference: Vercel AI SDK + Temporal documented multi-step generateText as smallest initial proof. Strands is strongest alternative when richer lifecycle hooks/delegation reduce real work; OpenAI Agents strongest alternative when dedicated runner semantics are decisive and provider conversion is acceptable. This ordering is a planner hypothesis, not selected technology. Do not implement three production wrappers. Run minimal comparable provider-free specimens; stop at hard-gate failure or decisive fit, deepen only survivors. Shared policy/effect fixtures are test support, not a universal runtime facade. All alternatives remain documented for committee scrutiny. Exact published artifacts still unresolved; no technology ratified before controlled evidence and owner review.

## Package implications
Keep four AI responsibilities from R3: agent-core (mission composition and selected runtime), inference (guarded dispatch and outcome custody coordination), model-routing (eligibility/capabilities), ai-providers (actual protocol adapters). Whether inference and ai-providers are separate workspaces depends on selected SDK and direct consumers; avoid wrappers around every upstream class. workflows owns shared Temporal infrastructure/host wiring; domain-specific and agent Workflow definitions may live with their semantic owner via Workflow-safe exports. Worker composition imports actual activities and plugin. Tool registry initially remains agent-core; generic tool package only if non-agent consumer proves reuse. No Redis, no new package or database chosen. No SDK types in Library/game authority or commercial contracts; internal SDK types allowed where useful.

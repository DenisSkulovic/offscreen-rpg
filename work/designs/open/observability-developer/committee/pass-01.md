## Ranked material findings

### OD-01 | High | Proof ownership and destructive cleanup boundary is not frozen
TARGET section 7 and V09 say dedicated UID-owned namespace, actual Pod execution and UID cleanup; SOURCE-MAP calls for tracking UID immediately. Baseline signals.mjs runSignalsProof creates namespace, ConfigMap and Pod, but records created only after all three succeed; deleteProofResourcesWithUid deletes Pod then ConfigMap then namespace using UID preconditions and ambient context. The design recognizes partial creation and frozen reads, but does not specify the authority to delete a namespace containing additional objects, the treatment of failed create with unknown UID, or whether all proof writes and cleanup use frozen identity and a shared session lock. UID equality proves namespace identity, not exclusive ownership of every object subsequently inserted into it. Counterexample: another local tool adds an unrelated resource to the proof namespace; deleting that namespace cascades to the unrelated resource even with correct UID. Another: ConfigMap creation succeeds server-side but times out before UID is captured; cleanup cannot safely guess its identity. This is not hostile tenancy; it is ordinary failure/ownership ambiguity in a shared local cluster. Blocks V09 repair and complete acceptance. Freeze per-phase ownership, frozen target for every write/delete, exact admission and handling of extra children/ambiguous creation, stop and retain on uncertainty, and lock/identity relationship between proof host, connection and upgrade. Demonstrate focused negative fixtures for unknown create outcome, partial cleanup, added unrelated child, replacement and target change; no name-only or broad cleanup. Do not expand into a general recovery controller.

### OD-02 | High | Live functional acceptance can confuse retained historic telemetry with current proof
Candidate experiments/data-plane.py uses fixed trace, span and run IDs and fixed values 17/3/.2; run-data-plane.sh starts disposable isolated backends, so those constants are reasonable there. TARGET section 7 and V08 transplant the positive/negative proof objective into persistent backends without freezing freshness, correlation and repeat-run semantics. Existing claims and retention are deliberately preserved. A prior successful run can satisfy exact-value instant queries even if the new export fails; fixed negative canary absence plus an unrelated positive control does not establish current delivery. Counterexample: rerun after a successful proof while Collector's metric exporter is broken, Prometheus still serves the prior sample within lookback; an exact trace ID may also resolve the old trace. Single-writer exclusion does not solve freshness. Blocks V08 and any backend functionality claim, not topology. Specify fresh trace/log identity per run and a metric observation bound to the new submission (timestamp/range or equivalent, no new metric dimension), pre-existing-series handling, scoped negative queries and positive controls per signal, no stale data credit, repeated execution against retained stores. Require a regression fixture where old successful records exist and new export fails. Preserve finite labels and no per-run metric dimensions.

### OD-03 | High | Remaining native certification and changed successor authority need an explicit execution relationship
Proposed CHANGE states serial with OBSERVABILITY-NATIVE and preserves original A1–A12, but ACCEPTANCE V12 and step 5 merely say reconcile later; TARGET section 2 changes dev desired render and artifact paths, while native canonical R30/OBS-03 requires revision1-only install and original A6/A9 clean isolated public CLI proof. New desired revision2 and new fresh desired revision1 change what the old acceptance tests would certify. The existing native gate is not waived, and a proof on a pinned old commit is not automatically proof of a modified successor. Counterexample: original A6 is executed against old source then the new artifact/lifecycle implementation lands; treating that receipt as certifying new fresh install is invalid. Conversely demanding terminal closure of native before developer repair may require using known-broken proof defaults. Blocks whole-Change integration boundary, not scoped design experimentation. Identify which original requirements remain on old source, which are re-exercised on the successor, which are explicitly carried forward as outstanding, and exact ordering/authority for overlapping open Changes. Preserve historical evidence and distinguish changed proof owner from waived gate. No requirement to execute A6/A9 now or to run release upgrades.

### OD-04 | Medium | Production geography correction is appropriate but incomplete as an ownership contract
Baseline infra/platform/observability/artifacts.mjs defines specimensRoot and reads pins, values and lock files as mandatory runtime inputs; baseline specimens/collector.yaml begins DESIGN ONLY. Directory has exactly five values, pins.yaml, image-lock-candidate.tsv, expected-inventory.json. These are not experimental files in operation; they are production installation inputs mislabeled as experiments. User's objection is substantiated. Sibling gateway has root values.yaml/pins.yaml/vendor; Redis and RabbitMQ use chart/ (RabbitMQ also vendor). R4 values/, locks/, root expected-inventory.json, vendor/ unchanged is coherent for five independent upstream releases, unlike a fabricated umbrella chart. Experiments correctly belong under active dossier, not runtime. However TARGET/SOURCE-MAP leave exact new lifecycle/connection/proof owner paths TBD and no explicit enduring directory ownership map for runtime, host helper, proofs and fixtures. This matters because shared foreground supervisor must be reused by proof paths, not copied into a new experiment directory or second harness. Blocks final geography acceptance, not D0 selected rename. Freeze a small end-state tree with owners and dependency direction, identify canonical operator runbook owner, separate runtime config/vendor/locks from maintained verification and historical design evidence; require full tracked reference census before D0 and no old runtime fallback. Do not impose identical layouts on unrelated platforms or move historical evidence to make grep empty. Naming alone is not the failure; false authority and accidental promotion are.

## Affirmative judgments and evidence limits

- D0: preserve exact parsed render, digest/inventory and immutable historical references; correct the misleading runtime designation. Actual path migration not run.
- Dual receiver: old Pod-IP diagnostic ports retained, dev wildcard inside Pod on 4327/4328, fixed loopback forwards, no new release or resource identity. Owner chart schema failure then correction, exact pinned validation and data-plane experiment support feasibility. No authentication or hostile isolation inferred.
- Metric design: the generator filters extra datapoint dimensions instead of collapsing them and strips exemplars. 2 services x 4 candidate values x 10 series = 80 application series under fixed bucket and trusted single-writer assumptions, plus target_info; not a global bound. Gauge _ratio is awkward but explicitly documented, no blocker. Producer numeric validation and concurrent writers remain excluded as declared. Experiment substitutes debug exporter, custom isolated Prometheus config and no actual Loki/Tempo path; script asserts marker presence/absence and some numeric values, not exact parent/child record counts or every bucket value. R3.2 reports human inspection; credit representative processing, not full production proof.
- Lifecycle: one exact predecessor transition, no automatic rollback, stable shared/exclusive flock, durable pending and frozen identity are proportionate. Source confirms actual existing in-place O_TRUNC pending advance, blind clear and ambient reads; targeted correction justified. R4's history restrictions and exact manifest/narrow live projection are sensible, not a claim of general drift protection. Real upgrade and API normalization remain V04–06 acceptance. No demand to implement before defense.
- Foreground: direct exec, expected parent check, Linux parent-death signal and inherited lock are a plausible bounded alternative to a daemon. V07 must exercise actual parent death, FD lifetime and child cleanup. No requirement for persistent reconnect or gRPC signal certification.

V10 should also reject empty role sets, stale sample timestamps and missing required roles; current summarizeResourceSamples can return empty/error subreports while caller returns ok:true. Treat these as mandatory negative acceptance refinements alongside OD-02, not a separate architecture redesign.

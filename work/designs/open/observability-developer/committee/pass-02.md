## Whole-platform architecture assessment requested by owner

The target deployment is recognizable expert platform engineering: five independent native upstream Helm releases, immutable chart/image inputs, values plus one dev overlay, no synthetic umbrella chart, one Collector with distinct diagnostic/developer policies, existing backend persistence and Grafana provisioning. Prefer this to duplicate Collector, arbitrary unrestricted ingress or a permanent port-forward daemon. Runtime artifacts no longer masquerade as experiments. The separate infra/verification/smoke/observability tree is the right boundary. No new cluster for everyday qualification; release behavior remains unchanged.

The principal architectural debt is custom orchestration, not component selection. Existing install.mjs (870 lines), artifacts.mjs (639), custody.mjs (505) already total 2014 lines before identity/inventory/readiness/receipt/tests. Proposed upgrade.mjs, connect.mjs, forward.mjs and exec-owned.py add distinct necessary responsibilities, but the resulting subsystem is unusually elaborate for local development. The strict ownership/preservation/refusal requirements explain much of this, and previous actual proof defects justify bounded repair; complexity must not be defended solely because it already exists. A typical expert might use ordinary Helm/GitOps lifecycle and ephemeral namespaces if owner constraints differed. Under current constraints these are not equivalent substitutes. No mandatory redesign is justified on line count or aesthetics alone.

Nonblocking engineering recommendations: keep upgrade as narrow orchestration over existing artifact/identity/inventory/custody primitives, not a second installer; one forwarding supervisor, no duplicate port-forward code; preserve one policy source per lane, no runtime generation from experimental Python; consolidate accepted normative amendments into existing canonical owner on promotion, do not turn dossier layering into permanent operational documentation; provide a short practical runbook for connect/status/upgrade/refusal and namespace cleanup debt. Watch repeated namespace retention and known-predecessor revision ceiling as explicit operational limitations; do not pretend this is general-purpose production upgrade tooling. Evaluate custom module size and reuse during packet/source review, not by speculative refactoring now. These recommendations reinforce R5 selected boundaries and are not new design gates.

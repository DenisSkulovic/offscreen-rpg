# Audit | Why a healthy wiki can still drift

**Measured against:** supplied lean export at commit f3e3bfe35490932ee363c00aad0fb239893d825e; GitHub main Change queue, Change standard and representative active packets fetched on 2026-11-18. Archive/evidence are excluded from the lean ZIP, so no archive completeness or clean full-checkout CI claim is made. **Audit status:** file/link counts measured locally; guard behavior inspected statically; full Node-based wiki tools not executed because npm dependencies are absent from the supplied export environment.

## A. Existing strengths, not merely slogans

- The [documentation rule](../../../../.agents/rules/documentation.md) explicitly makes product documentation the product authority, technical contracts second and code an artifact, and requires reconciliation before Done.
- The [Change work-unit standard](../../../../.agents/references/change-work-unit-standard.md) already requires authority headings, baseline, code intent, negative proof and a close ledger.
- The [Change template](../../../../.agents/skills/change-workflow/assets/CHANGE.md) includes a seven-column *completion* reconciliation table.
- The [existing guard](../../../../scripts/repo-tools/wiki-core/change-guard.mjs) has plan/close modes. In plan mode it checks for owner mentions, title, state, source-looking path and negative-proof words; in close mode it parses the seven-column ledger, verifies some paths/headings and checks undeclared changed files.
- The wiki graph/retrieval work improved doc discovery, linked-root coverage and heading retrieval. Those are useful achievements.

## B. Gaps confirmed from source

### Failure 1: planning describes code; documentation is mostly a postscript

The Change template's **Code scope and exclusions** is concrete. Its **Authority and baseline** identifies canonical owners, but does not make a planned *edit/no-edit decision for each plane*, its upstream/downstream dependent headings or the anticipated authority disposition. The real [UI01 packet](../../../changes/open/2026-11-17--ui01-semantic-tokens/CHANGE.md) provides four detailed implementation steps but only broadly requests owner-link reconciliation after execution. [DIR01](../../../changes/open/2026-11-17--dir01-appearance-roundtrip-proof/CHANGE.md) has the same shape. HK02's ledger is more detailed but still chiefly a close-time receipt.

The [plan guard](../../../../scripts/repo-tools/wiki-core/change-guard.mjs) accepts the presence of an owner path/phrase; its inspection does **not** establish planned product/technical dispositions, reasoned no-ops, related-doc impact or section-level dependency closure. The close guard adds important checks but cannot reconstruct missing design intent after the fact.

**Consequence:** an agent can implement the code *correctly relative to a packet* while the packet itself never ordered the necessary spec changes or dependent-doc review.

### Failure 2: most crosslinks are navigational, not typed impact edges

A simple case-insensitive Markdown-link scan over the 70 non-README docs/product/** and docs/technical/** files counted 260 **link occurrences to other docs/product or docs/technical pages**: 168 on lines 1–20 and 92 thereafter. **35/70 pages have zero such links after line 20**, **27/70 have two or fewer total**, **5/70 have none anywhere**. These are counts of link occurrences, not independent edges or correctness judgments; headings, inline links and repeated references are not distinguished here. Relative links were path-normalized; local fragment-only links, external URLs and docs hubs were excluded.

Examples worth investigating first, not labeling automatically defective:
- [Gameplay acceptance scenarios](../../../../docs/product/gameplay/acceptance-scenarios.md) is 235 lines and has no cross-document Markdown link.
- [Retention and access](../../../../docs/technical/observability/retention-and-access.md) is 169 lines with two early crosslinks and none after line 20.
- [Telemetry and diagnostics](../../../../docs/technical/observability/telemetry-and-diagnostics.md) is 150 lines with one early crosslink and none after line 20.
- [Engine selected architecture](../../../../docs/technical/engine/selected-architecture.md) has multiple introductory routes but only one later cross-document link.

Some pages *do* use useful in-context linking (notably platform topology, time and autonomy and storyteller controller). This is not an all-pages failure. A missing hyperlink is not necessarily a missing conceptual dependency; conversely, a hyperlink is not proof that its author understood the dependency.

### Failure 3: existing graph health measures the wrong property for change safety

The [wiki model](../../../../scripts/repo-tools/wiki-core/model.mjs) and [retrieval benchmark](../../../../scripts/repo-tools/wiki-core/bench.mjs) measure navigation, reachability, search ranking and answer-owner retrieval. Those cannot answer: “If the identity/permission rule in heading A changes, which other selected headings must be reviewed before this Change is complete?” A generic link graph treats “see also,” evidence citation and controlling invariant as indistinguishable unless typed semantics are added.

### Failure 4: freshness checks cannot discover unexpressed dependencies

[HK07](../../../changes/open/2026-11-17--hk07-dependency-aware-freshness/CHANGE.md) plans reverse impact from explicit path references and Git revisions. This is valuable but a source reference is not the same as an inter-contract dependency. If A depends on a claim in B without a usable link/edge, no graph traversal finds A. An empty impact result must mean **no known route**, not “no risk.”

### Failure 5: validation coverage has a known near-term trigger hole

The existing [documentation workflow](../../../../.github/workflows/docs.yml) matches docs/**, agents and README changes but does not generally match a Change-only work/** edit. HK02 correctly owns this repair; this design must not duplicate its CI scope work.

### Concrete possible drift: contradictory implementation status in adjacent technical contracts

At the **same exported revision**, [authority and transitions](../../../../docs/technical/engine/authority-and-transitions.md) opens by describing the deliberate-time “execution-permission and short-action correction” as **prepared but not implemented**. Its linked [chronology and activities](../../../../docs/technical/engine/chronology-and-activities.md) opens by describing the execution gate and finite-action boundary as **implemented with deterministic offline evidence**. Both govern the same time/permission neighborhood and both are presented as maintained implementation contracts. This is a **confirmed prose-level status disagreement** and a **source-reconciliation candidate**, not yet proof which assertion is true for every sub-slice. Do not settle it by picking the newest-sounding paragraph. Inspect actual source, accepted Change receipts and targeted tests, then correct the stale status with exact proof. The existing basic wiki path/anchor graph can be green while this disagreement remains.

### Authority classification trap: Admin is not a selected grant catalog

[Admin authority and governance](../../../../docs/product/admin/authority-and-governance.md) explicitly says its operating policy and illustrative permission packages are **proposed, pending owner review**. A dependency graph must not encode that proposal as a ratified rule merely because it appears under docs/product. Typed binding edges to such an owner should be refused or clearly conditional pending selection. The first relation seed should therefore use *selected* product/technical pairs (time and visual semantics); Admin is an excellent negative test and later ratification-gated coverage candidate.

## C. Diagnosis

The current ecosystem has **authority hierarchy**, **navigation** and **close-time reconciliation**; what is missing is a reliable, *design-time map of intended changes* plus a semantic, heading-scoped relationship model that supports impact review. Link quantity is not the objective. **Correct dependent-claim recall with accept/reject reasoning** is.

## D. Limitations and evidence discipline

- A lean snapshot does not certify full main, archived Changed packets, CI triggers actually exercised or current worktree state.
- The counts are quick Markdown-link diagnostics, not parsed AST counts, and “first 20 lines” is an approximation for introductory navigation.
- No static link count proves contradictions, real author intent, symbol ownership or completeness of semantic crossreferences.
- No live coding-agent study, model-cost measurement or mutation benchmark was performed in this audit.
- Proposal/selected and desired/implemented distinctions remain independent; documentation accuracy requires a grounded read and authority review, not code-driven ratification.

# Product documentation renewal | target and dispositions

## 1. Target and decisions

**The product bible describes the game we intend to build, not the game we have delivered.** The owner regards most current gameplay, Storyteller, UI and admin implementations as exploratory AI-generated POCs. Real infrastructure engineering and the developing Agent Core foundation do not confer maturity on the product. Do not discard the creative vision, successful experiments, or accepted safety constraints. A future engineering design may retain, replace or reject prototype internals. Existing public behavior and data still need explicit migration/compatibility decisions if changed later; this editorial renewal authorizes none.

E1 is evolutionary information architecture, not a new game design. Retain the five domain directories and stable file paths. Reject a clean-slate wiki rewrite (loses claim lineage and disrupts agents) and reject the previous label-only approach (contradictory prose survives). Keep accepted product meaning, rewrite mixed sections into coherent product-facing descriptions, remove implementation walkthroughs from the normative product path only after their unique facts have an owner. Preserve creative scenarios as acceptance or research, not proofs. No arbitrary word-count target or new metadata schema. Do not downgrade accepted rules just because their implementation is poor.

| Kind of content | Destination / writing rule |
| --- | --- |
| Accepted product behavior, rights, constraints | Existing product page and heading. Present tense is fine when clearly describing the intended game; distinguish conditional/optional policy and unselected options locally. |
| Proposed mechanics, policy or feature | Existing explicitly qualified section or linked deferred Design. Preserve alternatives and reactivation conditions; no silent ratification. |
| Authored acceptance story or benchmark | Existing scenario page. State oracle, expected success and forbidden outcome, not an execution receipt. |
| Specific existing code, fixture, route, timer, measured limit | Technical realization owner or nearest source README with dated source/proof; STATUS for capability-level facts. Keep only the player consequence and an exact link in product. |
| Historical implementation sequence or superseded proposal | Existing immutable history or research. Preserve unique findings in surviving owner first; no new archive copy for ordinary prose. |

A capability is **not established** unless current scoped evidence demonstrates it. In E1 the default for legacy application source is **legacy exploratory POC**, not production-ready. Use **not implemented** only for verified absence, **not demonstrated** for unknown or insufficient proof. Narrow fixture successes remain narrow. Do not add this sentence to every section; rewrite actual misleading claims instead.

## 2. Intended reading architecture

`docs/product/README.md` answers what the game is, how to navigate by player question, what the first solo target is and where actual maturity is recorded. Foundations define vision/vocabulary; gameplay owns rules and world consequences; experience owns what a player sees and can do; Storyteller owns creative policy and memory behavior; admin owns staff product intent and permission restrictions. Technical pages own exact implementation contracts and realized mechanisms. STATUS owns dated demonstrated capability, not another product specification. Keep existing heading anchors unless a necessary semantic move has an inbound-link map. A new reader should never need the original Change history to understand a product rule.

## 4. Target editorial architecture

Retain the existing directory taxonomy and stable page paths for E1. A coherent page may contain multiple sections, but do not keep implementation diaries in a normative route. The reader enters via a question, reaches the governing player-facing requirement and its exceptions, then follows a precise technical link only for realization. Rewrite headings and paragraphs together when necessary; a banner above contradictory prose is a failure.

| Reading surface | Desired structure | Concrete end state |
| --- | --- | --- |
| Product index | identity, first playable target, question routes, later ambitions, link to demonstrated state | A reader can describe the first solo experience without opening a technical or historical document. |
| Foundations | vision, concepts, target and explicit non-goals | No current application package, table or controller presented as a condition of the game. |
| Gameplay | rules and refusals organized by player/world consequence | Exact accepted rules and exceptions survive; implementation-only identifiers and fixture numbers leave the normative route. |
| Experience | journeys, controls, feedback, accessibility, authored examples | Keep Living Book as explicitly scoped POC reference, not the approved final UI. No new art direction or interaction framework selected. |
| Storyteller | creative quality, memory and controls, limits of invention/authority | Distinguish desired quality and consent from the capabilities of the offline narrator or current editor. |
| Staff | personas, legitimate workflows, sensitive operations and prohibitions | Staff actions remain intended/proposed as applicable; no existing route is taken to grant permission. |

The first playable target in `foundations/vision.md#first-playable-target` already selects prepared Play and a freeform Story Prompt, no mandatory preview approval, no fictional time from latency, and solo first proof. Preserve all four. Do not add a character creation wizard, choose a new MVP or approve shared play in this editorial evolution. For a target with an uncertain status, recover the actual owner decision; if absent keep it proposed, not a newly accepted or rejected rule.

**Meaning-preserving edit rule.** Classify at claim/section level, not whole-file level. Keep normative intent together with its exception and failure case; extract unique realization facts to the technical destination; replace duplicates by meaningful links; remove obsolete narrative after preserving unique evidence and its immutable provenance. An open policy choice remains visible at its present owner or existing deferred Design. Where a source contradicts a selected product rule, keep the rule and record the mismatch; do not change the game to match the POC. For long pages prefer an exact question-to-heading route. Do not invent a mandatory template, duplicate permanent register, or target word quota.

## Baseline isolation

PostgreSQL defaults grant PUBLIC CONNECT and TEMPORARY on newly created databases. Revoking CONNECT from a named role does not cancel PUBLIC permission; NOINHERIT does not exclude PUBLIC. Database/schema/role membership are distinct. A tenant must have access only to authorized databases, including no unexpected access to maintenance/template databases. Scope negative tests to connectable databases and explicit internal roles; do not claim catalog names are hidden or that tenants form hostile multi-user compute isolation.

Fresh cluster: native postInitSQL and postInitApplicationSQL are candidates to establish explicit baseline ACL on known postgres and bootstrap application DB, plus assess template1. Do not edit template0. Verify exact CNPG v1.30.2 bootstrap order and internal monitoring/replication/maintenance requirements with disposable test before adopting; do not blindly copy newer CNPG default isolation. Owner and required internal roles retain access. Existing cluster: explicit separately authorized inventory and narrow transaction for known baseline ACLs; no loop revoking on every catalog DB, no tenant ensure repair of unrelated access, no revoke of legitimate owner/internal access. Unknown accessible DB or missing expected privilege refuses. Ordinary platform ensure observes/refuses; new tenant provisioning requires established baseline and validates isolation. Verify template ACL behavior; database-level ACLs are not a substitute for hardening every newly provisioned DB.

## Proposed fresh provisioning sequence

1. Environment owner supplies exact context, namespace, cluster UID, consumer/tenant identity and policy; verify cluster readiness and baseline ACL before writes. Serialize conflicting provisioning by target/identity; coordinate baseline changes separately. Check native resources, Secret identity and SQL catalog for collisions; read failure is not absence. No foreign adoption.
2. Create source basic-auth Secrets with cryptographic random credentials, label for CNPG password reconciliation, create-only, never log or place passwords in argv/tracked manifests. Source remains authoritative; existing Secrets never regenerated merely because projection missing. Destination credentials projected only by authorized consumer. Check UID/ownership and resourceVersion; no broad secret listing in receipts.
3. Create scoped DatabaseRole CRs initially NOLOGIN; wait applied/current generation and semantic attributes, password Secret revision where relevant. Create Database CR(s) with allowConnections false, intended owner, retain. Wait for current applied and verify catalog identity/owner/closed state. Do not apply initial closed declarations to existing open stores.
4. From an authorized administrative connection to a separate known database, atomically revoke PUBLIC CONNECT/TEMPORARY on only the new DB(s), grant intended CONNECT and any explicitly required TEMPORARY (not default to all). Verify effective ACL including role membership. DB remains closed during ACL step. Native CNPG owns allowConnections and login transitions; don't fight reconciliation with imperative SQL for these attributes.
5. Open new DB(s) through CNPG only after ACL verification; wait observed generation and catalog. Roles still NOLOGIN. Administrative schema access checks via trusted scoped path. For application DB enable migration role, prove actual credential works, set appropriate public schema and default grants before running application migration with existing advisory lock/history validation; then verify object ownership and runtime grants. Runtime role still NOLOGIN until schema/gate policy complete. Temporal verifies empty owner-writable public schema, enables owner/login, authenticates both stores; vendor schema hooks run later. A closed DB cannot be connected to even by superuser; execute database ACLs from another database, not from target before opening.
6. For application DB: runtime DML grants on application tables, sequence access only as needed, schema USAGE no CREATE, no owner/membership privilege. Set future grants for actual creating migration role and correct schema; PostgreSQL default privileges are not retroactive or inherited from other roles. Keep migration journal and schema readiness gate outside writable application grants; reconcile gate exemptions atomically, inspect exact journal schema and grant scope before specimen. Existing broad grant on all public tables followed by later gate revoke creates a potential exposure interval on retained runtime login; do not assume safe on warm migration. Do not grant function EXECUTE beyond explicit application needs; PUBLIC function defaults and security definer/search_path need separate audit. Avoid broad changes to existing application permissions without evidence.
7. Verify effective positive/negative privileges and actual authentication with source credential, current role generation and Secret revision. Enable runtime login only after fresh gate; project runtime credential to owned destination, never project migration credential into normal workloads. Confirm projected version and actual app identity. Migration actor receives migration credential only when required. No fallback to owner URI.
8. Return bounded redacted readiness result distinguishing created/reused/partial/refused, database/role identity, no credentials. Failed provisioning retains owned state, no automatic drop, rotate or force repair. Explicit diagnostic/resume path only after proving exact ownership and phase; do not auto-adopt arbitrary partial state. Existing dev resume semantics and Temporal strict fresh refusal need detailed reconciliation.

## Reuse and migration

Existing healthy tenant: observe intended resource spec/status, catalog, ACL, membership, credential revision and actual login; reuse without writes if compatible. Do not reapply NOLOGIN/closed manifests; never lock out running workloads on ordinary ensure. App schema advancement is explicitly authorized migration lifecycle, not generic PG ensure. Existing runtime login during warm migration requires privilege-safe transaction boundaries and protection of migration metadata; prove old/new application compatibility separately. Keep dev schema gate name until consumer audit. Parking preserves source Secret, DB/role identities and schema state.

Release target: one application database and separated roles using common policy; existing lab DB and bootstrap owner remain until explicit reviewed transition. Candidate retain lab as migration owner and create scoped runtime role, change migration and runtime Secret references independently; avoids owner transfer and data rewrite. Need inspect ownership, generated Secret controller, existing schema grants, application deployment and migration-job fingerprint/credential contracts. No forced role recreation or automatic credential rotation. Cutover requires explicit quiescence or compatibility plan, read-only inventory, positive migration proof and denial proof; preserve previous credential references for controlled recovery without leaking owner credential back into ordinary runtime. Exact migration plan deferred to gap review, not an implementation commission.

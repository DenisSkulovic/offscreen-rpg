# Technical documentation renewal | target and dispositions

## 1. Target and selected information architecture candidate

The repository must tell an engineer what is **actually built well enough to depend upon**, what is a selected correctness contract, what is experimental source, and what is not yet established. Local infrastructure/developer tooling is the genuine engineering foundation; Agent Core is the next foundation under construction. The application layer is legacy exploratory POC unless a narrower independently evidenced reusable mechanism qualifies. This is an owner-directed maturity baseline, not a finding that every function is defective. Current code may still carry durable data, protected credentials or active callers; preserve safety, compatibility and evidence. No code deletion or dependency inversion is authorized by this design.

Choose evolutionary restructuring with existing domain directories and file paths; reject a universal schema/banner campaign and a whole-wiki clean-slate rewrite. Normalize each affected owner to a coherent current contract, followed where needed by a compact explicitly dated realization/legacy section. Historical amendment stacks do not belong in the execution path. Keep stable anchors or redirects, typed contract dependency edges, exact negative behavior and proof boundaries. Link immutable revisions rather than copying earlier proposals; preserve unique findings in their durable owners. Do not silently de-ratify an accepted contract just because its implementation is POC. If a contradiction requires a new architecture choice, retain the accepted constraints, explicitly identify conflict, and leave the decision to the relevant future Design.

| Content | Sole home | Rule |
| --- | --- | --- |
| Selected correctness, authority, identity, lifecycle, failure, transaction, cost, privacy | Existing technical owner | Exact conditions, ordering and negatives; realization not implied. |
| Actual source route and implementation limitation | Nearest code README or technical realization subsection | Current full revision/date, package/path/symbol, caller, bounded proof and gap. No invented symbol. |
| Current capability maturity | STATUS current section | Distinguish local platform, foundation, POC, absent/not demonstrated. Historical entries stay dated, not current reports. |
| Run result | Existing evidence owner | Exact environment, revision and scope; NOT RUN is not PASS. |
| Operator command | Existing runbook | Current actual command, scope and safeguards; no stale Compose or uncommissioned instructions. |
| Proposed architecture or alternatives | Existing Design/research | No command permission or successor assumed. |

Keep `docs/technical` as contracts, `docs/architecture` as explanatory diagrams (explicit target vs source), `packages/*/README.md`/app maps as retrieval routes. No new permanent maturity registry. Reusable primitive maturity is independent of RPG consumer quality: PostgreSQL runtime is not story persistence; immutable document store is not verified recall; Redis caching is not consistency authority; identity primitives are not complete authorization; reservation/settlement components are not full commercial operation.

See [evidence and specimens](EVIDENCE.md) for inspected source, ownership fences and concrete restructuring examples.

## 3. Target structure and authority resolution

| Surface | Target state | Not permitted |
| --- | --- | --- |
| Technical index | route by engineering question, then distinguish selected and realized | Calling an entire subsystem implemented or replacing contracts with a status report |
| Platform owners | current operational contract with environment-specific proof, next qualification and refusal | Downgrading native foundations because game integration is immature; elevating cold/release/hosted proof from dev evidence |
| Domain owners | selected obligations first, legacy realization separately, actual source entrypoints and remaining gaps | Treating old packet algorithms, package extraction plans or existing DTOs as the future architecture without evidence of selection |
| Source README | package responsibility, actual symbols and callers, negative case, precise contract/test route | Stale Application route, invented Agent Core symbol, full duplicate contract |
| Architecture Atlas | current deployed topology separated visually and textually from application target and hypotheses | One diagram that implies all target services are operating now |
| STATUS | concise current capability and qualification summary, linked dated history | Accumulated completion notices masquerading as current certification |

**Contract authority decision.** Keep explicit accepted guarantees even where their current realization is disposable. Treat implementation choices as legacy realization unless a controlling canonical owner or ratified design establishes a continuing obligation. An undocumented choice does not become ratified by passing a test. Conversely, a format/version, dependency or endpoint may be a current compatibility obligation even if it is not desired future architecture. Preserve that obligation until an authorized cutover; this Design does not choose a new runtime or declare data disposable. Contradictory or untraceable consequential claims must be surfaced at the relevant owner, with existing restrictions retained; no silent weakening or promotion. Remove only redundant, superseded or misplaced text after unique constraints, findings, scope and provenance survive.

**Status treatment.** Replace the current front door with a compact current view by capability: deployed/operated infrastructure (named environment and limitations), Agent Core foundation (exact selected evolution, source and acceptance), independently evidenced primitives, legacy RPG POCs, absent or not demonstrated product. Preserve dated receipts without making them required reads. Where long STATUS history is moved, use existing evidence/session/history destinations and immutable source references; unique unresolved findings remain discoverable in durable domain owners. No new status taxonomy file or maturity score. Do not rewrite existing proof receipts to improve appearance.

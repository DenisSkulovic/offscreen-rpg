## C06-A | One host owns receipt; separate declaration and publication
Use one bounded host supervisor for each proof run, implemented in Node with existing subprocess primitives; no service, shared volume or new dependency. Existing faults/run.sh apply_client/wait_succeeded/log loop and worker_loss.py are replacement seams. All proof Pods restartPolicy Never, no service account token; run-scoped immutable ConfigMap supplies fixture code, credentials mapped from native Secret. Each Pod has exactly one role and run nonce, exact expected UID captured from create response; logs bounded, structured, matched to that UID and container. No fixed-name predelete or apply. Receipt is test-artifact custody, NOT installer state. One private directory under .offscreen/verification/rabbitmq-<random nonce>, mode 0700, exclusive creation; receipt mode 0600, no credentials. Host only writes receipt via temporary exclusive file in same directory, fsync file, rename, fsync directory, read back and validate before next phase. On any write/fsync/readback error stop. Persist schema, run ID, profile/context, R8 baseline/namespace/CR/Service/Secret/PVC/PV identities, vhost '/', proof mode, known fixture resource UIDs, queue name or null, phase and outcome. Do not store raw secret or peer text. Retain receipt on success and failure; never auto-resume a failed run.
 
Sequence (durability and consumer-loss each independently):
1. Capture identities, verify dedicated canonical dev and explicit disruption grant for durability; create initial receipt before any fixture creation. All commands bounded, target rechecked before each mutation. Record create-intent role/name before each create, record exact returned UID before using resource. Lost create response => possible object, retain name but never claim UID or delete by name.
2. Create declare-only Pod. It connects, declares one server-named classic durable nonexclusive non-auto-delete queue and validates declare-ok empty counts/name, emits exactly one structured DECLARED record with run nonce and exact name, then gracefully closes and exits zero. It contains no publish path in declare mode. Host checks same Pod UID before/after log retrieval, successful termination, exactly one matching record, validates queue name UTF-8 length 1..255 bytes and no controls, records exact bytes losslessly as JSON string. No guessed prefix ownership. Only then persist queue identity with phase QUEUE_RECORDED and perform fsync/readback. No publisher Pod created before this gate. If declaration response or record lost, report possible empty orphan, no publish, no sweep. If known record but persistence fails, report known name only if available, no publish or cleanup relying on unpersisted receipt.
3. Revalidate target and read receipt; persist PUBLISH_INTENT before creating a separate publish-only Pod whose argv JSON array carries exact recorded queue name and run ID, no shell interpolation. It never declares a queue; mandatory publish to default exchange using exact supplied name, exact confirm per R9, one persistent payload, close then exit zero. Host verifies UID, successful termination and one matching PUBLISHED record; persist confirmed outcome. If any ambiguous create/publish/confirm/exit/receipt failure, stop; no retry, no further proof, retain queue and known identity (may contain message). Distinguish confirmed publication from unknown; do not infer absence from missing logs. Crash of host after publication still leaves prepublication queue identity and intent on disk. Host failure before queue receipt may leave only empty orphan, because no publisher exists. No cleanup by name without recorded identity.
4. Proceed with R9 repeat ensure/restart or hold/replacement flow only after confirmed publish receipt. On restart, same identities except broker Pod UID; on consumer-loss broker Pod UID and container restartCount unchanged throughout. Queue cleanup only after success-path drain/get-empty, exact receipt identity revalidation and conditional delete if-unused/if-empty with confirmed delete-ok. Any ambiguous delete or failed proof retains receipt and queue status for manual recovery, no retry or purge. Fixture object cleanup best effort only for recorded UIDs on unchanged target using API DeleteOptions.preconditions.uid; never delete uncertain create by name. ConfigMap cleanup after all known Pods terminated; if uncertain Pod creation/termination retain ConfigMap. No automatic recovery of leftover queues/Pods. Ordinary smoke uses exclusive connection-owned queue and no durable receipt gate, but same host identity/fixture custody and bounded cleanup.
 
## C06-B | What the worker-loss proof establishes
Hold-only Pod receives exact nonce via basic.get no-ack=false, redelivered=0, writes APPLY once, then maintains live AMQP socket and heartbeat, never ACKs. Emit structured HOLD_LIVE sequence every 2s only after servicing socket without detected error; on EOF, heartbeat deadline, server close, local hold deadline or other failure emit HOLD_FAILED reason code and exit nonzero. Host polls exact UID/Pod status and bounded logs; require APPLY and fresh increasing live sequence (last observed within 5s host monotonic; do not compare clocks across processes), Running container, restartCount 0, no deletionTimestamp, no failure record. Require two successive live observations with increasing sequence before deletion; immediately recheck identity and status, then issue UID-conditioned normal delete, grace <=5s (no force), await old UID absent, never delete replacement. If any independently observed pre-delete failure, terminal status, missed liveness window, deadline expiry or ambiguity in deletion response, FAIL/INCONCLUSIVE; no replacement proof credited. If post-delete failure record reveals independent socket/heartbeat failure with timing not attributable to termination, mark inconclusive rather than guess; expected signal termination itself is not a protocol failure. Preserve available logs before delete; missing post-delete logs not interpreted as proof of uninterrupted health. Replacement starts only after old UID confirmed absent and target/broker unchanged. Require exact payload, redelivered=1, second APPLY, ACK, get-empty; existing assert_exactly_once.py sees precisely two APPLY records and exits 1 with expected duplicate assertion. Complete success wording: 'Observed unacknowledged redelivery after an owned worker-termination exercise, with no independently observed pre-delete hold failure.' NOT 'termination uniquely caused redelivery'; a connection can fail in the observation/delete interval, and cross-system atomic observation is not possible. No claim exactly-once side effects or HA. Explicit failure observation always defeats PASS even when redelivery later succeeds.

## Deterministic negative traces (implementation obligations, not executed)
- Declare-only mode cannot call publish; missing/malformed/duplicate DECLARED or wrong UID/nonzero exit => no publisher create.
- Receipt write, fsync, rename, directory fsync or readback failure => no publisher create; host killed before receipt => no publisher exists; simulate host crash after queue receipt and after publisher launch => exact identity and publish intent survive.
- Publisher receives exact JSON argument, never declares; unknown create, confirm, exit or result persistence => stop no retry, queue retained; publisher crash after confirmed wire publish but before log => ambiguous, known queue.
- Wrong context/baseline/namespace/CR/Service/Secret/PVC/PV/vhost identity => no subsequent write/cleanup; uncertain Pod UID => no name-only delete; uncertain Pod termination => retain fixture ConfigMap; queue delete if-unused/if-empty failure => retain.

- Scheduling timeout, observation timeout, deletion timeout, replacement timeout, cleanup exhaustion and insufficient repeat-ensure budget all bounded; no new commands beyond budget, no success on partial result.

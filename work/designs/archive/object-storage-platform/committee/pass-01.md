## Material findings

**OS-C01 (high): identity metadata is not authorization proof.** R7 decision 3 requires exact policy readback but never selects the authoritative policy document read path or the binding between Secret access key and named principal. Baseline tools/dev-environments/src/adapters/dev-s3-tenant-live-adapter.mjs parseWeedUserList returns names only; its fixture contains status, policy names and key counts, not policy contents or key identity. recoverUser uses broad IAM export, explicitly disallowed in ordinary target operation. A policy with the expected name but wildcard resource, or Secret containing a different valid principal's key, can pass name/count/HeadBucket checks. R4 two-tenant denial is good evidence for those identities, not proof of future/reused tuples. Closure: establish a feasible tag-specific authoritative read path (redacted specimen or actual source), freeze exact effective-policy and credential identity verification or explicitly narrow reuse assurance with an equivalent safe admission test; cover same-name overbroad policy and wrong valid key negative cases. No need for hosted IAM research.

**OS-C02 (high): legacy compatibility lacks a frozen data-path identity predicate and demonstrated acceptance of the occupied baselines.** R5/R6 require matching resource names/labels, image, selector, bound PVC and ready endpoint; baseline infra/platform/object-storage/dev-bootstrap.mjs assessObjectStoreProbe checks name/owner and selected fields, not actual mount or PV identity. A matching Deployment and Bound PVC can coexist with a different mounted volume or data directory, or a replacement PVC. R3 records two PVC UIDs but no complete classifier inputs. Counterexample: correct service points at correct ready pod using emptyDir or another claim at /data; structural readiness passes listed checks while existing data is absent. Closure: freeze actual pod/deployment volume, mount, provider args, admin Secret refs, storage class/access mode and PVC/PV binding checks, and define what prior UID evidence is required versus unknown. Provide redacted read-only observations of both occupied profiles sufficient to establish compatibility or state explicit owner-accepted refusal; fixtures should reject wrong mount and recreated/unknown identity where continuity is claimed. Do not require migration or live write tests.

**OS-C03 (medium/high): namespace custody at mutation and cleanup is not fully specified.** R7 proof records namespace UID and nonce and checks at cleanup, but does not explicitly require the Redis R9 internal target custody checks before every mutation or an atomic UID precondition on namespace deletion. A GET then delete by name is not a UID-fenced deletion. Fixed per-context flock only serializes cooperating object-storage writers, not cluster recreation or other lifecycle owners. Closure: state how cluster/namespace identity is validated for every guarded mutation, how proof target is closed to callers, and which actual API deletion mechanism carries UID precondition (or retain proof namespace for explicit cleanup rather than claiming atomic protection). Include target replacement negative fixture. Do not require protection against hostile arbitrary kubectl; this is ordinary accidental lifecycle collision.

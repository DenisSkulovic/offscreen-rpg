## Designer defense

- No-change alternative: current provider data path works (12/12 R4) but application startup creates buckets and workload/credential/config ownership is provider-coupled; preserving current implementation entirely fails actual owner objective. Defended.
- Simpler alternative: keep raw kubectl apply and JSON render. It avoids adoption risk but retains custom installation ownership; native fresh-only Helm plus observation-only legacy provides standard release inventory and ordinary YAML without rewriting persisted state. Exact-version Helm behavior and Redis scoped experiments support feasibility; matching metadata adoption is explicitly refused before invocation; residual noncooperating writer risk disclosed. Defended for trusted local scope.
- Vendor neutrality counterexample: cloud S3 has no weed shell, no local Service, no static keys. Source binding seam and runtime HeadBucket-only meet this boundary without inventing cloud control plane. Hosted composition not yet implemented. Defended for source seam; hosted runtime evidence-gated.
- Existing data counterexample: eleven dev identities and both PVCs exist, no Helm releases listed. Native adoption or secret replacement would threaten data. Read-only compatible legacy path preserves deployment/identity; fresh native path never adopts. Release credential migration separately gated. Defended for structural scope, migration not defended.
- Concurrency/failure counterexample: parallel slot provisioning and lost kubectl response. Fixed per-context lock and durable uncertainty receipt block retries, retain remote ambiguity for explicit operator review; no general transaction claim. Existing legacy scripts must be retired or fail closed before new guard is sole writer. Prior Redis R9 descriptor experiment establishes local mechanism feasibility, not new implementation proof. Defended conditional on explicit cooperating-writer scope and required host tests.
- Security counterexample: authenticated bucket access can coexist with overbroad policy. Scoped provisioning and exact policy readback plus negative live proof mandatory for native release and dev proof; existing release admin exception remains explicitly labeled. No new admin propagation beyond named legacy compatibility consumers. Defended for fresh structural scope, legacy credential migration evidence-gated.
- Operational economics: no new dependency, no Seaweed operator or distributed topology, existing SDK, one chart, one bounded guard; avoid more provider research absent contradiction. One cohesive structural Change after independent review and owner acceptance, with migration held separately. Defended.
- Proof feasibility: existing pinned image, Helm 3.22.1, Node 24.19.0, existing Kind contexts and SDK verified by owner; same chart and lifecycle used in isolated generated namespace. Fresh native installation, actual scoped release principal, runtime service path and guard code NOT RUN; these are explicit integration-critical implementation gates, not evidence of existing success. No decisive design premise needs another provider experiment before independent review.

Overall self-defense: **DEFENDED for fresh local structural renewal + read-only compatible legacy continuity + source-level provider-neutral binding.** Existing release scoped credential migration, destructive legacy adoption/cutover and external hosted deployment **EVIDENCE-GATED / excluded**.

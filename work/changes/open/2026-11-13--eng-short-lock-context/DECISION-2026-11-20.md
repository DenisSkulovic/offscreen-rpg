## T03 contract | synchronous resolution, no half-admitted operation

Preferred minimal strategy: **read/capture → remote materialize → fenced commit**, without introducing a long-lived saga for a request that has not yet been admitted.

1. **Fast idempotency read:** when a `storyResolution` already exists for the same owner, story, operationId, revision and identical validated submission, preserve the existing replay behavior without re-reading remote objects; mismatched replay conflicts. Do not suppress the existing durable outbox wake.
2. **Read-only SQL snapshot (no `FOR UPDATE`)** collects exact story owner/revision/view state, active passage content hash and interaction, source generation identity/output, selected submitted option, current items, settings revisions, campaign time/authorizations, relevant activity rows, notes/scene scope, world/rule source pins and any mutable context inputs consumed by `loadStorytellerContext`. Capture exact normalized values/source identities in a bounded typed object. End DB transaction **before** DocumentStore I/O. A mutable SQL value that cannot be fenced is a **STOP**, not a guess that checking scene revision alone is sufficient.
3. **Off-lock immutable materialization:** load active passage(s), selected canonical manifest/documents and pinned rule/world sections **only from recorded exact hashes and selections**; validate the same Storyteller/legacy schemas, task limits and snapshot digest. This stage performs no game mutation and **never sends a model request**.
4. **Short authoritative final TX:** `lockOwnedStory`, first handle same-operation replay; re-read all relevant SQL facts/source identities under lock and compare to the frozen capture (including world/actor/offer/settings where applicable). Pin root hash+root revision, active passage ID+content hash, source generation, notes/scope and exact selected doc handle. Then reuse the existing insert task + `storyResolution` + outbox + view-version transition **atomically**. A changed source causes 409 with **zero** new rows/provider work. Never replace the player's choice, silently switch to new root, or auto-retry under a different intention.
5. **Crash/retry:** failure before final commit leaves **no** new operation/generation/outbox. Failure after commit is recovered by unchanged same-ID replay/receipt. Two concurrent identical requests converge on the same row; distinct attempts compete on the original story/version fence. Keep old public API and actor checks. Do not accept optimistic source reads as sufficient without final authoritative lock/re-read. SQL digest must be over a deterministic bounded projector, not arbitrary JSON serialization of mutable rows.

If this synchronous strategy cannot retain exact source/receipt invariants, **do not paste a big in-process fake cache**: report the precise insufficiently versioned SQL fact and choose a narrow durable provisional capture plus outbox using existing `storyteller_context_capture` ownership, with an explicit current-only/replay contract. That is an identified alternative, **not permission** to invent a second Task Queue or billable dispatch.

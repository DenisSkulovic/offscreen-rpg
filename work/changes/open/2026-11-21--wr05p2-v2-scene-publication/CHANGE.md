## Non-obvious correction to WR05S grammar

WR05S added a v2 parser and SQL version 2, but it is currently **not fork-sufficient**:
- `fictionalState.continuityNotes` accepts only `null|[]`, whereas `@offscreen/storyteller/context:continuityNotesSchema` allows up to 20 nonempty `{key,text,sources,revision}` records.
- `passage.decisionPlan`/`waitPlan` are only `null`, though `stories/plans.ts` has admitted versioned plans and active scenes can wait.
- `activeActivities[]` lacks `boundariesSettled` (actual SQL: `game_activity.boundaries_settled`).
- `worldObligations[]` lacks `firedAtGameSecond`; `activeAction` lacks essential `game_action_execution` plan, offer, operation/base revision, offerId/actionKey, targetGameSecond and status revision.
- `offer` wrapper must preserve **both** the campaign-offer object and its associated `game_offer.plans` when relevant; the present v2 `source/meaning/payload` fields are historical metadata, not actual `offerSchema` members.

**Selected minimal repair:** amend the **v2-only** Documents schema before any v2 publication writes. Keep existing v1 parser/hash frozen. Do not import `@offscreen/storyteller` into `@offscreen/documents` (it depends on Contracts, which depends on Documents). Define a compact strict v2 note schema locally matching the proven four fields/limits, with cross-package fixture parity tests in the Story Engine. Broaden only v2 passage plans to nullable bounded `{version:1,body}` historical wrappers; write-side runtime validates `waitPlanSchema`/`decisionPlanSchema` before wrapping. For active work add the omitted semantic fields above and adjust WR05S test fixtures; only v2 changes. **No second selector table, no backfill, no v1 change.**

## Source-grounded pipeline and decided SQL/CAS algorithm

**Read/capture and pre-stage outside the story lock:** reuse WR05P1's `readSceneAfterState`, normalized stable snapshot and pure `projectStorytellerNotes`. Read expected story revision/view/root, source generation, notes, selected relevant campaign/work rows in *one repeatable-read* owner-scoped snapshot. Prechoose passageId, interactionId and offerId, and derive admitted plan/authorization from validated frozen generation content. Existing `storyteller/publication.ts` currently calls `randomUUID()` for offer inside the SQL transaction: move this identity selection into the staged candidate, never reroll. Compute the finite **scene-publication delta** only (item transfers, validated notes patch, selected offer/plans, hold transition, active scene scope, references), not an entire game event simulator. Compute exact post-state from captured base. Stage changed Library/passage as existing code does, then `stageSceneCheckpointObject` under DocumentStore **before** transaction; hash+read-back verify. Unselected CAS objects are inert.

**Under the existing story lock:** recheck owner, base narrative revision/view/root, generation/source/task/capture evidence and relevant activity/obligation/action/settings rows. Apply the original authoritative SQL writes using frozen candidate IDs/typed decisions. **Read post-state through WR05P1 helper in that very transaction**, compare to staged candidate. Match is full semantic state, including notes, offer/hold, active work rows and fictional clock. On mismatch throw and roll back *all* SQL rows (including notices and published status). Only then insert `story_scene_checkpoint` v2 selector using existing `insertStagedSceneCheckpointSelector`. Replay equal operation/hash returns existing selector; conflicting payload fails. No network/CAS/provider under owner lock.

**Paths to unify:** `stories/continuation.ts:stageSupportedContinuationCheckpoint` currently drops active work/decision/wait and `commitStoryContinuation` inserts checkpoint **before** `publishStorytellerNotes`. Fix exact order. `storyteller/publication.ts:publishStorytellerResult` consequence branch (~810+) currently creates and stores offers, notes and holds with no checkpoint; it must use the same staging/commit reconciliation. `stories/initialization.ts` provides v1 openings: adopt v2 for newly eligible first scenes without inventing fictional elapsed time. `stories/reads.ts:projectCheckpointCampaign` currently projects all activities/holds/obligations as empty for v1; keep v1 path unchanged, add v2 exact as-of read using checkpoint and captured settings revision, never current live state.

**Refusal:** if a given legacy source/flow cannot represent a full after-state, do not silently write v1 or a partial v2 under the new gameplay contract. Return precise `state_not_representable`/hold for newly required v2 path; retain v1 legacy compatibility only where accepted by current product. Large checkpoint remains 1 MiB bound; 16 KiB per wrapped open-work payload. No child re-designs these limits.

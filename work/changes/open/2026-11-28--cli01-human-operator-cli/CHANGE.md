### Adapter and inventory contract

- Parse root/group help locally (`--help`/`-h`, including valid leaf help); no host probes on help or malformed own arguments. No-args shows help; unknown command/profile/unsupported option or duplicate own option exits 2 with concise usage. Strict finite routes, no arbitrary executable, no `--` escape into another command. For postgres/verify leave detailed validation to existing parser, no new flags. Explicit `--json` only for inventory, platform, release status and delegated commands that already support it. Do not change legacy script defaults. Run delegated foreground children with inherited stdin/stdout/stderr (except captured release status), no detach, propagate exit code and signal failure; preserve Ctrl-C/cleanup. Do not wrap or reformat child JSON streams or credential output. Test with injected runner; importing module never executes commands.
- Inventory for `status`, `cluster list`, `cluster status [env]` and preflight of `cluster start`: use `infra/clusters/kind/manager/config.mjs#readKindProfile` for exact profile cluster/context/topology. Use bounded read-only calls (`manager/host-probe.mjs#runReadOnlyCommand` or equivalent existing bounded runner) to `docker ps -a --filter label=io.x-k8s.kind.cluster=<cluster> --format '{{.Names}}\t{{.State}}\t{{.Label "io.x-k8s.kind.role"}}'` per selected profile, and `kind get clusters` for presence. Expect exact `<cluster>-control-plane` and `<cluster>-worker`, one of each matching role; never infer ownership from arbitrary substring. No Docker inspect env, kubeconfig dumps or raw stderr in new summaries. Failed/malformed inventory, unexpected nodes, name/role mismatch or disagreement with Kind inventory => UNKNOWN/INCOMPLETE, never ABSENT. Kind may omit stopped nodes; a complete Docker stopped pair with Kind omission remains STOPPED, not absent. ABSENT only when both successful inventories report no such cluster/nodes. Both running => RUNNING (container state only); both exited/created => STOPPED; mixed or other state => INCOMPLETE. Distinguish observations from Kubernetes readiness. Print context, node counts and observed state, with native `kubectl --context <context> get nodes` and `pnpm offscreen platform status <env>` next steps. Inventory JSON one `{schemaVersion:1, clusters:[{profile,clusterName,contextName,state,runningNodes,expectedNodes}]}`; counts null when unknown; stable order dev/release; no raw vendor output. Exit 1 on unknown/incomplete, 0 for successfully observed absent/stopped/running.
- `cluster start` dispatches existing `up ... none` only on RUNNING or ABSENT inventory; STOPPED refuses nonzero with exact `docker start <cluster>-control-plane <cluster>-worker` owner-only guidance and `kubectl --context <context> wait --for=condition=Ready nodes --all --timeout=180s`, then retry. INCOMPLETE/UNKNOWN refuses with read-only inspection guidance, no automatic recovery. The CLI never executes Docker start/stop, deletes or repairs nodes, scales platform workloads or modifies kube context. Do not equate Docker running with Kubernetes ready: existing `runInfraUp` remains the final guard. No automatic application/platform service launch in `cluster start`.

**Observed problem:** `packages/application/src/stories/index.ts:createStoryApplication.read` statically imports `chamberAllowsResponse` from `developer-tools/chamber-fixtures`. `developer-tools/chamber.ts:createChamber` imports story factory and already separately overrides `read.canRespond` based on its fixture policy. API creates the ordinary story app for normal controllers, and a distinct Chamber app only when `options.developerTools === true`; Game Authority creates a normal story app with no dev-mode option. This misplaced reverse import prevents the intended authority package boundary.

**Selected fix:** StoryApplicationOptions gains `fixtureSourceCanRespond?: (source: string) => boolean`; `read.canRespond` checks playable real source OR the explicitly supplied predicate, default false for synthetic fixtures; existing other eligibility conditions remain. `createChamber` supplies the Chamber fixture predicate to its private underlying story factory and retains its own read policy; API injects the predicate into ordinary stories **only when the existing developerTools flag is true** (same flag that mounts Chamber controllers); Game Authority, worker, normal tests and production without developerTools retain default deny. Authorization remains owner/scope/interaction/active-resolution checks and not this injected predicate alone. No new HTTP flag, origin sniffing, database migration, provider call or fixture content.

**Acceptance:** no `stories → developer-tools` import; Chamber HTTP fixture response behavior preserved in authorized dev mode; plain story app and GA do not mark synthetic fixture source respondable by default; real playable source unchanged; wrong owner denied; unchanged DB SQL and stable story response semantics.

A hung `docker` command is a separate WSL/daemon failure; do not keep infinite polling.

**Actual S3 owner located:** `infra/kubernetes/lab/object-storage/store.yaml` deploys `chrislusf/seaweedfs:4.54` with `weed mini -dir=/data`; it takes one global `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` from Secret `object-store-s3`. `object-storage/smoke.sh` creates one global key, one `lab-objects` bucket and an AWS CLI client; **no per-bucket IAM is currently provisioned**. Planner selection: retain one shared S3-compatible server only if it can provably issue bucket-scoped credentials at runtime without restarting/disrupting other tenants. If not, planner must select an alternative supported shared-S3 configuration; do not let Cursor improvise a new object store or silently distribute the global admin key.

**Database connections and migration owner:** `packages/db/src/config.ts` defaults `DB_POOL_MAX` to **5**; `packages/db/src/database.ts` constructs a `pg.Pool` with that max; `packages/db/src/migrate.ts` uses a single separate `pg.Client` with database-scoped advisory migration lock. `infra/kubernetes/lab/cnpg/cluster.yaml` currently pins app Postgres `max_connections=20`. A four-slot full graph with three SQL-using services can nominally open up to **4 × 3 × 5 = 60** app pool connections, ignoring migrations/admin/reserves; this is a worst-case pool ceiling, not observed active connections. T03 must specify per-slot `DB_POOL_MAX`, database owner/CONNECT privileges and revised measured server connection budget. Prefer dedicated per-slot DB/login, `REVOKE CONNECT ... FROM PUBLIC`, explicit `CONNECT` grant and private schema permissions; migration may use the slot DB owner but app runtime must never have cross-database administrative privileges. Verify all DB consumers before computing the final budget.

**Authentication isolation:** `apps/api/src/modules/auth/auth.ts` sets Better Auth `baseURL`, exact `trustedOrigins`, and a constant appName, with no configured `advanced.cookiePrefix`. Cookies are keyed by hostname/path rather than port. Therefore four `http://127.0.0.1:<different-port>` sessions can collide by cookie name even with distinct databases/secrets. Better Auth documents `advanced.cookiePrefix`. Selected T04 design: use a deterministic **per-slot cookie prefix** (in addition to per-slot signing secret/session database), keep same loopback host for GitHub OAuth callback port flexibility, and test simultaneous two-slot OAuth initiation/callback/session/logout in one browser profile. Check compatibility with the repo's pinned Better Auth 1.7.5 and any existing cookie readers before marking T04 Ready. Do not mistake distinct ports for cookie isolation.

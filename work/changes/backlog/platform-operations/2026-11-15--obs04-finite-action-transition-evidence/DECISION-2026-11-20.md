# OBS04 | Narrow terminal witness on existing finite-action event

**Date:** 2026-11-20. **Source inspected:** GitHub main at `5e47c294bf01`, exact files/symbols below. **Status:** planning obstacle resolved, code/tests/migration **NOT IMPLEMENTED / NOT RUN**. One bounded optional forensic capability remains; this decision does not select it over TURN02 or the playable-kind release.

## Verdict: real missing datum, overgrown proposed machinery

OBS04 originally asked for a co-committed typed historical before/after transition witness. T01 (Nov 20, receipt `ec73a535`) previously passed **7/7** (5 pure + 2 disposable SQL), but only proved the existing event/receipt writers and uniqueness in those fixtures. The packet then got stuck at T02 "name the missing datum". It has a real answer now:

- `game_action_execution_event` stores event ID, execution ID/revision, story, kind, gameSecond, label, ordinal; **no typed interruption cause or pre-transition source state**.
- `game_action_receipt` on success stores action plan, offer, outcome, roll, effects, declarations and optional generation; **no exact pre- and post-commit campaign clock/holds/item holders**, and **no receipt at all on interruption**, correctly.
- `story_public_event` projects a terminal status and a **sourceId pointing to the execution event ID**. It is player-facing, not a forensic state diff.
- `world_obligation_event` and related domain events already record their individual causes; don't mirror entire world/receipt state into OBS04.

Thus we cannot reconstruct what a specific terminal commit *changed* in the story from immutable rows alone after the current `campaign` / `story_item` records evolve. In particular, interrupt `cause` is a structured reducer output that the existing terminal event does not persist. **These are non-inferable past facts.** OBS04's bounded goal is legitimate.

However, **do not implement** the initial proposed second per-story evidence sequence, a new generic event stream/table, unbounded `changed[]` copy of the whole campaign, provider/OTel/Kafka integration, or universal history reconstruction. Existing `game_action_execution_event.id`, `(execution_id,execution_revision)` uniqueness and ordinal identify the fact; `story_public_event.eventSequence` is a different player-visible projection. An OBS04-only counter has no demonstrated consumer. One nullable versioned witness **on the existing event** is sufficient for this pilot.

## Exact versioned witness (small typed first slice)

One **additive nullable JSONB** `game_action_execution_event.terminal_evidence`, deliberately NULL for old rows and nonterminal events, e.g.:

```text
FiniteActionTerminalEvidenceV1 {
  version: "finite-action-terminal-evidence.v1",
  source: {
    storyId, executionId, executionRevision,
    operationId, offerId, actionKey, baseNarrativeRevision,
    planSha256  // digest of the persisted accepted plan; not the text of a prompt
  },
  outcome: { kind: "settled"|"interrupted", interruptCause?: "controlling-world-obligation"|"required-item-holder-changed" },
  before: { gameSecond, activeActionOperationId, holdKinds, characterSha256, storyFactsSha256 },
  after:  { gameSecond, activeActionOperationId, holdKinds, characterSha256, storyFactsSha256 },
  changedItemHolders: [{ itemKey, beforeHolder, afterHolder }],
  coverage: { type: "terminal-core-only" }
}
```

Treat this as a *proposed field contract*, not a claim of a final implementation schema. During T02, inspect actual `campaign.holds` and item-holder shapes before ratifying `holdKinds` and holder identity, use existing domain parsers and stable bounded JSON hashing. Include only item keys implicated by the accepted finite-action plan (plus explicit changed keys if required by the actual transition), not the entire inventory. Enforce a fixed maximum changed-item count/bytes with deliberate refusal of unsupported larger cases, not silent truncation or entire-state duplication. A digest records state identity, **not** the before/after value; the only captured rich values in v1 are original clock/active-action/hold classes and affected item-holder identities. Do not pretend that large character/facts JSON can be reconstructed from hashes. If a concrete incident requires one exact character/fact field rather than a digest, add that justified, bounded field separately under the same one-event contract.

**Meaning of before/after:** the transaction's *immediate pre-terminal state*, not the original action-admission state, and its fully committed *post-terminal* state. This distinction matters when an item was transferred by another actor between admission and settlement. The accepted plan/operation remains frozen on `game_action_execution`.

**Compatibility:** old terminal events have `terminal_evidence=NULL` and project coverage `not-instrumented`, not all of history. This is neither a player-facing story event change nor a new game authority. Existing event/receipt data remain primary truth; witness is an immutable historical explanation linked to exactly one terminal event.

## Placement matters: the current writer has a real ordering trap

`packages/application/src/campaign/action-executions.ts:settleActionExecution` is called after `lockStoryById` from `createCampaignActionExecutions.advance`, in an existing `database.db.transaction`. It first calls the pure `decideActionExecutionTransition`.

- **Waiting:** returns without terminal event or evidence. Do not allocate anything.
- **Interrupted:** `recordActionExecutionEvent` inserts the source and public event *before* campaign changes, `fireWorldObligations`, or held interruption narration finish. It returns `eventId`, already used by the interrupted-consequence receipt. Capture the typed reducer cause + prestate, then **finalize one event witness after all those same-tx mutations and before return**.
- **Settled:** receipt/effects, execution event/public event, campaign update, report obligations and `applyCampaignFollowUpIntents` occur in sequence. Preserve the returned source event ID; after downstream same-tx writes, read narrow final SQL state/item holders and **finalize the same event witness** before return.
- **Atomic:** a source event inserted before its witness is fine *inside one SQL transaction*, but no successful terminal COMMIT may omit the new witness on instrumented code. If witness creation/validation/UPDATE fails, the entire transaction rolls back including event, public event, receipt, rolls, effects and world changes. The existing accepted running execution remains addressable to retry; no second already-committed reward is allowed.
- **Source ordering:** do not rewrite `recordActionExecutionEvent` for all `started/paused/resumed/pace-changed` events. Extend only terminal cases and keep `story.viewVersion`, public event sequence and execution revision semantics unchanged.

## Minimal implementation and acceptance

1. **T02, frozen scope:** source-backed matrix: after existing terminal commit, which before/after values cannot be recovered from immutable event + receipt + world event? Use one successful item transfer and two interruptions (holder-changed, controlling obligation). Finalize exact bounded JSON object and migration behavior. Do not invent a new sequence/table.
2. **T03, one additive migration and writer:** nullable evidence JSONB on existing execution event; strict pure typed builder/validator; under story lock build pre-state and reducer cause, co-commit source event and post-state evidence in same transaction. Preserve existing event UUID and its public source linkage, receipt/reroll semantics and world effects. SQL-only inside the lock: **no additional DocumentStore/CAS read**. Limit DB reads and JSON bytes; measure overhead against baseline.
3. **T04, provider-free disposable SQL positive/negative:** success, both interrupts, waiting, duplicate worker wake, concurrent same-story settlers, rollback after event insertion and after witness finalization (including downstream obligation/follow-up failure), empty/malformed witness, wrong owner, source mismatch, old row coverage. Assert one source event and witness on terminal **and** one public source-linked event, zero successful receipt on interruption, exactly one original receipt/outcome on success, no ghost witness or double roll.
4. **T05, minimal owner-scoped read-only projection:** if a real consumer is selected, expose a *test-only* trusted-reader projection with `instrumented|not-instrumented`, typed source linkage and changed keys/clock values. Avoid a raw production Admin endpoint or new UI; do not log private source data. This read is forensic, not authoritative input to an action.
5. **T06, final evidence/closure:** actual source SHA, migration up/test downgrade strategy, commands/results, baseline vs E0 added SQL timing/bytes and total serialized witness size, recorded redacted fixture, negative cases and docs. Only then mark Done and archive. Existing T01 7/7 is historical and does not satisfy T03/T04.

**Implementation coupling:** OBS04 shares `action-executions.ts`, world/follow-up writers and source types with ENG03 and possible TURN02/GM07 integration. Serialise production writes with the active Game Authority integrator. No new live cluster tests for a standalone provider-free SQL forensic pilot; actual kind can consume the same code later without declaring it a release prerequisite.

# CL01 | exact device pairing and CLI decision algorithm

## Persisted auth state

Add tables terminal_device_pairing (id UUID PK, code_hash unique SHA256, challenge_sha256 SHA256, source_ip_hash SHA256, client_label up to 64, state pending|approved|consumed|denied, owner user FK nullable, created_at, expires_at, approved_at, consumed_at) and terminal_access_token (id UUID PK, token_hash unique SHA256, user_id FK, scope literal player-story, expires_at, revoked_at). Use new migration after 0023, journal version 7; no unencrypted token/verifier/code stored. Pairing code from secure randomness, ten Crockford characters excluding ambiguous glyphs. CLI verifier=32 random bytes; challenge=SHA256(verifier). Expiry five minutes for pair, seven days for token. Lock pairing row FOR UPDATE during approve/exchange, guaranteeing one consumed exchange. Stored token hash lookup with expiry/revocation/owner verification.

Endpoints under dedicated Nest TerminalAuthController:
POST /api/terminal-auth/pairings unauth, input challengeSha256 and label, response pairingId, code, verificationUri, expiry, pollAfterSeconds=2. Rate limit by querying indexed pairing rows on source_ip_hash+created_at: at most five created in ten minutes per HMAC-SHA256(client IP, server-side secret), and three outstanding per challenge; derive client IP from the trusted socket-injected value, not user-supplied forwarded headers. The HMAC key is **the existing BETTER_AUTH_SECRET** from readAuthConfig: add narrow CreateAppOptions.terminalPairingHmacSecret and pass authConfig.secret from apps/api/src/main.ts, not a new global env or a raw auth cookie. In tests this option is explicitly injected; when absent, pairing creation fails closed as unavailable and must never fall back to an unkeyed rate-limit hash. No separate counter/third table or process-local limiter.
POST /api/terminal-auth/pairings/:id/approve browser cookie + Origin, body userCode **typed by user in a consent form, not automatically accepted from a URL**. Check hash/code/expiry/state under SQL transaction; set owner and approved. No bearer approval.
POST /api/terminal-auth/pairings/:id/exchange with base64url verifier. Verify hash constant time, pending returns 202, approved consumes row + inserts seven-day hashed token in one transaction; return raw token only in response once. Consumed returns 409, expired 410, unknown uniformly 404; never return token from a GET, logs or audit body.
GET /api/terminal-auth/tokens/current returns only user id/display name, scope and expiry for a valid bearer, no raw token; DELETE /api/terminal-auth/tokens/current bearer of scope player-story revokes its own token, no userId input. Admin cannot create or enumerate tokens.

StoryPlayerIdentity.requireStoryPlayer(headers): if Authorization is present it must be exactly Bearer token, and Cookie must be absent. Only query terminal_access_token with hashed bearer, unexpired/unrevoked, player-story scope; resolve owner user record. Otherwise delegate unchanged IdentityService.requireUser(browser headers). Do NOT patch global IdentityService; switch only StoriesController.run/runLaunch/storyUpdates and reauthorization callback. No provider/admin/GA/Drafts bearer authorization. Maintain existing global Origin check; terminal client sends exact configured Origin for writes, HTTPS except explicit loopback localhost.

## CLI behavior

tools/terminal Node24 ESM workspace: src/cli.ts, auth-store.ts, http.ts, player.ts, render.ts, pending-intent.ts, with focused tests. No direct packages/db/story-engine dependencies. Configurable base URL, reject non-HTTPS nonloopback, redirects disabled, AbortSignal timeout 10s. login creates verifier in memory, opens verificationUri, polls exchange no more frequently than server interval, atomically stores token with 0600 permissions and symlink/owner/mode validation; logout revokes server before local wipe, offline wipe clearly warns token remains valid. Never print token, headers, secret prompts or verbose HTTP bodies.

Commands: login/logout, stories, launch (stdin or --prompt-file rather than argv for sensitive prompt), launch-status, play, choose, refresh, history, fork, resume, and --json. Render only StorySnapshot public content. Legacy choose uses frozen respondToStorySchema and interactionId/optionId. Campaign offers must browse path until node.action exists, commit with frozen expectedRevision/offerId/path to actions/:uuid. Save frozen pending request and digest BEFORE PUT in owner-only state path under ~/.local/state/offscreen-rpg/<sha256(origin)>; pending intent is keyed to owner/story and no second operation ID on ambiguous reply. Read resolution receipt and snapshot before replay; if mismatched digest, fail closed. Launch recovers existing GET status and never stores raw prompt. Fork same sourceStoryId/sequence stable SHA256 based UUID and forkStorySchema, not an arbitrary new branch identity. Handle held/uncertain/waiting and stale revision as visible explicit states, never auto-send while awaiting ACK. --json exposes validated public DTO with no credentials, private model context or raw HTTP headers. Sanitize ANSI escapes in rendered story text.

No controller data owner checks change, no local authority. Negative acceptance: concurrent exchange exactly one token, wrong owner/token, expired/revoked, token in Admin/Drafts 401, mixed cookie+bearer 401, malicious ANSI text, offline replay one operation ID, no silent retry.

Do not reassign the existing ./schema export (Better Auth expects auth.ts there).

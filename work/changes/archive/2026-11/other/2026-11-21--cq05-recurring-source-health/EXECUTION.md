# CQ05 | decided source-health algorithm and contracts

## Tool contracts

Create `scripts/repo-tools/code-health-core.mjs` (pure functions), `scripts/repo-tools/code-health.mjs` (read-only Git/FS adapter), `scripts/repo-tools/code-health.test.mjs` (isolated synthetic fixtures). Add `pnpm repo:code-health` and `pnpm repo:code-health:test` in root package scripts.

`pnpm repo:code-health` default prints **at most 10 largest source files**, **at most 8 directory hotspots** and next-step instructions. `--json` emits a single stable `offscreen.code-health.v1` object with `head`, `baselineRef`, `baselineAvailable`, `summary`, `files`, `directories`, `findings`, `strictRegressions`. `--base <branch-or-sha>` makes growth numbers available. `--strict-new --base <ref>` compares against that explicit base and exits 1 only for newly crossed severe thresholds; missing baseline or Git error exits 2 (**not a green result**). Default mode never exits nonzero for existing warnings, only for scan/tool failure. No CLI `--write` and no automatic issue generation.

## Discover and measure

1. Obtain tracked plus untracked/non-ignored working files with `git ls-files --cached --others --exclude-standard -z`, deduplicate, require existing files, normalize '/' separator and include only `apps/`, `packages/`, `tools/` source-owned `.ts/.tsx/.mts/.cts` files. Exclude any `dist`, `.next`, generated, `node_modules`, coverage, `test/tests/__tests__/fixtures` components and `.test/.spec/.integration` source suffixes. A deleted tracked file must not be counted.
2. For each remaining source, read bytes and count lines using newline-aware split (no extra phantom trailing line). Parse with `typescript.createSourceFile` using `ScriptKind.TSX` for .tsx and `TS` otherwise. Count function declarations, function expressions and arrow functions (including nested functions), maximum AST function span, syntactic `as` assertions/`!` non-null expressions/`any` keywords, and deepest `if/for/while/switch/try` nesting within a function (ignore expression/AST layout depth). These are indicators, **not proof of misuse**. Expose parse diagnostics as scan findings, not zero.
3. For each immediate owning directory, count **direct** production source files, bytes, total lines and files above thresholds, and count subdirectories holding production source. Report directory pressure based on direct file count, *not* recursively counting all descendants. Paths are deterministic and alphabetically sorted.
4. Default numeric review bands (hardcoded single central config, with clear named threshold version): `file >=700 lines` review; `file >=1,200` high attention; `function >=120 lines` review; `max control-flow nesting >=5` review; `direct files >=35` directory-structure review. These are review signals; safety-critical small files can also be dangerous. Show type assertion/non-null/any counts as **inventory only**, not threshold-based vulnerabilities. Scope to *production* code.
5. With explicit `--base`, list baseline source with `git ls-tree -r --name-only -z <ref>` and retrieve source for **only candidates that already trigger a review warning or were modified**. Use `git show <ref>:<path>` with no shell interpolation; missing baseline file means newly introduced, not a file with zero source lines. Compare threshold-crossing by named file/dir and significant file growth (`>=150 added lines` and `>=30% relative growth` from nonzero old size). Cap history reads and report `baselineAvailable:false` on failure; never treat failure as no regression. No Git ancestry assumption: label `--base` a chosen comparison ref, not always a merge-base.
6. `--strict-new` fails only newly introduced files above >=1,200 lines, newly crossed >=1,200-line boundary, newly crossed 35-direct-files directory boundary, or >=150-line AND >=30%-relative file growth **already resulting in >=700 lines**. Existing severe debt on baseline is **reported but not a hard failure**. Growth can be legitimate: owner reviews and explicitly exempts with rationale in the relevant Change, never by simply removing the threshold.

## Reporting / lifecycle

- Human output reports precise numbers and top candidates, including Storyteller's 63-file flat pressure. No console flooding: if the full JSON is needed, request `--json`.
- The reader in an implementation Change runs the focused changed-file lint as usual; the **parent** runs `repo:code-health --base <integration-branch>` at a coherent checkpoint/closure. An integration custodian interprets structural regressions before joining. A weekly or monthly manual full review is a **cadence**, not a new always-on agent and not a claim of background scheduling.
- Code-health output does not create Change folders. When review confirms actual architectural debt, ChatGPT maps existing owners/contracts, chooses semantic seams, creates the few necessary Change packets, and records review/deferral in existing roadmap/Change receipts. Existing risk controls, typed APIs and tests remain mandatory.
- Never split one transaction or schema identity to satisfy size threshold. Never move Storyteller files merely to decrease direct count; directory restructuring needs independent source/consumer analysis.

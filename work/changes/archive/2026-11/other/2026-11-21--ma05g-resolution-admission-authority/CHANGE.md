**Goal:** One coherent migration of Storyteller resolution **replay, locked commit and task-record creation** to the Story Authority side, while preserving the source's **read-only SQL snapshot → off-lock CAS/document/task preparation → newly locked revalidation and atomic commit** algorithm. Maintain existing `createStoryResolution(database,documentStore?)` and all public Storyteller admission exports. No new package, DB migration, provider call, callback inside a transaction, or gameplay change.

**Why now:** `stories/resolution.ts` imports three runtime entrypoints from `storyteller/admission.ts`. That 640-line runtime module contains a read-only/off-lock preparer **and** an authoritative replay/commit writer. Simply moving the entire file would copy the architectural problem. The separation below moves both SQL writers and the neutral SQL prerequisites, then makes only the existing public Story Resolution factory a small composition façade. Direct ENG03 lock-measurement consumers must continue to work.

## Selected composition decision

1. `stories/storyteller-resolution-authority.ts` owns `replayStorytellerResolutionIfMatching(database,input)`, `commitStorytellerResolution(tx,prepared)`, and private `assertStorytellerResolutionFence`. The commit receives the already prepared and **typed** `StorytellerTask`. It **never** imports `application/src/storyteller/*`.
2. `storyteller/admission.ts` retains `prepareStorytellerResolution`, including its existing SQL read-only capture, CAS/document retrieval, canonical selection, interaction validation and policy/task assembly. It imports the shared fence/prepared shape from `stories/storyteller-resolution-contract.ts` and direct-reexports the relocated commit/replay symbols for old module consumers. Off-lock preparation is **not** moved into provider transport or a post-commit worker.
3. `stories/resolution-core.ts` contains today's `createStoryResolution` logic, renamed `createStoryResolutionCore`, and accepts a **required** dependency `prepareStorytellerResolution` through a small named contract. It imports the new SQL authority module directly. It does not import `storyteller/admission.ts`; its other existing Scripted path imports from `generations` remain intentionally out of scope (MA06 generic persistence cohort).
4. `stories/resolution.ts` is the backwards-compatible thin composition façade, exporting `createStoryResolution(database,documentStore?)` with the same signature. It imports `prepareStorytellerResolution` from `storyteller/admission.ts`, calls `createStoryResolutionCore(database,documentStore,{prepareStorytellerResolution})`, and re-exports any other original public symbols if found on refreshed source. `stories/index.ts` retains importing this façade. This is the deliberate, **sole** outward dependency in the composition boundary and means the core is MA06-extractable.
5. A supporting `stories/storyteller-task-record.ts` owns `insertStorytellerTask(tx, {id,ownerId,task})` with its exact `generation` + `storytellerPublication` + outbox insertion and `selectStorytellerNoticeTopicAtAdmission` selection in that insertion transaction. Runtime `storyteller/records.ts` preserves old direct **identity** exports. Do not move `setPublication`, provider runner or message dispatch in this Change. The topic selector continues to be chosen at admission, **not** at retry/replay.
6. SQL-only `storytellerActivityContextFilter`, related state/type constants and `isStorytellerActivityState` move to `campaign/storyteller-activity-filter.ts`; old `storyteller/activity-context.ts` direct-reexports for runtime consumers. Move `activeSceneAnchorSchema` into `stories/active-scene-anchor.ts` with old context export identity. Move only the `StorytellerResolutionContextSqlCapture`/ `ResolutionPassageSource` **type definitions** to `stories/storyteller-resolution-contract.ts`, re-export from `storyteller/context.ts`, and use type-only imports in the runtime preparer. Avoid duplicate runtime schemas.
7. Shared fence contract contains exactly existing `StorytellerResolutionFence`, `PreparedStorytellerResolution = {fence;task: StorytellerTask}`, SQL snapshot types and a typed preparer function alias `PrepareStorytellerResolution` inferred from existing input shape. Do not widen fields to `any` or `unknown` merely to break an import; preserve the current deliberately unknown JSON fields at the same boundary.

## Non-negotiable behavior

- Owner/revision/submission validated by existing `createStoryResolutionCore.admit`, before branch selection. `replay` still checks `storyResolution` same operation/revision/submission, enqueues exactly the **frozen persisted wake topic** inside its SQL transaction and returns true; changed payload is conflict. No new generation on replay.
- `prepare` still reads an owner-scoped snapshot in a short transaction without story `FOR UPDATE`, verifies current source/output, materializes CAS and canonical context **off-lock**, creates a complete resource-fenced Storyteller task. This stage causes no authoritative story mutation or provider spend.
- `commit` still locks the owner story using `lockOwnedStory`, rechecks prior operation and the entire Storyteller fence (revision/viewVersion/premise/notes/scene root & scope/passages/generation/current interaction/selected campaign settings/commitments), checks same-base resolution, inserts task+publication+notice and resolution and advances view within **one original tx**. A stale document root or story activity state conflicts with zero partial mutations.
- Old and new named functions must be **strict-identical exports**, not wrapper implementations. `createStoryResolution` original positional API remains unchanged. No fake zero-DB confidence or silent omission of direct-factory tests.

# Start a reviewed playable candidate

Status: Implemented, awaiting review

Approval: The owner approved preparing this slice on 2026-09-18 and asked to implement it after the playable-opening-candidate work landed on `main`.

## Intended outcome

A player who has generated a current successful playable opening candidate can explicitly start it as a persistent live story.

The first live passage must be the player-facing presentation of the **exact persisted candidate they reviewed**.

Starting must not regenerate, reinterpret or replace the candidate.

The story retains durable provenance back to the generation that produced the published passage so later resolution can recover the hidden option intentions from the authoritative saved proposal.

This feature ends at a live, reopenable first scene with visible choices.

Selecting one of those choices and generating the continuation is deliberately the following feature.

## Representative flow

1. The player saves a draft.

2. The player generates a playable opening candidate and reviews its scene and choices.

3. The candidate is successful and still current for the exact saved draft revision.

4. The player presses **Start story**.

5. The browser creates or retains a stable story operation/identity for retries and submits:
   - the selected candidate identity;
   - the expected source draft revision.

6. The server verifies under one transactional boundary that:
   - the caller owns the relevant draft/candidate;
   - the generation succeeded;
   - its output validates as the playable opening contract;
   - it is still the current candidate for that exact draft revision;
   - the candidate has not become stale.

7. The server converts the saved proposal through `playablePresentation(...)`.

8. The server atomically creates:
   - the story;
   - passage sequence 1;
   - its visible scene and interaction;
   - durable provenance linking that passage to the candidate generation.

9. The API returns the ordinary saved story snapshot.

10. The browser navigates to the live story view.

11. Reloading or reopening shows exactly the same first passage and choices.

12. Retrying the same Start operation does not create another story or another first passage.

13. If the draft changed before Start committed, Start fails as stale/conflicting and the old candidate is not converted into a live story.

## Scope and boundaries

### Included

- Explicit Start action from a successful current playable opening candidate.
- Ownership and source-revision validation.
- Atomic conversion of the persisted candidate into live story passage 1.
- Durable source-generation provenance on the published passage.
- Idempotent Start retry behavior.
- Reopening the resulting story through the normal story snapshot path.
- Browser transition from candidate review to the live story.
- Integration/browser coverage for success, stale candidate and retry behavior.

### Explicitly deferred

- Resolving any opening option.
- Calling a storyteller for a continuation.
- Pending asynchronous intention resolution.
- Waits generated from model proposals.
- Inventory/effects generated by the storyteller.
- General character/world memory.
- Pace configuration.
- Free-text intentions.
- Multiplayer.
- Notifications.
- Paid inference.
- Story deletion/finish lifecycle expansion.

### Existing invariants to preserve

- The browser cannot supply opening prose, interaction structure, hidden intentions or effects.
- Only validated persisted server-side generation output becomes live content.
- A stale candidate cannot start.
- Start never performs inference.
- Initialization is atomic.
- Duplicate initialization cannot create duplicate passage 1.
- The live passage contains only player-visible interaction data.
- Hidden intentions remain in the saved generation proposal.
- Later draft editing cannot mutate an already started story.
- Chamber fixtures remain valid and need not use generation provenance.

## Provenance decision

Add an optional authoritative generation reference to a published passage.

Conceptually:

`story_passage.source_generation_id -> generation.id`

It is nullable because authored chamber fixtures do not originate from generation.

For a story started from a playable candidate:

- passage 1 stores the candidate generation ID;
- that generation's validated output is the authoritative proposal behind the passage;
- the visible `content` and `interaction` stored on the passage are the result of `playablePresentation(proposal)`.

Do not copy hidden intentions into the browser-visible interaction.

Do not duplicate the complete proposal into the passage JSON merely to make retrieval convenient.

The next continuation feature should be able to load the current passage, follow its generation provenance and recover the exact saved proposal used to publish that offer.

Use a foreign key where compatible with the existing schema and lifecycle.

## Start identity and retry

Use the story ID as the idempotent identity of this Start operation unless the current implementation reveals a concrete need for a separate start receipt.

The first implementation should prefer the smallest correct contract:

- a client-stable story UUID;
- candidate generation ID;
- expected draft revision.

A retry with the same story ID and same accepted candidate must return/reopen the existing story.

Reuse of that story ID with a different candidate or incompatible initialization must conflict.

Do not add a generic command journal or start-operation framework in anticipation of future lifecycle features.

## Concurrency requirement

Candidate-currentness and story initialization must be validated atomically enough that an edit/regeneration racing Start cannot silently produce a story from a candidate that was already stale before the Start commit.

Prefer one database transaction containing the authoritative validation and initialization.

If reuse of existing initialization logic would introduce a check-then-insert race, extract the smallest transaction-capable initialization helper rather than performing validation outside the transaction.

Do not rewrite the general story subsystem.

## Player presentation

A successful current candidate gains a clear **Start story** action.

The action is unavailable when the candidate is:

- pending;
- running;
- failed;
- uncertain;
- stale;
- missing.

While Start is being submitted, prevent duplicate UI submission.

After success navigate to the canonical live story route.

The live first scene should look like an actual story rather than a special creation-preview state.

Do not implement choice resolution in this feature. The choices may be visible but temporarily non-actionable if the general story viewer cannot yet safely distinguish generated unresolved choices from chamber-resolvable choices.

Prefer explicitly disabled/unavailable interaction over routing generated choices into the authored chamber resolver.

## Acceptance

The feature is complete when:

1. A successful current playable candidate can be explicitly started.

2. The resulting live passage content exactly matches `playablePresentation(...)` of the saved candidate output.

3. No generation/model call occurs during Start.

4. Passage 1 retains durable provenance to the candidate generation.

5. Hidden option intentions remain retrievable server-side through that provenance and are not exposed in the snapshot.

6. Reloading the resulting story preserves the same scene, choices and provenance.

7. Retrying the same Start identity with the same candidate is idempotent.

8. Reusing the Start/story identity with incompatible candidate data conflicts.

9. A stale candidate cannot start.

10. A candidate owned by another user cannot be started or disclosed.

11. A racing draft edit/regeneration cannot result in silently starting an already-invalid candidate.

12. Existing chamber initialization still works.

13. Existing story history, timing and item-transfer behavior remains unchanged.

14. Relevant integration and browser checks pass.

15. `docs/progress.md` records that creation now reaches a real live first passage, while option resolution from generated proposals remains unimplemented.

## Decisions still needed

None expected for this slice.

If implementation reveals that candidate provenance cannot safely be represented as a nullable passage generation reference, stop and surface that specific data-ownership problem rather than inventing a broader generation-history framework.

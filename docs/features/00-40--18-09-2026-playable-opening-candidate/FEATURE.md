# Playable opening candidate

Status: Implemented, awaiting review

Approval: On 2026-09-18 the owner authorized selecting and preparing the next focused implementation slice toward the connected playable story lifecycle. This feature is intentionally limited to producing, persisting and reviewing a playable opening candidate. Starting the live story from that candidate is the next slice.

## Intended outcome

A saved story draft can produce a deterministic offline **playable opening candidate** rather than the current prose-only scripted sample.

The candidate contains:

- the opening scene content;
- one visible choice interaction with one or more options;
- the underlying intention associated with each option, retained server-side for later continuation generation.

The player can leave and return while preparation completes, review the resulting scene and choices, and clearly see when the candidate belongs to an older draft revision.

This is the first half of connecting story creation to the actual runtime. The following feature will start a live story from the exact accepted candidate produced here.

No paid model or provider call is involved.

## Representative flow

1. The player creates or edits a story draft and saves a non-empty premise.

2. From the saved draft, the player opens the opening-preview page and requests an opening candidate.

3. The request is admitted against the current draft revision using the existing generation/outbox/Temporal path.

4. The deterministic fixture completes in the background.

5. While work is pending, the player may leave the browser. Returning or reloading retrieves the same saved generation state.

6. When complete, the preview shows:
   - the generated scene;
   - the choice prompt;
   - each visible option label.

7. The full persisted generation output also retains each option's `intention`. Those intentions are not sent to the browser as hidden storyteller metadata.

8. If the draft was edited after this candidate was requested, the candidate remains readable but is visibly marked stale and is not considered current.

9. Retrying the same admitted operation ID remains idempotent. A conflicting reuse of that ID remains rejected according to the existing generation semantics.

10. Failed, uncertain and unfinished generation states remain represented by the existing UI/recovery behavior.

## Scope and boundaries

### Included

- Use the existing offline playable-opening preparation from `@offscreen/ai` as the canonical request boundary.
- Persist a versioned playable-opening generation input and the full validated `PlayableProposal` output.
- Replace the current deterministic prose-only scripted opening fixture with a deterministic playable proposal.
- Preserve the existing draft-to-latest-opening relationship and asynchronous generation lifecycle.
- Present only player-visible scene/interaction data through the HTTP contract.
- Retain option intentions only in the persisted generation output for the next feature.
- Update the opening preview UI to render the scene, prompt and choices.
- Preserve current revision/staleness, retry, pending, failed and uncertain semantics.
- Update tests to prove persistence, reopening, stale-draft behavior and that hidden intentions are not exposed by the preview API.

### Explicitly deferred

- Starting a `story` from the candidate.
- Accepting or selecting the candidate as a separate persisted action.
- Resolving a selected option.
- Live model/provider calls.
- Model budgets or usage accounting.
- General memory/context retrieval.
- Waits, decisions, autonomous defaults or item effects generated by the storyteller.
- Regeneration policy beyond the existing "request another opening" behavior.
- Multiplayer.
- Notification delivery.
- Presentation polish beyond making the candidate understandable.

### Existing invariants to preserve

- Generation identity and ownership remain server-authoritative.
- An admitted generation is tied to the exact saved draft revision it captured.
- Later draft edits do not mutate or invalidate recovery of already admitted work.
- Only the latest linked generation is the draft's current preview.
- The browser never supplies hidden storyteller effects or authoritative application state.
- Generation lifecycle state remains owned by the existing generic generation machinery.
- The deterministic fixture must not become a provider adapter.
- No external/paid call is made.
- The eventual Start feature must be able to use the persisted candidate without reconstructing hidden intentions from visible labels.

## Data and contract decision

A playable opening generation stores the complete validated `PlayableProposal`.

The HTTP preview does **not** expose that raw proposal. It exposes its player-facing presentation:

- `content`
- `interaction`

The interaction contains the visible prompt and option IDs/labels, but not option `intention` values.

Use the existing `playablePresentation(...)` conversion as the semantic boundary between stored storyteller output and browser-visible data.

The persisted generation input must be versioned and validate the value returned by `preparePlayableOpening(...)`, including:

- input version;
- prompt version;
- task = `opening`;
- draft ID and revision;
- immutable request messages/output schema.

Do not reuse the old prose-only `openingOutputSchema` for new playable candidate records.

The old prose-only scripted format does not need to remain the active UI path. Existing local development data may be discarded/recreated rather than adding compatibility machinery for obsolete fixture generations.

## Acceptance

This feature is usable when all of the following are true:

1. A current saved draft with a premise can request a playable opening candidate.

2. The admitted generation input is produced from `preparePlayableOpening(...)` and is validated before persistence.

3. The deterministic fixture settles the generation with a valid `PlayableProposal` containing:
   - scene content;
   - a choice;
   - at least two distinct visible options;
   - distinct retained intentions.

4. The saved HTTP preview presents the resulting scene and choices without exposing the option intentions or the raw provider request.

5. Reloading the preview after completion produces the same saved candidate rather than recreating it.

6. A candidate requested for draft revision N becomes visibly stale after the draft advances to revision N+1.

7. Reusing an admitted request ID with the same identity remains idempotent; incompatible reuse remains a conflict.

8. Pending/background behavior continues to work through the existing outbox/Temporal fixture path.

9. Failed/uncertain states continue to parse and render without inventing a candidate.

10. Integration tests explicitly verify that server-only intentions exist in persisted generation output but are absent from the browser/API preview.

11. Existing unrelated chamber/story tests continue to pass.

12. `docs/progress.md` no longer describes the active opening preview as prose-only once this feature is complete, while still stating that Start is not connected.

# Context, caching, prompts and spending

The cost objective is a coherent story within an explicit allowance. We cannot promise a few cents per unattended week without measuring frequency, context size, output length, repair rates and model prices. Ordinary waiting itself needs no model invocation.

For concrete request packets, current-versus-proposed tools, per-call token envelopes and branch-specific gameplay ledgers, see the [Storyteller walkthrough](playthroughs/storyteller.md). Those offline estimates are not measured usage or permission to enable inference; this document owns the shared accounting/context contract.

[Usage policy](usage-policy.md) owns configurable account/tier entitlements, lower player/story limits, fixed/rolling usage windows, on-demand consent and pause/recovery. Provider capacity is only an upper capability bound: effective application context/output limits can be much lower. The conservative development preset there is stricter than the general offline recipe tuning candidates below.

There is no single globally correct quality/cost point. Use the same gameplay and evidence authorities across a minimal sponsored/free recipe, ordinary subscription recipes and explicitly funded high-context play. Profiles configure models, context, output, exploration, maintenance and frequency independently. A user may prefer a cheap small-context route with terse prose, while another may explicitly fund a frontier route with extremely large context and richer exploration. Both must preserve required truth, committed mechanics and recoverability; only optional breadth, prose richness, exploratory work and latency/cost envelopes differ.

## Build context for a specific decision

Assemble context in a deterministic order and record a compact manifest of source IDs, revisions and prompt versions:

1. Stable application instructions and output/tool contracts.
2. Storytelling preferences, premise and character definitions relevant to this run.
3. Current authoritative situation, possessions/conditions that constrain actions and participant permissions.
4. Recent committed passages and accepted player intentions.
5. Selected older facts, unresolved threads and memories relevant to this development.
6. The specific requested operation and its constraints.

Allocate a token budget to these sections and reserve output capacity. Required current facts and the selected intention take priority over decorative lore. If required context cannot fit, reduce optional material or hold; never silently drop the fact that the wizard lost their wand. A larger route requires a separately admitted policy, not model-driven escalation.

The player and model may see different information. Server-only prepared futures can inform the storyteller without entering browser snapshots, notifications or public traces. Context retrieval must always be story-scoped and respect intended visibility.

The context manifest references one immutable base snapshot and a frozen decision/settings version. Retrieval tools either read facts from that version or detect that it is stale and stop; they must not quietly mix the old situation with a new inventory. Read snapshots in a short transaction, persist the artifact, then release database resources before inference. Input/result artifacts remain available for unfinished and retryable workflows; their cleanup policy is not simply the telemetry retention period.

The [canonical document workspace](canonical-files.md) supplies explicit paths/identities, source links, chronology windows and unresolved threads. Exact, lexical and semantic/hybrid retrieval belong in its POC evaluation, with backend choice separate from content ownership. Compare their contribution on the same return scenes; vectors are candidate discovery, not proof of a fact. No embedding service or paid call is enabled by this design.

## Bounded work, not an open-ended agent

Status: implementation contract for the [bounded-cost feature](../features/2026-09-19--19-08--bounded-storyteller-cost/PLAN.md). Existing code has one-shot dispatch, account/run reservations and uncertainty stops. It does not yet enforce the following task-wide exploration, maintenance and context-recipe policies. Memory exploration must consume these controls rather than add a second budget manager.

The application selects a small versioned **task recipe** using the task purpose and captured state, without a routing-model call. A recipe selects required sections, optional selectors, applicable rule fragments, output schema, tool allowlist and effort envelope. It is not a new Storyteller personality. A model may decline optional exploration, but cannot grant itself tools, extra rounds, a larger model or more funds.

Rule loading follows a deterministic ladder. The application first supplies the pinned adapter identity, current mechanical facts and the compact rule fragments named by the operation's mechanic tags. It also supplies a byte-counted topic/heading catalogue from the pinned rule manifest. Only an unresolved adjudication question may spend the recipe's existing read allowance on another exact section. Minimal recipes stop at mandatory fragments; richer recipes can inspect examples or related rulings. No recipe begins by transmitting a full rule library, asks a model to rediscover universally known applicability, or uses another model call merely to choose which rule page to read.

| Work | Default context and capabilities | Model-work boundary |
| --- | --- | --- |
| Quiet activity/check/chain progression | Admitted mechanics and exact state; no model tools | Zero provider calls, including hidden summarization |
| Ordinary opening/continuation/consequence | Relevant creative sections, current constraints, receipt/intention, compact evidence | One round; no tools by default |
| Evidence-seeking turn | Same mandatory core plus scoped leads and a small read/search contract | At most three rounds and six reads total, including final generation and any repair |
| Historical report | Committed source outcome plus relevant presentation guidance | One round; no current-choice planner or exploration tools |
| Derived memory maintenance | One bounded source segment and existing affected records | No independent model call by default; separate capped job only if explicitly enabled |

Recipe selection is task-local, not one monster prompt for every job and not a new variant for every fictional genre. Returning identities, explicit unresolved references or incomplete required evidence can select the evidence-seeking recipe before dispatch. Direct deterministic retrieval remains useful even for a one-round recipe. Optional thematic discovery can be permitted by that recipe; it is not mandatory research on every turn. A fully supplied conversation or microbe response need not search anything.

Creative direction comparison defaults to the final composition round, where the model returns one bounded private selected/rejected set beside the ordinary candidate. A separate private ideation round is an experimental rich-route option, not the default: it must retransmit grounded evidence and then pass its selected direction into final composition. The final round must consume that artifact rather than generate it again. On the maintained candidate-capped Greywake packet, the exact credential-free OpenRouter projection measured 20,256 captured request bytes inline versus 30,788 across separate ideation and composition, a 10,532-byte increase with the same total generated-token allowance. This is structural cost evidence, not a quality verdict; a separate round is adopted only if forked live comparison shows enough player-value gain to justify the extra dispatch and retransmission.

Treat configured budgets as continuous, versioned policy dimensions rather than three hard-coded product shapes. Recipes define required minima and scalable optional bands. Context assembly fills those bands by marginal decision value: required state and direct evidence first, then relevant continuity, texture and broader discovery. Output reserves similarly protect a complete playable answer before allowing elaboration. Large allowances may increase breadth, deliberation or prose when evaluation shows value; they must not trigger padding, exhaustive file loading or gratuitous tool rounds. Small allowances may shorten optional description and exploration, but cannot produce an incoherent choice, omit a required constraint or silently invent missing evidence merely to stay cheap.

Record what each operation actually bought: selected-section bytes/tokens, omitted optional candidates, retrieval/read rounds, generated and reasoning tokens, accepted-output rate, latency and reported charge. Evaluate cost per accepted useful turn across representative quiet, rapid-dialogue, return-memory and unusual-world cases. Optimize repeated fixed instructions and deterministic projections, but prefer a smaller task-appropriate packet over a larger cacheable universal prompt.

### Enforce the whole operation

Capture the operation identity, recipe/version, maximum total model dispatches, reads, cumulative transmitted input, total generated tokens, reasoning policy, retained bytes, wall-clock deadline and total microusd ceiling. Bound each request too. Count framing, output/tool schemas, repeated prefixes, tool responses and diagnostics; final-prompt size alone is not total input spend. The financial cap and token/byte caps are independent constraints, not substitutes for each other.

All work caused by the operation shares these limits: exploration, repair, optional extraction and any future delegated calls. Deferred maintenance also needs an explicit maintenance allowance and originating-operation attribution; moving it to a queue cannot hide its cost or create credit. Multiple turns share the run/account cap; per-turn ceilings alone do not control a rapid session. Optional unattended generation/maintenance needs a persisted frequency limit and capped allocation in that shared allowance. Coalesce duplicate triggers by committed source range/purpose; reloading, replay or faster game ticks cannot mint new paid work.

Reserve the bounded operation envelope against the existing account/run ledger. Subdivide it for dispatch rather than charging/reserving it twice. Track cumulative token/round consumption durably across attempts and restarts. Before exploratory work, preserve enough of the envelope for one final request using the bounded retained context and final output allowance. If that cannot fit, skip optional exploration; if essential evidence is missing, hold before paying for a knowingly unusable result. The reserve is capacity, not a guarantee the final model output will be valid. A repair only uses remaining capacity; never grant another envelope on failure.

Initial offline tuning candidates are one-round ordinary requests targeting 32 KiB with the existing 48 KiB hard maximum, and exploration capped at 64 KiB of cumulative serialized requests across at most three rounds. Ordinary/final output starts at 2,048 generated tokens; an exploratory operation starts at 4,096 generated tokens total, including any billable reasoning and repair. Reports/standalone memory candidates start at 16 KiB input and 1,024 generated tokens. These are maxima to measure against captured fixtures, not typical usage estimates, model-price quotes or permission to enlarge the current execution policy. Byte accounting includes full captured schemas/messages; provider framing is budgeted additionally. Route-valid token ceilings and the existing conservative reservation can be stricter. If the required schema/state does not fit, record the cause and simplify the contract or hold; do not raise limits merely to pass a fixture.

Money limits must come from an explicit funded run, not hardcoded promises of affordable gameplay. A route is ineligible if its bounded cold/cache-write cost cannot fit. No automatic replenishment or assumption that the original deposit remains available.

### Small tools and small records

Prefer bounded application reads that return the requested state, a short source excerpt or ranked handles, not a whole folder with all its backlinks. Compose deterministic retrieval/filtering in code rather than asking a model to orchestrate each database lookup. Keep canonical records readable and concise: identity, current claim/status, attribution, source/version and only the prose needed for that role. Original player-visible prose stays intact; compact cards link to it rather than copying it. Record size, cumulative patch output and excerpt limits belong to validated schemas, not only prompt advice.

Use one small stable tool set per recipe; no catalogue of every game mechanic/storage operation in every request. The Storyteller-facing memory vocabulary is conversational: `ask_memory` carries at most two ordinary-language questions and a simple established-evidence versus fitting-possibilities intent, while `read_memory` opens only handles returned in the same operation. Deterministic application code chooses and combines registry, lexical, semantic, relational and exact-source primitives permitted by the frozen recipe. It performs filters, deduplication, ranking and result packing instead of making the model operate backend machinery. Count every internal query, directory page, section and subread against the same allowance even when one friendly question fans out behind the facade. Queries have bounded result counts, excerpt bytes, backend work/time and source coverage. No recursive glob/read-all tool, arbitrary SQL, host file access or concealed paid reranker. Required exact state is supplied directly. Search results are candidates, not truth; partial/no-match is explicit. Deduplicate repeated reads, drop obsolete optional pages and reassemble each round from the retained working set rather than append an entire transcript. Pruned content loses its loaded-evidence status.

Provider-native function/tool calling is optional transport syntax, not the domain contract. Different cheap/free models support it unevenly, so the authoritative protocol remains a strictly validated structured action-or-final response that every adapter can represent. Evaluate native tool syntax only when it lowers malformed requests or token cost for a specific admitted route. A player-facing clarification is a separate game interaction and must not be used merely because the Storyteller failed to retrieve context.

Avoid automatic LLM compaction when context fills: deterministic omission/repacking is first, then a named hold if mandatory content cannot fit. Summary size thresholds schedule eligible work, not an unconditional new bill. Do not summarize summaries repeatedly or rewrite the whole library. Defer optional maintenance when its allowance is empty; preserve raw sources and show index/summary coverage gaps.

### Reasoning and delegation

Default to a compatible non-reasoning or explicitly low/bounded-reasoning route only after a quality evaluation; price alone is not enough. Capture actual route semantics: whether reasoning can be disabled, whether it shares the output ceiling, and all billable categories. Unsupported/unbounded semantics make a route ineligible. Hiding reasoning text does not disable its computation or billing. Do not request a verbose reasoning transcript; store short operational purposes, source references and measured usage. [OpenRouter reasoning controls](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

There are no runtime subagents in this prepared implementation. Context isolation is not a cost reduction by itself: an extra worker pays for its own instructions, evidence, reasoning and the parent's consumption of its answer. Anthropic reports substantially higher token consumption for its research-agent system; that is evidence of a tradeoff, not a forecast for our game. [Anthropic's multi-agent research account](https://www.anthropic.com/engineering/multi-agent-research-system).

If later measurements justify a research specialist, admit it as an explicit extension: one bounded question, minimal scoped evidence, source-linked answer/uncertainty, no recursive delegation or direct world writes, and a child allowance carved from the parent's existing envelope. Count both sides of the handoff. Compare against deterministic retrieval and a single focused model call first; do not build a general multi-agent orchestrator to solve an unmeasured problem.

## Summaries without losing the story

Summaries are derived artifacts with source sequence coverage and a version. Create them when enough material accumulates, not after every sentence. They support retrieval and recaps; they do not replace authoritative possessions, current conditions, ownership or promises the product needs to enforce.

Memory segments summarize bounded source ranges; a return recap can select relevant evidence across several ranges. Their coverage is explicit. Neither divides gameplay into chapters or requires a scene to end. A low-drama promise can become the most relevant fact for today's decision, so a permanent importance score cannot determine every future retrieval.

Reassess a bounded amount of material at useful context/size boundaries or on return, and reuse valid results. Do not call a model after every ordinary receipt or repeatedly summarize the whole lifetime. Segment revision and source coverage distinguish old summaries from newer evidence. Include a minor early encounter and routine achievements in the recall acceptance cases. [Concepts](../concepts.md) distinguishes these storage boundaries from Storyteller turns and player decisions.

Keep canonical facts linked to the passage or accepted change that established them. An unverified rumor remains a claim. When facts change, context assembly prefers the current record while preserving history explaining the change. Include a test in which a minor earlier object becomes relevant much later.

Long histories need bounded retention of raw generation traces, not deletion of the player's readable chronology. Track stored media and trace volume as costs alongside tokens. Repeated recap requests should reuse an artifact valid for the same viewer and chronology revision.

## Long-running quiet play

A low rate of dramatic incidents does not by itself reduce inference cost. Resolve an eligible ordinary interval without polling a model every tick to ask whether something happened. A reusable routine needs an explicit supported outcome policy, preconditions and a bounded interval; applying it is different from reusing the exact result of an earlier operation. Resource changes still occur once per completed operation, and an interruption cannot award the full planned interval as though it completed. Do not assume partial rewards are linear without a defined rule.

Batch ordinary reporting and summarize repeated activity where useful. Keep consequential changes inspectable without producing one prose passage per mechanical update. Reassess when circumstances change, a player makes a new request, a relevant boundary is reached or an incident is due. Repeated checks must not redraw chance until an event appears. The first supported routine and incident policy remain to be designed; this is not authorization to implement a simulation for every profession.

Fresh daily conversations can still require fresh inference even when no danger occurs. Measure routine resolution, conversation generation, memory extraction, summarization, retrieval/embeddings and recaps separately, including discarded work. Cached context does not make new dialogue free. A 30-day story is a useful evaluation scenario, not a promised price point.

## Three different caches

### Active-scene continuity and disposable task conversations

Each task reconstructs an immutable request from persistent state and evidence. Profiled stories retain a revision-fenced active-scene anchor, and task admission loads its complete passage range before bounded selection. Missing or oversized required coverage holds preparation instead of silently truncating the scene. Existing stories without an anchor retain the six-optional-passage fallback. Tool-round transcripts remain future task-local work; useful findings may survive only through admitted source-linked artifacts. This does not imply summarizing every prior turn. Preserve the detailed ongoing interaction while its wording, choreography, commitments and unresolved observations matter. The offline audit proves complete bounded source coverage for human and nonhuman fifteen-turn fixtures, not live narrative quality or unlimited scenes.

History, current exact state and attributed claims have distinct roles. Current prose appears once in the provider projection while retaining its evidence handle. Publication may revision-fence a proposed restart at the newly committed current passage; no passage-count heuristic infers that a scene ended. A summary of a completed portion must declare its coverage and preserve unresolved details; it cannot silently replace required evidence or alter mechanical state. Archived discovery remains owned by the memory feature.

Request purposes select their own templates, schemas and limits. Existing opening, continuation, consequence and report tasks remain one-shot. Separate models or agents are optional implementations of a demonstrated need, not a fixed pipeline every decision must traverse. All future retrieval, repair and maintenance consumes the existing attributable operation budget.

Memory retrieval uses a named server-resolved recipe rather than exposing backend scoring knobs as entitlement. Minimal, balanced and rich postures select bounded candidate breadth, source-passage participation, query-term/ranking effort, exact reads and retained evidence bytes. The effective recipe intersects those defaults with the stricter task/usage envelope and is frozen into the retrieval trace. A campaign preference or user tier may choose among permitted postures, and a task may deliberately choose a cheaper posture, but none may relax story-root freshness, visibility, authority or branch isolation. More allowance permits more optional evidence work; it never grants a different canon or forces the system to fill the allowance.

Measure scene-wide cost as cumulative requests, repeated input, generated output and attributable maintenance. Preserve exact bytes and unknown token estimates until a tokenizer is verified. Potential common-prefix reuse is an offline structural fact; a provider cache hit or discount requires provider evidence. Rebuilding from durable evidence can preserve identical prefixes without preserving a server-side conversation.

| Cache | What it saves | Correctness rule |
| --- | --- | --- |
| Application data/context | Database reads, assembly and tokenization work | Key by story, visibility, source revisions and schema/prompt versions; expire or invalidate when dependencies change. |
| Exact generated artifact | A repeated provider call for the same logical operation | Reuse only an accepted result or a validated prepared result with matching preconditions. Do not treat semantically similar stories as interchangeable. |
| Provider prompt/KV cache | Part of provider inference work and sometimes input cost | Provider/model-specific prefix rules, pricing and expiry; measure reported usage rather than assume a hit. |

Stable instructions and reusable context belong early in the request; changing intent belongs late. Storyteller prompt `storyteller.v6` orders the task and profile first, then `sceneContext`, followed by `currentState` and `selectedIntention`. The structural audit reports each section's kind, item/character/byte counts and hash alongside cold serialized-request totals and adjacent common-prefix bytes. It omits exact section content by default; `pnpm storyteller:packet-audit -- --sections=<case-id>:<section-key> --max-selected-bytes=<bytes>` writes only explicitly selected content to a separate bounded artifact. These are structural measurements only: byte counts and hashes are not token counts, provider cache hits, write prices or savings. Keep schema/tool ordering and stable recipe sections deterministic; volatile allowance counters, timestamps, state and search results belong after that prefix. Per-recipe specialization can reduce cache reuse across recipes, but a smaller appropriate request takes precedence over one oversized universal cached prompt. Do not retain irrelevant history just to preserve a prefix, or pad short prompts to meet a cache threshold. Measure cache hits and actual savings; cache write charges can exceed ordinary input charges, so admission uses the greater applicable cold/write bound, not an assumed cache hit.

OpenRouter documents prompt caching and provider sticky routing, with behavior varying by model/provider. Explicit provider order and failover can affect reuse. With hours between story updates, short-lived caches may expire before the next request. Calculate the unattended baseline without assumed cache discounts, then measure actual savings. [OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching).

Hosted inference does not give our application control of GPU memory placement or KV eviction. Redis cannot preserve a provider's GPU cache. Self-hosted inference would introduce a separate capacity, batching and model-serving project; defer it until there is evidence and a reason to operate GPUs.

Prepared story material is another form of reusable work, but speculative branches cost money. Prepare a short likely continuation after commitment; do not generate every possible action tree. Record the fraction and cost of prepared content discarded after player intervention.

## Budget accounting

Track per-story spending and an explicit funding account/period. Before sending a request, atomically reserve a conservative upper bound that includes the greater applicable uncached/cache-write input cost, configured maximum output, relevant billable reasoning/tool usage and an allowance for fees. Normalize provider categories so reasoning counted inside completion is not charged twice. Use a versioned price snapshot and route constraints. Reconcile with provider-reported cost/usage afterward; estimated and actual values remain distinguishable.

Provider settings are capability and price facts, not commercial authorization. Application admission resolves the platform, entitlement and lower restrictions, requires its stable route identity to equal the configured provider route, then intersects both sets of ceilings. The resulting task stores the full effective-policy snapshot and narrowed resource envelope. A started story retains that snapshot for later continuations, consequences and reports; a provider task with only execution settings fails closed. This makes the grant reviewable and replayable without reinterpreting a later tier configuration. Durable window debits and policy-transition holds remain a separate enforcement phase.

Each dispatch attempt is the durable audit grain. Its exact specification is the captured request plus that round's generated-token ceiling; packet review, reservation and transport consume the same pair. A multi-round operation persists the round's UUID attempt identity, exact request/hash and private raw response in its generation-owned exploration artifact before interpreting the response; the accounting attempt with that same identity owns reservation, dispatch and settlement. It records funding account and run; owning application user; nullable story/draft identity; generation, operation and attempt identities; task purpose; Storyteller profile/revision; prompt, recipe, resource-policy and price versions; requested model/provider; conservative estimate and reservation; provider-reported charge; normalized prompt, completion, reasoning, cache-read and cache-write tokens when reported; provider generation/model identifiers; reservation, dispatch and settlement timestamps; observed duration; terminal outcome; and reconciliation status. Store unavailable metering as unknown, never zero. Do not store prompt/output prose in the accounting row: immutable generation artifacts retain that private content while the ledger retains queryable attribution. Provider dispatch is not safe until exact packet review and accounting both consume the already persisted round identity; neither may mint another ID after recovery.

The estimate is a pre-dispatch upper bound, not a fabricated prediction. Until a route-specific tokenizer and cache-write pricing are validated, retain serialized request bytes separately and label input-token estimation unavailable; price configured token ceilings conservatively. After settlement, calculate an independent expected charge only when the captured price dimensions cover every reported billable category. Otherwise keep calculated cost and delta unknown while preserving the provider-reported charge as the settled amount. A mismatch is evidence to investigate, not permission to rewrite provider usage or release another attempt.

Provider responses are normalized at the adapter boundary. Preserve the raw provider generation identifier, resolved model when supplied, finish reason, HTTP status and non-content usage metadata, but never log credentials, reasoning text, prompts or generated prose. Provider-reported cost is the primary settlement source. A later provider metadata lookup may enrich an existing attempt idempotently; it may not create another charge or silently convert uncertain usage to zero.

Budget availability is `limit - settled usage - outstanding reservations`. Concurrent workers must reserve under the same account lock or equivalent conditional update. Do not let each story independently observe the same free dollar and spend it. Lock funding scopes in a consistent order if both account and story caps apply.

Reserve each attempt, or an operation envelope covering all permitted attempts, before it begins. Retries, repair, summarization, images and discarded results count. Free users still consume a developer-funded allowance; “free tier” is an entitlement, not free infrastructure.

For development, use an explicit developer-funded account with per-story and global caps; this does not decide future commercial billing. Every operation pins its funding account and allowance period. Changing a story's owner, tier or preferences cannot silently move an already dispatched charge. Settle an attempt exactly once against its reservation, retain uncertain reservations across period boundaries and prevent a period reset from creating duplicate credit. Do not expire reservations merely because an Activity timed out.

When allowance is unavailable, expose a generation blocker and permitted recovery action as specified in [story lifecycle](story-lifecycle.md). Reading, pausing and seeing why a story stopped remain available. A budget increase is not an instruction to rerun a previously committed resolution or clear a manual pause.

An HTTP timeout can leave the provider request running and billable. Do not release its reservation immediately and send another call blindly. Mark usage uncertain, retain a conservative reservation, reconcile through provider identifiers where available and allow manual/operator resolution. Cancellation is best effort; it cannot promise zero charge.

Temporal replay can reuse a recorded Activity result, but an unacknowledged Activity can retry. Its first step must inspect the persisted attempt and reservation. Bound total provider attempts across Temporal retries, SDK retries and model repair; no individual layer may create a fresh allowance. Returning artifact references rather than full prompts/results also limits workflow-history storage and exposure.

Absolute provider spend caps cannot be guaranteed solely from token estimates if prices, upstream retries or reporting are uncertain. Combine conservative application admission control with gateway/account limits where available, bounded attempts, alerts and a global kill switch. Explain the uncertainty rather than advertising mathematically exact billing control we do not have.

## A concrete cost envelope

The following prices are invented arithmetic inputs, not quotes for any model. Assume $0.50 per million input tokens and $2.00 per million output tokens. An 8,000-input/1,000-output call costs:

```text
(8,000 / 1,000,000 × $0.50) + (1,000 / 1,000,000 × $2.00)
= $0.006 per call
```

At two calls per day, a seven-day unattended period would cost $0.084 in this simplified example. At one call every five minutes, it becomes 2,016 calls and $12.096. Neither includes setup, retries, tools, summaries, images, gateway fees or hosting. Model choice matters, but generation frequency can overwhelm a cheap token price.

This also exposes the product tradeoff: frequent novel unattended developments and extremely low spending may conflict. Settings should constrain narrative frequency and spending independently. Faster fictional time need not automatically mean proportionally more narrated moments. If a story runs out of valid prepared material and budget, hold it with a clear reason rather than claim a logic-only engine can invent an equivalent continuation.

Bound consecutive immediate autonomous transitions as well as provider calls. Even prepared zero-cost outcomes must not form an unbounded loop that consumes Temporal tasks or generates notification spam. Measure workflow actions/history, database/worker hosting, storage and delivery alongside model usage. The token envelope above is not the full cost of keeping a hosted story available for a week.

## Prompts and experiments

Keep prompts and small reusable fragments in `packages/storyteller`, reviewed with code and exercised against fixtures. Compose only fragments with a clear responsibility: behavior, output schema, storyteller preferences, contextual material. Record the resulting prompt version/hash and source versions for each attempt. Do not create a general prompt CMS or dozens of database snippets just because composition is possible.

Langfuse is the proposed tool for AI traces and experiment inspection. Its prompt management supports versions and labels, and its TypeScript observability integrates with OpenTelemetry. Remote prompt management can be added when editing without deployment becomes useful; pin a resolved version per run and retain a last-known-good local fallback. Telemetry or prompt-service downtime must not corrupt or indefinitely block an otherwise valid story. [Prompt versioning](https://langfuse.com/docs/prompt-management/features/prompt-version-control), [TypeScript observability](https://langfuse.com/docs/observability/sdk/overview).

Use offline comparisons first: the same story snapshots and intentions against candidate prompts/models. Measure reference validity, continuity, choice diversity, accepted-outcome latency, cost and human preference. Schema validity alone is a weak quality metric. Automated model judges are advisory and themselves cost tokens.

Measure total cost per accepted playable turn, not just the cheapest successful API response: include failed/discarded attempts, repeated input, reasoning and attributable maintenance. Report zero accepted turns as failure with its cost, not a division result or a zero-cost success. Show cold worst-case, actual reported cost, latency, useful versus irrelevant evidence, round/read count and cost by purpose. Compare a one-shot recipe, deterministic retrieval plus one shot, and bounded exploration on the same grounded return and rapid-dialogue cases. Scripted runs prove accounting/plumbing only; affordable narrative quality still requires a separately authorized tiny live evaluation and owner taste review. No automatic model judge or expensive fallback.

For live A/B testing, assign a stable variant at story creation or another explicit boundary, not a new personality every request. Record model/provider and prompt versions so a routing change does not masquerade as a prompt improvement. Do not run a second paid shadow generation on every player action by default.

## Approved local POC boundaries

Capture at most six previous passages, current state, selected intention and up to twenty source-backed notes, with a 48 KiB complete request limit. Mandatory evidence overflow holds before inference. New tasks produce note patches with the scene; there is no separate summarizer or tool loop. First provider execution allows one dispatch per attempt, no SDK/model fallback or repair. Explicit retries require settled usage, a new retry receipt and remaining shared run allowance. Ambiguous usage stops paid admission globally. The source adapter is opt-in and is tested only with fake transports until a separately approved live run.

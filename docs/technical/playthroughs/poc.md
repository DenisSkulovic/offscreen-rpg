# The POC this atlas is asking us to prove

Status: proposed selection and acceptance reference, not a new claim of implementation or owner approval. Runtime coverage remains in [progress](../../progress.md). This document chooses a small connected proof from the larger examples; it does not replace the owning feature phases.

The readiness pass makes this session concrete in [GS-01 through GS-07](harbor-session.md), with state/roll/task ledgers and alternate failure/quiet branches. Use the [solo integration contract](../solo-gameplay-contract.md) for selected timing, publication, hold and authority defaults, and the [feature route](../../features/README.md) for bounded coding order.

## The player-facing promise

“Make a meaningful choice, commit to something that takes time, leave, and return to a character whose work and circumstances really changed. When the story needs you, it offers a grounded choice; when it does not, the life can continue without manufacturing a scene.”

The owner should be able to explain, without reading source, why the character is here, what has been earned, why work stopped, what remains possible, and which choices would actually differ. If they cannot, a functional backend is not sufficient evidence of a good POC.

## One short session, with alternate replays

Use the existing harbor/beacon content as the first earned-work proof and pineapple as the active-choice contrast. Do not build the complete Batman game to prove the underlying flow. The following combined harbor session is a **proposed fixture revision**, not a description of the current beacon runtime:

1. Opening: Mara can begin a supported repair, secure the tools, or take a genuine wait. GS-01 defines the exact prepared state and options; no false instant “wait until the stranger leaves.”
2. Accept a bounded repair intention with a visible progress explanation and estimate. Start at zero; one failed attempt consumes time without progress. The player sees the difference between effort and countdown.
3. Leave or pause/resume. Refresh/reentry exposes the same instance and exact earned work. A manual pause differs visibly from simply closing the page.
4. A selected event interrupts at an admitted boundary. GS-02–04 supply three immediate scenes with no routine menu and explicit supported outcomes. One cautious option withdraws without secretly forcing confrontation.
5. Resolve the event, do the short B task, then resume the exact A. Run B through real settlement, not a database shortcut. Show monotonic world chronology and no work earned on A while doing B.
6. Complete A exactly once. In GS-06 the player independently chooses a genuine wait; at its end, go idle. A separate accepted repair → wait chain replay tests automatic continuation; do not confuse the two permissions.
7. Return view: completion, earned credit, elapsed/held time and interruptions are understandable from factual receipts. A literary recap is optional, not needed to conceal missing state.

Replay this fixture with follow-up policies changed, not core rules rewritten:

- **Quiet replay:** no occurrence; no generated completion report; independently selected repair and wait create no generation tasks after initial preparation. GS-07 gives the distinct no-event repair timeline.
- **Narrated replay:** completion requests a historical report while the player can choose the wait. Delay report publication until the wait has ended. The report attaches to the completed repair, does not replace current controls and cannot grant credit again.
- **Accepted-chain replay:** capture repair → wait and its explicit horizon before execution. Completion starts the accepted wait exactly once when authorized, or stops with a reason. Repeat with quiet/report/scene policies; the scene must prevent that successor until an explicit handoff. This later slice proves continuity without an arbitrary workflow DSL.
- The interactive branch in the main session supplies the third case: a required scene holds relevant progression until it is resolved.

Also prove **player-directed dormant play**, not only the chain: after quiet completion, independently choose another still-valid prepared activity, complete it, then repeat an eligible one with no new generation tasks. Reuse a small authored harbor opportunity package and the same rules; no whole village generator is needed for the first proof. Change an admitted access/scene condition and reject a stale now-ineligible start. [LO-02 through LO-04](local-opportunities.md) specify the corresponding larger-world experience. A repair that is already complete must not be offered as repeatable work just to fill this test; select genuinely repeatable content.

Pair that with a **rapid scene-only run**: three consecutive authored narration/choice turns explicitly permit no routine starts, even though the character owns an apple and has reusable activity definitions from earlier. Do not append “Eat apple,” reopen sleep/travel, auto-resume suspended work or start a queued entry when one decision resolves. Only a later explicit Storyteller handoff reopens selected activities. Use supported immediate actions with no artificial waiting; generation latency remains visible rather than becoming fictional work. The dormant run retains one valid authorization across quiet receipts; every new interactive situation explicitly sets its own. This contrast is essential, not a later pacing polish pass.

Aim for roughly a minute of active waiting at an explicit demo rate, not a real overnight onboarding requirement. The same rules can run slowly; a fast demonstration must not grant completion via test-only shortcuts. Longer waits can be evaluated separately for their emotional payoff.

## Ready-to-implement reasoning, not another engine rewrite

The first dependency remains activity identity/shared chronology. Activity A1 now has the concrete BC-04 oracle, source map and selected clock/collision semantics. Old A effort is retained; B advances world time; exact A resumes at the current position. Preserve receipts/private plans and existing immediate resolution. Follow the feature route rather than implementing all atlas scenarios.

Next, situation S1 establishes choice authority; activity A2 adds genuine wait; S2/U2a jointly establish quiet player-directed reuse; U2b separates reports/scenes; S3 extends bounded preparation; U2c adds accepted chains. Queue transitions and effects share an atomic boundary/explicit handoff so duplicate wakes cannot start children. Do not implement these as one giant phase or postpone them behind complete cooperation/every rule family.

Agency fixes can be bounded content/admission changes: replace the false instant wait and make the failed attempt's next affordances honest. Do not respond to an uninteresting menu by creating an autonomous-agent framework. The record of the failed attempt must explain any new precondition or changed risk.

Finally, walk the actual application flow with the owner. The mechanical/authorship/quiet-life proof is the first milestone, not the full vision: arbitrary premise setup, long-history discovery, deeper activity rules and separately authorized live quality remain explicit follow-ups. Optional checks follow verification policy; passing a suite alone cannot satisfy the player's experience. No live call is authorized. Identify scripted prose honestly.

## Design findings to carry forward

### Time must buy a specific kind of change

The traces distinguish assured waits, contracted coverage, contributed work, repeated routine outcomes and changing position. Forcing every one into contribution would be as misleading as making every one a timer. Add a typed rule only for a concrete semantic difference; share lifecycle, authority, clock and effect machinery.

### Narration and new authority are different costs

A late arrival report may safely describe old history. A new interactive scene may require current-world admission, new identity/fact proposals and an active hold. One generic “generate next node” operation obscures both correctness and spending. Current consequence tasks alone do not supply the proposed report-only or event-admission contracts.

### Failure without a changed situation can become reroll farming

The Gary fixture exposes this today. No model prompt can compensate indefinitely for a plan that permits the same meaningful attempt forever with no consequence, changed method or time cost. Conversely, banning all retries is not the answer; a new tool, approach, situation or accepted effort can make another attempt legitimate.

### Quiet success needs a next life, not a dead end

An empty menu can truthfully signal a held fixture, but continuing-life play needs permitted work/resumption/idle controls outside a compulsory generation loop. Otherwise “no scene needed” becomes “the player is stuck until we pay for one.” This is why mechanical resumption and finite accepted plans matter to the POC.

### A candidate event is not an established attacker

Simulation can select a development opportunity without an LLM poll. Turning it into a new katana boss requires a supported world proposal and publication. If the event rule already committed a hazard, failure to narrate cannot erase it. That admission distinction is unfinished and should remain visible.

### Runtime capability is not permission

Being able to resolve a fight does not authorize the sleeping player's character to choose it. Being able to call a provider does not authorize spending. Being able to reassign a worker does not authorize controlling another player's character. These permissions are separate captured inputs, not guesses from personality prose.

## Owner calibration: what to ask after reading or playing

- Does the cautious pineapple path feel like a legitimate episode, or a less-rewarded refusal to play the “real” game?
- Does repair feel earned because the character's capability and outcomes matter, or just like waiting beside a progress bar?
- Can the owner predict what pause, suspend and cancel will preserve without asking the developer?
- Is it acceptable for a new event to stop an overnight plan, and is the return explanation satisfying?
- Does a selected report add atmosphere without making every boundary noisy or costly?
- Which one-minute sequence makes the owner want to continue tomorrow? Which paragraph/choice feels generic or arbitrary?

These are observations to seek, not a questionnaire blocking the documentation work. The atlas supplies concrete samples to disagree with. Full combat, complex economies, map rendering and brilliant long-form prose cannot rescue a central loop the owner does not enjoy.

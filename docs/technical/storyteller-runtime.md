# Storyteller runtime and model routing

A storyteller is a versioned content profile over shared application capabilities. It is not an agent instance or a provider/model selection. The runtime currently has opening, narrative continuation, mechanical consequence and historical-report task contracts, surrounded by context assembly, validation, accounting and publication. Mechanical opening and consequence outputs can propose bounded private action plans; deterministic code owns their admission. The report contract is execution-ready but is not yet admitted or published by gameplay. Targeted memory retrieval and private creative discovery share one bounded protocol and persisted controller. A provider task carrying the memory recipe now runs that controller through the ordinary generation executor, saves its accepted final candidate as the generation output and enters the existing publication path; neither a graph framework nor an agent per NPC is required.

## Profile and task contracts

`packages/storyteller/src/profiles/definitions/` contains JSON definitions. The private catalogue validates identity/revision, public description, tone, pacing, choice guidance, continuity guidance, creative limits and per-task guidance. Public catalogue responses expose metadata only. Adding another supported storyteller means supplying data and registering it in the catalogue; generic runtime code does not branch on profile identity. The explicitly scripted rehearsal source consumes validated authored content and is not an inference implementation. Its mechanical benchmark adapter may recognize authored fixture facts in order to produce repeatable state-dependent evidence; those branches stay inside the offline fixture source. Generic task preparation, admission, publication and application policy must not recognize a world, species, character or profile through a scenario-specific conditional.

A draft stores an optional profile reference while incomplete. Admission requires and resolves that reference, then freezes the full profile in an immutable task artifact. Start copies the reviewed candidate's profile and execution policy to the story. Later catalogue edits cannot alter an admitted generation or existing story automatically. Explicit [settings revisions](story-settings.md) allow mid-story customization while retaining immutable task snapshots. Changing a draft's profile increments its revision and invalidates an older candidate. Discarded pre-POC artifacts are reset rather than decoded.

The profile and the campaign's narrative direction are separate inputs. A profile provides reusable creative defaults. Narrative direction, when present, is campaign-owned private context describing the larger pressure or development the Storyteller is cultivating; it can also explicitly state that none is wanted. Every task captures the effective creative settings and exact direction revision it used. A profile/settings change affects a later task at the normal revision boundary but does not rewrite an admitted task, established world state or the campaign's direction by implication.

Storyteller preparation currently captures `inputVersion: 10`, `promptVersion: storyteller.v7` artifacts for the `storyteller.profiled.v1` durable kind/topic. The artifact contains source fences, full profile, execution policy, bounded context, its manifest, exact model request and immutable task resources. Only task-relevant instructions and profile guidance are assembled. The model sees local evidence handles, not database identifiers. Premise, fictional dialogue and retrieved prose are data below application authority. The narrative-opening instruction includes a concise redundant example because observed free endpoints advertised strict structured output but returned mis-nested or schema-minimum JSON; that example must match the task-specific provider schema exactly. Opening providers return only `version` and `scene`; the application adds empty continuity arrays after validation. Version 7 removes stored-only arrays that version 6 incorrectly requested from the model. Version 5 introduced bounded descriptive document-change proposals without granting write or mechanical authority. The JSON Schema and local validator remain authoritative; schema validation does not prove resistance to prompt injection or semantic correctness.

The version-1 scene result envelope contains a scene, separate current/arrival note patches and a bounded descriptive document-change proposal list. Mechanical consequence scenes use v3, narrate saved receipts and propose zero to four private plans; they cannot create an interval or reroll. Mechanical opening scenes use a task-specific v1 plan result, while narrative openings retain playable v1. Continuation scenes use v2 and can publish a choice or one prepared interval. Historical reports instead use a strict version-1 envelope containing only passage-shaped prose. Their task-specific schema rejects choices, action plans, effects, document changes, continuity patches, arrivals and extra fields; the continuity publisher also rejects report tasks. The earlier narrative rehearsal requires 2–5 choices with distinct normalized labels and IDs, forbids automatic life ending, and never accepts a free-text gameplay command. The selected published intention is recovered server-side from generation provenance, including the current/arrival source part. Labels and intentions are attempts, not guaranteed outcomes or permission to mutate resources.

Document changes are proposals, not direct writes. They may create or revision-fence descriptive lore, identity, relationship, narrative-thread and private-possibility documents. Narrative-continuation and mechanical-consequence publication supply exact source-passage provenance, stage immutable objects outside the database transaction, and commit their manifest versions atomically with the passage after rechecking narrative and document roots. Inventory, skills, scores, health, time, obligations and activity progress remain typed engine effects/state and cannot be edited through prose.

## Context and continuity

Requests carry only their task's result schema: opening, continuation, consequence or report. Consequences cannot return arrival-note patches, and reports cannot return either note patch or any scene authority. Context preparation rejects conflicting copies of the current passage and evidence beyond its sequence before any dispatch. These structural checks do not validate the truth of prose. The [offline acceptance contract](../engineering/offline-poc-acceptance.md) defines responsibility-specific context and manual probes for the remaining DM work.

Admission holds the story lock while reading the premise, current passage, selected intention, possessions, private notes and relevant committed evidence. The `bounded-scene.v3` policy retains every note source and current passage while projecting the current body only once. When application admission supplies an `active-scene.v1` scope, every committed passage in its declared range is mandatory alongside its explicitly required passage identities; a gap, mismatched current boundary or mandatory overflow fails closed. Without admitted scope, selection retains the current behavior of up to six optional recent passages. The artifact records the scope, loaded evidence and omitted optional sequences. The server query is scoped to this story and its admitted revision, and prepared futures are never evidence.

Continuation and consequence results may explicitly propose `activeScene.kind: restart-at-current`. The application can apply that proposal only while atomically publishing the exact validated current passage against its source revision; the new private anchor is that passage and cannot name an arbitrary historical range. Omission or `continue` preserves the existing anchor. Restarting raw active context does not erase passages, continuity notes or authoritative state. Historical reports and opening review cannot replace the anchor.

There are at most 20 derived notes, each at most 400 characters and four evidence sources. A result can create, update or retire up to eight notes in each publication part. Sources must resolve to supplied evidence or the permitted newly published part. Notes cannot authorize inventory, combat, movement or time changes. Their semantic truth still needs evaluation; referencing a passage proves provenance, not that a summary faithfully interprets it.

Current prose, notes and narrative revision commit together. Arrival notes commit only with the corresponding arrival passage and actual passage identity. Replay and stale-result fences use the existing story transition machinery. No automatic compression call, embedding store or universal world entity model is introduced.

This policy bounds bytes, not lifetime relevance. Every retained note currently pulls each non-current source passage's complete body into mandatory context; an old unpinned event cannot be rediscovered by this loader. Current prose is projected once under `current`, while its handle remains valid for provenance and result validation. The result validator does not preflight next-request feasibility, and provider input allowance is checked separately from the 48-KiB capture rule. The proposed [memory and situated recall](../features/2026-09-18--20-09--storyteller-memory-and-recall/FEATURE.md) completes provenance/body separation and defines a longevity evaluation.

## Execution and publication

The server separates admission, execution, publication, memory and recovery into focused modules. Temporal carries operation identifiers only. A task executes outside database transactions and settles its result before publication under the story lock. The persisted publication record distinguishes pending, published, stale and blocked from the generation's own outcome. Domain validation includes the application timing policy before a transition can be saved.

Scripted sources are explicitly pure and may be recomputed after an interrupted execution. Provider execution is different: each attempt allocates beneath one immutable operation envelope, reserves shared budget/windows, records dispatch intent, makes at most one request, and atomically saves its known charge and generation outcome. Immediately before transport, an application-supplied authority resolver must return the exact effective-policy snapshot captured by the task. Missing, malformed, revoked, downgraded or merely changed authority releases the unsent attempt; it cannot rewrite or enlarge queued work. A replay reuses a saved result; a dispatched request whose outcome is unknown is never resent. A publication failure does not discard a successful result or require another paid call.

An explicit recovery receipt retries the same admitted intention. Failed attempts with settled or confirmed-unsent usage may get a new attempt under the same run allowance. A pending finite-action consequence cannot retry until the exact execution is settled and its receipt promotes that same generation. Blocked publication retries the saved result. Unknown usage offers read-only refresh and requires operator reconciliation. Retry notices have their own workflow identity while referencing the original generation. Creative settings cannot change while a current resolution owns the narrative revision, so publication never silently applies a result captured under superseded creative authority. Old `opening.playable.scripted.v1` and `continuation.playable.scripted.v1` histories retain their decoders and meaning.

Report execution deliberately reuses this generation/accounting path, including the pure scripted source. Report-only activity completion atomically freezes the exact source passage, revision, tick, rules state, rolls, completion effects and factual result; persists a hook; and dispatches the strict report task. Publication locks the story but intentionally does not require that source revision to remain current: it attaches prose to the matching hook and increments only `viewVersion`. It cannot replace the current passage/menu, publish notes or mutate facts. A failed optional task marks prose unavailable while retaining the factual result; uncertain execution remains visibly generating for explicit recovery.

When a campaign exists, task context also carries a bounded `activitySituation`: current activity access, the exact active identity and up to twenty nonterminal commitments with action identity, revision, lifecycle state and public rule-specific progress. This is private preparation evidence, not authority. It omits terminal history and hidden plans. The scripted beacon consequence demonstrates the intended boundary by selecting an exact retained identity/revision from this context; scene output still passes situation/action validation before publication can offer that resume. Historical reports receive their frozen source state through the same task capture and cannot turn this context into current choices.

## Provider and budget boundary

The OpenRouter HTTP adapter is constructed explicitly with a credential and opt-in. It accepts one pinned model/provider route, disallows route fallback and redirects, bounds output/response bytes and time, and has no internal retries. Its captured output protocol defaults to native JSON-Schema constrained decoding. A separate evaluation compatibility mode may request a plain JSON object when an endpoint's constrained decoder collapses values to schema-minimum placeholders; the exact same task schema remains captured and application validation remains strict, with no coercion or implicit repair. Provider policy also captures the response transport: buffered JSON remains the default, while bounded SSE is an explicit evaluation transport that requests final usage and reconstructs the same locally validated provider envelope from streamed content. This field is part of the exact reviewed packet, not an adapter-only toggle. Its transport is injectable for free tests. Once response headers exist, either transport retains a bounded valid `X-Generation-Id` even when reading or parsing the body fails; the resulting uncertain attempt can therefore carry the provider lookup identity into durable accounting. SSE improves the chance of receiving headers before a long generation finishes, but does not guarantee that a timeout occurs after headers. Missing usage, incomplete streams, ambiguous HTTP outcomes and timeouts retain the reservation and stop further paid admission. Known refusals or malformed output still settle their reported charge.

Funding, run and attempt tables use integer USD microunits and decimal-string JSON boundaries. The captured task envelope is the non-renewable ceiling for a complete operation. Each dispatch reserves its exact packet and an explicit byte/input/generated/reasoning slice beneath that ceiling; the current one-shot executor defaults that slice to the full envelope. Usage windows reserve the same dispatch slice. Known intermediate settlement consumes the slice and leaves the operation open, known final settlement closes it, and uncertain dispatch retains liability and closes admission. A byte-based input upper bound includes request/schema framing; exceeding it holds the operation. Accounting takes a global admission lock, then account, run and attempt locks; these transactions never acquire a story lock. Independent story publication does not acquire accounting locks. Account/run caps and attempt limits are shared across concurrent work. Unexpected over-reservation charges stop all funding accounts. Reconciliation does not automatically clear a stop.

Normal startup and the local launcher use the offline source. Merely storing a key cannot enable inference. Production composition requires `STORYTELLER_LIVE_ENABLED=true`, a validated `STORYTELLER_EXECUTION_JSON`, a matching approved worker policy, a current dispatch-authority resolver and pre-provisioned funding/run records. The environment-only worker composition deliberately supplies no authority resolver yet, so even an otherwise configured provider task is released before transport. No account or allowance is fabricated at startup. There is currently no commercial entitlement selection, operator provisioning/reconciliation UI or selected live route. Before a deliberately authorized evaluation, connect current server-owned authority, verify the real allowance and current route/pricing and prepare the operator procedure; do not infer a balance from the original deposit. See [context and spending](context-and-cost.md).

## Tools, rules and the remaining DM task

No model tools are currently dispatched by the normal executor. Ordinary admissions default to captured `single-turn.v1` resources with creative exploration explicitly off. A caller may request an off/minimal/balanced/rich creative posture during provider admission; the application intersects every dimension with the effective usage policy and provider envelope. If useful capacity remains, the immutable task carries both the narrowed creative recipe and a compatible `memory-exploration.v1` parent recipe with one final-answer round reserved. If policy cannot fund at least one exploration round, read and retained packet, the request captures creative exploration as disabled instead of treating an omitted limit as permission. Storyteller validation rejects creative work outside the parent round/read/byte, generated-token, latency or microusd ceilings.

The provider-neutral memory protocol validates a private non-publishable `needs_context` round with two model-facing actions. `ask_memory` accepts at most two ordinary-language questions marked as established-evidence or fitting-possibilities work. `read_memory` opens only a task-local `m#` current-record or `x#` exact-source handle shown at the beginning of an evidence item ID; evidence packet `s#` values are provenance citations, never read handles. The canonical dispatcher currently maps evidence questions to bounded lexical retrieval and possibility questions to the admitted broad-discovery route; future evaluated registry, semantic and relational strategies remain application-owned routes behind the same facade. Internal traces retain `search_memory`, `creative_search`, `inspect_memory` and `read_source` distinctions for diagnosis and accounting without requiring the model to orchestrate them. Possibility questions obey captured enablement, query, per-query candidate and operation-wide lead caps; a final private direction set obeys its candidate-direction cap. Lead accounting counts every returned creative candidate entry, including a repeated canonical handle from another query, because each entry consumes result/context capacity. The canonical dispatcher applies those caps before allocating handles or returning results and reports `lead-limit` rather than pretending budget exhaustion found no match. The persisted controller independently rechecks the normalized snapshot before accepting it, so a custom dispatcher cannot bypass task authority. A `memory-exploration.v1` resource shape caps two or three total model rounds, one to six reads and retained bytes while reserving exactly one final-answer round; provider authority must still supply limits at least that strict. The application has a provider-free canonical dispatcher over one captured root: searches allocate task-local memory handles, exact inspection rechecks the manifest before loading, source links allocate separate source handles, and a serializable snapshot preserves handles, results, reads and retained bytes across restart.

The memory exploration controller stores that snapshot in a generation-owned `storyteller_memory_exploration` artifact after every accepted private round. Before invoking a round source it persists a UUID attempt identity plus the exact captured provider request and SHA-256. It then persists one normalized delivery containing the JSON model output and optional JSON-safe settlement evidence before invoking an idempotent settlement hook or interpreting the response. A crash in settlement therefore retries settlement from the saved delivery without invoking the model source again. Before executing canonical reads it separately stores the normalized memory action with its own SHA-256 identity. Recovery reuses both the captured delivery and saved read request, and counters advance only when the resulting snapshot commits. A crash after a canonical read but before that commit may repeat the same read-only lookup, but it cannot double-count it or repeat the already captured inference. Final/failed artifacts must clear both pending lifecycles. A separate persisted model-round counter includes malformed final deliveries as well as accepted context rounds, so one invalid final may be repaired only when the original task's total round allowance still has capacity. The invalid attempt settles against the same operation as intermediate work; it never receives a fresh budget. The controller rejects a context request that would consume the reserved final round, validates and stores the final candidate, and replays an already accepted candidate without another decision or canonical read. The ordinary executor promotes that validated candidate to generation output and then invokes the unchanged publication fence. Stale roots, invalid handles, read exhaustion and round exhaustion become durable classified failures and return the same failure on re-entry. Concurrent artifact revision changes fail explicitly.

Provider-backed exploration composes that lifecycle with attempt-owned dispatch review, reservation, an immediate current-authority recheck, dispatch, durable delivery and settlement. Each round uses the exact persisted request and a deterministic share of the operation's generated-token envelope. Its conservative input reservation is the smaller of the serialized-request byte upper bound and the route's per-request input-token ceiling; the operation envelope separately permits the sum of those per-round ceilings across only the admitted model rounds. Request limits therefore do not silently become operation limits, and a large byte upper bound cannot reserve more input tokens than the provider route could accept. A provider result is converted once into a JSON-safe delivery: output plus decimal-string usage and telemetry. Settlement reconstructs the typed provider evidence from that delivery. A restart with a saved delivery settles it without transport; a restart that finds an already-dispatched attempt but no saved delivery marks it uncertain and never resends it. A review hold is a durable resumable exploration state retaining the same attempt and packet. Rejection, confirmed-unsent denial and known provider failure are durable failed states; provider failure retains its saved delivery and settled accounting evidence. Ambiguous transport is a distinct terminal uncertain state retaining its request and any available delivery while the accounting liability closes further paid admission. These states replay their classification instead of redispatching. When a deterministic canonical-read or recipe failure terminates after an intermediate round was already settled, an idempotent accounting closure changes only an open operation with no reserved liability to complete; it cannot disguise uncertain, exhausted or in-flight work. Task instructions and constraints are versioned with the generation, not accumulated in one ever-growing agent prompt. Prefer a deterministic query for known context over spending a tool round to request it. Never expose arbitrary SQL, filesystem access, browsing or credentials.

The implemented immediate loop uses one structured task with captured state and deterministic proposal validation. The [memory proposal](../features/2026-09-18--20-09--storyteller-memory-and-recall/FEATURE.md) adds automatic retrieval and, when needed, bounded read-only discovery/inspection under the same operation and accounting boundaries. Other responsibilities may remain pure functions or focused one-shot calls. They cannot become competing authorities for story state. Temporal owns durable scheduling; PostgreSQL owns committed story facts. A graph library is warranted only when its bounded task logic earns that complexity. One agent per character or an LLM router per choice is not part of this POC.

The current consequence task has captured current prose, character, committed story state and receipts. It returns narration plus up to six fresh private action plans. The shared task contract owns authority, evidence use, mechanical boundaries and honest distinction between intentions; it does not impose one universal preference for momentum, quiet, danger, comedy or option count. Those creative defaults belong to the selected Storyteller profile, with compatible campaign direction able to refine them. Mechanical opening and consequence tasks select the canonical committed-time rule alongside mechanic-specific rules; assigning a duration is part of authorship and must not be inferred by copying the preceding menu. Task validation and publication independently admit those plans against captured state and evidence before publication atomically persists the passage, public offer and private plans. This input is not proof of complete historical context. Later targeted recall must solve missing evidence rather than merely add a no-op tool call.

## Supported behavior and evidence limits

The offline narrative pineapple rehearsal supports asking Gary, quiet breakfast, travelling to work, observing outside and returning home. It includes two contrasting profile examples, a remembered promise and real 20-second quick-play waits. The separate mechanical benchmark uses Gary and a suspicious rattling delivery to demonstrate that committed character/story facts change the next plan set. The microbe contrast uses the same task and admission contracts without human choices. Unknown mechanical seeds hold explicitly instead of receiving a generic “assess” action that pretends to understand them. Other narrative premises are saved but receive an explicitly unadapted rehearsal message. Waiting, reading history, reload and pause/resume require no inference.

Tests exercise structured boundaries, context retention, provenance, fake charges, replay and publication recovery. The consecutive browser flow still requires explicit acceptance evidence. They cannot establish whether a real model follows the profile, offers satisfying agency or sustains an enjoyable story. No live route, narrative quality or real billed-cost behavior is certified. Generated mechanical effects, multiplayer, automatic defaults, general interruptions, streaming and unlimited memory remain separate work.

## Mechanical POC boundary

The [rules/activity contract](rules-and-activities.md) implements generated opening plans, direct receipts, bounded emergent facts, genuine activity tick schedules, server-owned rolls/effects and one offline consequence DM turn that proposes the next actions. Consecutive browser acceptance and long-story retrieval remain unimplemented. [Settings revisions](story-settings.md) exist, while the definition/application tag contract remains incomplete. Isolate mechanical settlement from context-preparation failures before expanding task inputs. Explicit captured artifacts must retain their versions and meaning while referenced by active work; discarded prototype formats follow the repository lifecycle policy.

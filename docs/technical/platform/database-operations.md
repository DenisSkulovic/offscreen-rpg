# Controlled database operations | selected local-first contract

## Purpose and scope
One developer today, design suitable for a small team (~20). Ordinary app DML remains domain-owned; ordinary schema migrations remain @offscreen/db and tools/db-migrations, existing release Job unchanged. Exceptional data repairs, transformations and reconciliation use a reviewed operation catalog in tools/db-operations. No separate repo, no new application dependency, no arbitrary SQL shell, no forced use for every local diagnostic. Existing manual owner access remains available; agents do not gain live permission from this design. DBOPS01 remains owner of generator metadata reconciliation, mixed-version release/backfill integration and nontransactional DDL. DBOPS02 owns operational performance. Analytics pipelines and S3/Temporal cross-system operations are future scope.

## Hard local safeguards
Explicit DB_OPS_URL only, literal loopback endpoint, exact database and role, target confirmation and enrollment UUID, primary check. Loopback can forward to remote and clones copy UUID; this is accidental-target protection, not security attestation. Explicit enrollment creates separately owned offscreen_ops schema once, refuses existing schema, never auto-enrolls or adopts. This operational schema is not part of Drizzle domain registry; no app bootstrap changes. Operations use dedicated session and shared schema-migration advisory lock 683291351 (one bigint argument); cooperating migration and operation runs cannot overlap. The lock is held across all batches, not application writes. Source-only Git clean HEAD provenance, trusted explicit registry, no runtime plugin loading. Local actors self-asserted; no claim of authenticated approvals or signed artifact. High-risk execution refused initially. No automatic undo, reset, destructive data or ledger deletion. Recovery strategy required. All counts and checkpoints bounded/validated; one transaction for batch effects plus ledger checkpoint. Unknown COMMIT never automatically retried; inspect durable status then consciously resume matching artifact. Same operation key+version executes once per enrolled DB; changed SHA refuses even if same definition; deliberate reviewed new version or future artifact policy needed. Known failure may leave no durable failed atomic attempt; receipt returned to operator, not fabricated history. Audit events record committed progress, not independent immutable audit trail.

## Lightweight team practices
Operation definition declares identity, owner, risk, affected tables, kind, mode and recovery notes. Plan is read-only advisory, execution rechecks conditions; SQL code is trusted reviewed implementation, not sandboxed by TypeScript query wrapper. Use parameterized SQL, stable keys, CAS/row locks and final invariant check. No network/provider/file effects inside SQL transactions. Small atomic repairs <=1000 affected rows, batched limits 1..500 rows and 1..100 batches per invocation (default 100/20). Bounds on reported rows are contract checks, not a SQL workload sandbox. New writes during backfill must be compatible or final verification fails. Explicit resume only, no background daemon. Normal development access unchanged. Schema review provides historical integrity and lexical risk hints, human recovery/compatibility review; no automatic down, no rewrite of historical SQL. Source-tested offline inventory: `pnpm --filter @offscreen/db-migrations review:change -- --base <ref>` (`tools/db-migrations/scripts/review-change.mjs`); absence of lexical hints never means safe; DBOPS01 still owns generator metadata repair.

## Future hosted policy (documented, not enforced locally)
Dedicated scoped executor role, short-lived credentials/SSO through identity provider, protected branch approvals, approved immutable artifact digest, target environment binding, external protected audit receipts and break-glass access. No fake production profile, no local self-asserted actor treated as authenticated. Remote execution remains unsupported until actual deployment identity and grants are designed. Do not duplicate corporate IAM or approval workflow for one developer.

## Proof
Source fixtures first; actual SQL atomicity, lock contention, restart/unknown commit and recovery require separately authorized VER02-owned disposable PostgreSQL. Existing DB10/VER04/05 remain distinct. No live evidence or new product acceptance from this design.

## Ownership and dependency law

PostgreSQL is the authoritative relational store. The application remains a modular monolith with one application database and existing SQL names, cross-domain foreign keys and atomic transactions. Package ownership does not imply a new physical database, PostgreSQL schema, role grant or distributed transaction. The separate-service proposals in data-and-persistence concern a later deployment boundary, not this refactoring.

| Owner | Responsibility |
| --- | --- |
| @offscreen/db | Domain-neutral PostgreSQL connection configuration, pools, lifecycle, transaction primitives, admission, SQLSTATE errors, concurrency helpers, redacted telemetry and generic migration execution. No business tables or domain imports. |
| @offscreen/identity-persistence | Server-only Drizzle declarations for user, session, account, verification, rate_limit, terminal_device_pairing and terminal_access_token; authentication relations. No runtime DB dependency or public DTO. |
| @offscreen/story-persistence | Story Engine-owned schema-only leaf: drafts, generations, stories, campaigns, Launch and 20 Writer/Storyteller custody tables. Imports identity-persistence where foreign keys require it; no Story Engine runtime import. |
| @offscreen/admin | Staff principal/session, capability, audit, case and case-link tables in persistence/schema; Admin owns queries and authorized operations. |
| @offscreen/lab-support | QA run/stage declarations in persistence/schema; lab-only boundary. |
| @offscreen/outbox | Generic durable delivery table, enqueue and relay; depends on DB; no domain topic or business handler. |
| apps/api identity/terminal-auth | Better Auth composition and terminal credential persistence operations. Domain use cases keep existing authorization and token hashing. |
| tools/db-migrations | Complete explicit schema registry, Drizzle generator config and schema verification; depends on the domain declarations, never the reverse. Historical SQL and journal remain packages/db/migrations, the single ordered deployment asset. |

Schema leaves are owned by their named domains, not a replacement horizontal contracts package. Interface packages remain pure/public-safe; browser, deterministic Workflow runtime and SQL-free Writer executor may not import SQL schema leaves or SQL clients, even through a transitive runtime edge. The existing Story Engine remains the SQL authority for durable Writer capture, funding, dispatch, attempts and publication; pure Storyteller never imports it. No new generic ORM repository or table-by-table service abstraction. A query with domain authorization, lock order, join semantics, CAS, or idempotency is domain code.

A domain owns one declaration per SQL table and exports narrow server-only persistence entrypoints. Foreign keys import the canonical table object, not a duplicate declaration or a runtime domain barrel. Admin may join authorized Story/Identity tables; this does not grant write authority. A schema-only module is not itself a permission boundary. DB infra imports only external driver/ORM/validation and foundational utilities; it has no reverse edge to schema owners, migration composition, application or transport packages. CI checks actual imports, manifests, exports and restricted closures, including negative fixtures.

## Schema composition and evolution

Drizzle generation is performed by tools/db-migrations with an explicit list of source schema modules and one registry covering every table exactly once, including Better Auth relations. The registry and generator paths are reviewed together. No schema discovery via all workspace globs or importing application entrypoints. The untyped generic Drizzle connection stays independent of domain schemas; callers compose table objects explicitly. Better Auth receives its explicit identity schema object as before. Historical migrations and metadata remain at packages/db/migrations, and the generic CLI/runner takes a folder path. Existing deployment and dev-tenant paths stay compatible. The generation command points to the composition owner, not the DB package. No second journal.

Ownership extraction is source-only: table names, columns/types/defaults/nullability, keys, FK actions, index predicates, check SQL, policies, relation definitions and monetary units are identical. Preserve exact SQL and journal bytes. Compare canonical registry identities and generate against a disposable copy of a frozen current-schema snapshot with the pinned Drizzle version; zero extraction-attributable DDL, no modified history. When checked-in generator metadata is current, also verify against a copy of that metadata. Stale checked-in metadata refuses tracked generation until separately reconciled; the synthetic test baseline is not deployment history. A dropped table or changed default/FK must fail the identity test. Never apply a migration to establish that a source relocation is harmless. No permanent old DB schema aliases.

Migration execution uses a dedicated connection and the existing application session advisory-lock identity 683291351. A competing runner refuses rather than racing. Historical applied hashes and journal prefix are validated before DDL (existing Drizzle journal hash and created_at fields; no silent repair or rewriting history). Unknown, missing or changed applied entries stop. After verified DDL, success requires a second applied-ledger read while the same session lock is held: re-assert the applied prefix and require row count equal to the verified journal entry count; missing, extra, or changed hash/timestamp rows refuse success. The migrate CLI reports only allowlisted journal/applied/lock categories through a fixed safe formatter (no raw error text, DSN or SQL). A transactionally compatible migration commits its SQL and ledger together; failed SQL rolls back. Nontransactional DDL such as concurrent indexes requires a separately reviewed operator path, never automatic execution inside Drizzle's transaction. Lock and statement budgets apply; unknown commit outcome requires inspection, not blind replay. Release migrations use a dedicated role, runtime roles retain DML-only privileges as configured.

Expand → compatible app rollout → resumable bounded backfill → constraint validation → contract after old binaries and in-flight workflow readers are retired. No default destructive down migration. Backfills are domain-owned, checkpointed by stable keys, bounded by row/time/lock budgets, idempotent and separately authorized. Review generated SQL for locks, table rewrites, drops and type changes. DBOPS01 owns historical generator metadata reconciliation, actual mixed-version/interrupt/backfill evidence and risk review; DBOPS02 owns operational thresholds; DATAOPS01 owns backups/restore and SCALE02 HA. Source ownership alone proves none of these.

## Database runtime

createDatabase remains the compatibility entry and returns the untyped Drizzle client, bounded checkConnection, idempotent close and explicit managed execution entrypoints. Existing direct client use remains during incremental adoption; it is not represented as admission-controlled. One pool per process/workload configuration, not per request or domain. Existing defaults remain pool max 5, connect/acquire 5000 ms, statement 10000 ms, idle-transaction 10000 ms, idle connection 30000 ms. New managed defaults: queue max 20, acquisition budget 5000 ms, transaction budget 10000 ms, lock timeout 2000 ms; configured positive bounded integer values, lock <= statement <= transaction for managed policies. Runtime validates only safe config fields, never emits DSNs. Workload tags interactive, worker, admin, migration are closed categories; process composition selects budget. Pool totals across max replicas plus migration/operator reserve must fit PostgreSQL usable max_connections; e.g. 6 API x5 + 4 worker x5 + 10 reserve =60 planned connections, not measured capacity.

Managed admission uses a bounded FIFO with monotonic elapsed time; reject new operations after close, overflow typed saturated, queue deadline removes waiter before acquisition. Abort before admission removes waiter, after acquisition does not pretend SQL has stopped. Pool acquisition timeout is separate from execution; if late acquire completes after caller refusal, release client without running SQL. One permit tracks one actual checked-out operation until cleanup finishes, not merely caller timeout. No unbounded retries, no unbounded promise queue, no connection per transaction outside pool. Close stops admission, rejects queued work, waits for active cleanup, ends pool once; stuck work is reported rather than releasing live capacity or claiming shutdown success. No automatic process kill. Idle connection errors report safely; pool reconnects on demand; no mass reconnect loop. Health probe has its own bounded deadline and no business data. DB outage fails authoritative requests safely, never substitutes cache or fabricated success.

## Transaction execution and errors

The managed transaction helper runs a caller-owned SQL-only callback on a single checked-out client/Drizzle instance using explicit isolation (read committed default, repeatable read, serializable), read-only/read-write and local statement/lock/idle-transaction timeouts. The callback receives the existing Drizzle transaction type, not a second nested pool or a raw connection. Set local timeout via parameterized set_config in transaction; never leak session settings to next borrower. Deadline budget is measured monotonically, includes queue/acquire, execution and backoff. Server statement and lock deadlines actually constrain SQL; a JS timer is not evidence of cancellation. The helper checks remaining budget before callback and commit; callback must be short, cooperative and SQL-only. On deadline during callback, do not commit if callback subsequently returns; await settlement and rollback before release. No arbitrary network calls or sleeps in managed callbacks. No promise race that releases a client while SQL runs. Driver cancellation, if later supported and proven, must still await settlement. No claim of hard total interruption of arbitrary JavaScript.

Default retry none. Explicit sql-only-conflicts policy allows at most 3 total attempts for PostgreSQL 40001 serialization failure and 40P01 deadlock, after known rollback and fresh transaction; exponential jitter 25–200 ms within total budget. Do not retry constraint violations, lock timeout, query cancellation, auth/config, application errors or connection errors automatically. Retry callback reuses stable command IDs; domain must certify no provider, S3, email, payment, Temporal or other external effect and no irreversible in-memory effect. A connection failure after COMMIT is sent yields commit-unknown; do not retry; resolve via existing durable command/receipt identity. On rollback or connection failure, dispose tainted client, never return an active transaction to pool. Preserve original error cause internally; external error mapping belongs to domain/transport. SQLSTATE classification unwraps bounded Error.cause chains; only closed categories exported to logs. Integrity failures remain domain refusals, not generic retry.

Transaction handle is scoped to callback; do not retain or use after return. Existing Drizzle handle is not magically runtime-revocable: enforce lifetime via API discipline, lint/review and focused tests of managed helper; do not claim arbitrary escaped handles can be revoked. Nested work uses explicit caller tx or explicit savepoint; no hidden nested transaction. No ambient AsyncLocalStorage transaction or decorator. Outbox insertion uses the same tx as state change. Existing story locks, budget lock 714092631 then funding/run/attempt, no accounting→story lock, lease tokens, owner predicates and CAS are preserved exactly. Infrastructure offers explicit helpers for row-count conflict, transaction advisory lock and lock-order documentation; no generic business locking API or Redis authority. Transaction type moves from outbox into DB and has one canonical definition.

## Query performance and telemetry

Use bounded explicit page sizes and stable keyset cursors with unique tiebreaker, domain-owned filters and indexes. Prefer query plan and measured access paths over automatic indexes. No generic query retries or cache injection. Transactions are short; no object-store or model requests under story/accounting locks. Rebuildable read projections can use cache only after domain authorization and version preflight.

Telemetry is injected and failures are harmless. Stable registered operation names and workload, isolation, outcome, error category; no arbitrary strings, IDs, SQL parameters, DSNs, token hashes, prompts or raw SQL logs. Report acquire/queue duration, active/idle/waiting/queued count, transaction duration, rollback, conflict retry, unknown commit, timeout and rejection. Report query latency only for instrumented queries; do not mislabel transaction timing as per-statement timing or claim complete coverage of direct Drizzle calls. Use monotonic timers and bounded label sets. Health metrics do not decide business authority. DBOPS02 joins these application metrics with authorized PostgreSQL statistics, lock waits, slow plans, vacuum/wraparound, bloat, WAL, disk, lag and capacity. EXPLAIN ANALYZE only on safe disposable data or explicitly authorized read-only workloads; no production mutation or maintenance inferred.

## Local CNPG topology (selected 2026-11-25)

Dev and release share the PostgreSQL chart, typed topology rendering, explicit instance reconciliation and readiness predicates. Default baseline identities and one-instance profile defaults remain unchanged. Baseline cluster names are `dev-pg` (dev) and `lab-pg` (release) in INF53. Instance count means total PostgreSQL instances including primary, a positive safe integer subject to CNPG API and resource admission, not a fixed enum. Normal stack ensure (`install.sh`, dev CNPG bootstrap) creates the baseline from its profile and reuses existing compatible topology without implicitly scaling it back. Only explicit topology `ensure` changes an existing count. Shared dev baseline resize is reserved for the human owner with operational confirmation, not ordinary agent stack commands; existing SQL tenant grants and endpoint identities stay unchanged.

Explicit local topology command:

```text
pnpm infra:postgres <plan|ensure|status> \
  --env dev|release --cluster NAME --instances N \
  [--owner RUN_ID] [--confirm-context CONTEXT] [--allow-scale-down] \
  [--json]
```

Baseline `--cluster` names are `dev-pg` (dev) and `lab-pg` (release) and refuse `--owner`. Independently named clusters require `--owner RUN_ID` (lowercase DNS label, 1–24 characters) and live in namespace `offscreen-pg-<ownerId>` with profile owner labels plus `offscreen.rpg/pg-experiment=<ownerId>`; see [INF54](../../../work/changes/archive/2026-11/platform-operations/2026-11-25--inf54-postgres-owned-clusters/CHANGE.md). Owned renders clone the pinned baseline chart document and replace only metadata name/namespace/labels; image, storage, bootstrap and resources stay profile-owned. Absent owned namespace/cluster objects are created with `kubectl create` only (never apply or adopt on conflict); existing owned clusters must match experiment owner and pin/bootstrap/storage identity, then reuse INF53 compare-and-swap `spec.instances` patching. `plan` and `status` are read-only. `ensure` requires `--confirm-context` equal to the profile kubectl context name (`kind-offscreen-dev` or `kind-offscreen-release`). That confirmation is **operational authorization** to mutate local topology on an already-selected context, not proof of Kubernetes RBAC identity. `ensure` also requires a matching owned target, healthy starting cluster when the count changes, and `--allow-scale-down` for any reduction. Use one chart and one topology reconciler, not separate environment implementations. Baseline creation remains existing bootstrap responsibility. Existing-object scale uses only `spec.instances` via compare-and-swap JSON patch testing UID/resourceVersion; no deletion/recreation, no forced adoption, no auto-retry on conflict or unknown write result. Refuse nonhealthy starting topology for changes; identical requested spec may wait for convergence. Ready requires observed desired count, ready count, actual instance count, current primary and healthy condition. Async replication remains default; no zero-loss claim. CNPG may remove retired standby storage on scale-down; do not manually delete claims or promise standby PVC preservation. Preserve cluster identity and data; no rollback by deleting resources. INF53/INF54 source proof and owner live acceptance are recorded separately; this section is not HA, backup, or failover acceptance.

New resources require capacity admission: preserve 4096 MiB host headroom plus incremental configured per-instance memory limits; fail on unreadable memory or insufficient capacity, leave scheduler/storage enforcement active. Report requested total and incremental CPU/memory/storage, no arbitrary low topology cap. Default profile limits stay unchanged. No production availability claim.

Independent clusters are isolated datasets, not application shards. No data redistribution, routing, connection-string changes to ordinary workloads, or cross-shard transaction semantics. Dev experiments use fresh run-owned namespaces, not shared dev-pg or tenant namespaces. Release may use same isolated experiment mechanism. Removal from configuration or count changes never delete an independent cluster implicitly. Explicit cleanup of disposable experiments belongs to owned resource lifecycle with UID fencing; no broad namespace or PVC deletion by topology ensure. SCALE02 retains application HA, RPO/RTO and backup/restore acceptance.

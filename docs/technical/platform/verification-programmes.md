# Verification programmes | infrastructure, packages and apps

Selected owner direction 2026-11-25. Baseline 0c45ae7318295398d706511b9d702720a55c8a92. A programme is a permanent, executable attempt to falsify the documented operational guarantees of a subject. Unit tests are complementary, never a substitute for live evidence. The subject owns the assertion; dependencies supply resources, not ownership. This is engineering verification, not a new game Lab runtime.

## One entrypoint and one execution model

`pnpm verify list`, `pnpm verify <infra|package|app> [name] [--profile <id>] [--section <id>] [--plan|--live] [--json]`. Infra subject is unnamed; package/app name is exact workspace directory basename or exact manifest name (resolve once, reject ambiguity). Unknown option/profile/section, repeated flag, plan+live, unsupported combination: exit 2 before side effects. Default package/app profile standard; infra diagnostic. With no --live, source sections execute and live sections are NOT-RUN (exit 1 for incomplete selected run); --plan is always read-only and exit 0 for valid plan even when resource unavailable. --live is the explicit per-run authorization for only declared disposable resource actions; no production, arbitrary URL, repair, provider inference, user data, or pre-existing tenant mutation. --json emits one final JSON report to stdout, progress stderr. Existing pnpm infra:verify --suite source/diagnostic and provisioning commands remain compatible. No migration of active INF51 files in first wave: adapter invokes existing CLI and preserves its reports/evidence, never equates successful diagnostic with live acceptance.

Permanent home tools/verification/ (private tooling workspace, not production dependency): runner/ (CLI/catalog/planner/executor/report/subprocess), resources/ (adapters), suites/infra/ (adapter), suites/packages/db/ (manifest and scenarios), suites/apps/ (future). Discovery lists actual package/app workspace manifests (no recursive arbitrary imports); explicit static suite registry, unimplemented subjects report NOT-IMPLEMENTED rather than empty success. New package/app suite registers explicit manifest; no duplicate runner. Subject-specific tests remain with subjects; programmes orchestrate built public entrypoints and real dependencies, never import private implementation internals to prove public guarantees. Resource adapters are generic and own creation, readiness, identity, cleanup. Infra implementations stay in infra; tooling consumes their safe entrypoints. Existing diagnostic-engine executeChecks/runCommand provides semantics and bounded child process design; initial runner uses it for common ordered check execution without editing active infra branch; do not create another test discovery engine. When INF51 settles, optional consolidation of shared primitive ownership may be separately planned, not duplicated by assumption.

## Declarative contract

Manifest (ESM static data) {schemaVersion:1,subject:{kind,id},defaultProfile,profiles:{id:ordered section IDs[]},sections:[{id,capabilities:string[],tier:'SOURCE'|'FIXTURE'|'LIVE',requires:string[],resources:ResourceRequirement[],scenarioIds:string[],timeoutMs:number}]}. Registry references explicit scenario module functions, not dynamic user-supplied paths. ResourceRequirement {kind:'postgres' initially,profile:'single'|'constrained'|'replicated'|'dual-replicated',count:1|2,access:'owned',faults:[] or closed enum ['restart','backend-terminate','primary-loss'],limits:{memoryMiB,cpuMillicores,storageMiB,maxConnections}}; other future adapters add validated resource kinds. Each section names resources and budgets; plan computes per-section and peak sequential budget (not sum), never starts unused services. Unknown dependencies/cycles, duplicate IDs, unsupported resource combinations, unbounded time/size/fault settings reject. Explicit order is topological and stable. Independent sections continue after failure; dependent ones BLOCKED with exact prerequisite. Distinct evidence tiers never promoted. Every selected scenario yields PASS/FAIL/BLOCKED/NOT-RUN/TIMEOUT, cleanup separately. Run selected groups serially by default, parallelism only within bounded scenario; no parallel resource topology. Source profile no resources. A failed cleanup is failure even when assertions pass. Empty results never pass.

## Execution, safety, evidence

Runner creates private .offscreen/verification/run-<random>/report.json with schemaVersion, runId, source HEAD/dirty, subject, profile, selected sections, resolved resource plan, start/end, complete, scenario rows with tier/status/duration/assertion IDs/typed measurements/expected versus observed, topology actual facts, cleanup ledger, child report pointers. Atomic temp+rename after each result; no raw exceptions, SQL, env, credentials, DSN, arbitrary console or child stdout persisted. Allowlisted numeric counters, durations, category and static reason codes; sanitize identifiers and bound sizes. Exit 0 only if every selected required scenario and cleanup PASS, 1 failed/incomplete, 2 invalid/refused invocation. On SIGINT/SIGTERM stop new sections, terminate only owned child groups, cleanup in reverse order, mark unstarted NOT-RUN, incomplete if interrupted. On crash retain private owner receipt and manual recovery instructions; never auto-adopt stale resources. Use process groups on Linux/WSL; refuse live on unsupported host when ownership cannot be proven. Never promise an arbitrary callback deadline is a SQL cancellation. No unbounded waits. No Docker prune, broad kubectl deletes, reset-test-db, shared deployment changes. Explicit run identity, resource identity and cleanup proof, no reliance on name alone. Missing dependencies BLOCKED, not PASS. Store historical report paths, not secrets; no Git tracked report artifacts.

## Subject ownership

Infra/PostgreSQL tests installation/operator/storage/readiness/replication/failover as infrastructure. Package/db tests public @offscreen/db client, config, managed admission, managed transactions, migrations, telemetry, concurrency against PostgreSQL. No Redis. Package/cache tests memory (none), distributed Redis, and optionally Redis + PostgreSQL origin; SQL remains supporting dependency. Package/documents and object-storage test their contracts with relevant object store. App/api tests HTTP/auth and real dependencies; app/worker tests durable execution. All unknown/unimplemented subjects appear as such. No global full-stack startup by default. No automatic expansion into other package suites.

## DB topology and limits

Single: dedicated local Docker PostgreSQL 17.11-bookworm (existing pinned tag infra/platform/temporal/images.pin and infra/images/release/test/pod-bind-smoke.test.mjs); record actual resolved image ID/digest, do not claim parity with CNPG PG18.7. Constrained: same image, max_connections 20, 384MiB RAM/0.5 CPU; standard single 100 connections, 768MiB/1 CPU; tmpfs 256MiB data, no persistent external volumes; explicit disk/memory preflight, sequential runs. Multiprocess: same server, three independently created Node processes, pool max 3 each, observer reserve two; demonstrate bounded per-process admission and aggregate observed sockets, not a global admission controller. Replicated: isolated CNPG Cluster (one primary, one standby; instances=2) in fresh run-specific namespace on existing verified local dev Kind context, operator already ready, no base cluster mutation. Dual-replicated: two such independent clusters in that namespace (four PostgreSQL instances total); explicit independent endpoints; no shard routing or distributed transaction guarantee. Allow only bounded memory/CPU/storage profile and preflight headroom; no fallback to shared dev PG. Existing normal chart hardcodes instances=1; topology adapter uses strictly typed copy of rendered dev Cluster document and replaces name/ns/labels/instances/storage/resources/bootstrap only, preserving pin and explicit validated allowlist. Do not alter release/dev chart or installer. CNPG uses asynchronous replication by default; verify WAL replay barrier before primary-loss test, do not claim zero loss for unreplicated writes. Temporary forwarding interruption is separately reported; do not attribute transport restart to database package. Fault authorization only within chosen live topology profile. No provider calls.

## DB guarantee matrix

Standard sections admission, transactions, migrations (single, no Redis). Stress sections admission-stress, multiprocess, constrained (single/constrained). Recovery sections connection-recovery, shutdown, transaction-fault (single, owned faults). Topology sections replicated, dual-replicated (CNPG, optional if unavailable -> BLOCKED). Full includes all in declared order. Source includes package source tests and schema check, no live claims. Public API from current DB07: createDatabase(config,onBackgroundError), readDatabaseConfig, withClient, transaction(policy,callback), checkConnection, close, db legacy escape hatch, @offscreen/db/migrate applyMigrations; DB09 will add public telemetrySnapshot and concurrency helpers. DB legacy direct client not managed; test and report this explicitly. No automatic domain adoption. DB10 keeps component acceptance and graph closure; programme reuses its compiled component tests in dedicated fixture, then adds workload/recovery and topology evidence. DBOPS01/02 remain mixed-version/backfill and operational capacity owners; not silently closed by these experiments.

Every run reports an explicit coverage table: documented guarantee, scenario, topology, tier, observed outcome and limitations. Latency p50/p95/p99/max, throughput, errors by closed category, accepted/rejected/completed counts, connection/queue maxima, cleanup/recovery duration; retain bounded sample arrays or histograms; no unbounded load or universal SLO inferred. Deterministic invariants required; performance measurements descriptive unless an explicit configured bound is a correctness guarantee. No production performance extrapolation.

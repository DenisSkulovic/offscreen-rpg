# Implementation overview

This is the current project snapshot. Replace statuses and next steps in place; keep history in Git. Product documents define the experience, technical documents define the intended behavior, and tests establish what the implementation actually proves. A component passing tests does not make its whole user flow complete.

**Current phase:** build and connect the application using scripted generation and local/test substitutes. Paid models, paid media and paid hosted integrations remain deferred until the broader application is implemented and exercised, and the user explicitly chooses to enable them. OpenRouter credentials are now stored locally, with $10 intended to last at least a month and a strong preference for no-LLM tests or dirt-cheap models. No live adapter or budget enforcement is enabled. Before deliberate live evaluation, implement the safeguards in [spending](technical/context-and-cost.md#current-development-allowance); ordinary tests remain entirely scripted.

## Next milestone: a persistent scripted testing chamber

It is not too early for a testing chamber. It is the next integration target, not a reward after building the whole product. The existing `/demo` proves presentation only; saved opening previews prove creation and background execution only. The chamber now supports a short branching conversation, saved consequences, reopening and chronology. The timed cafe visit now waits and arrives while the page is closed. Journey pause/resume preserves remaining time; a separate timed reply has a deadline and default. A letter fixture also commits one item transfer with its scene. Pace changes remain absent. Neither presentation nor persistence alone makes it a playable story.

The foundation available for reuse includes identity/ownership, revision-checked drafts, stored scripted previews, PostgreSQL transactions, an outbox/Temporal worker, scene presentation and automated browser tests. Docker, PostgreSQL and Temporal now run locally. The local database suite passed 9 checks and the application integration suite passed 32 checks covering identity, drafts, previews, chamber initialization and browser branching, HTTP response authorization/retries, continuation retries/races, authoritative answer validation and paginated history (including a concurrent append); these include a real 20-second interval, early-completion rejection, pause across browser closure and worker restart beyond the original deadline, resume and one saved arrival. Duplicate controls cannot reapply an earlier pause after resume. Deadline checks cover an early timeout, accepted-answer retry after expiry, competing default deliveries with a late player response, and a real 15-second browser-closed timeout through Temporal. Item checks cover browser delivery/reload, duplicate transfers, initialization retry after transfer, effect-list rollback, story isolation and rejection of client-supplied effects. They do not prove shared deadlines, pause during inference or a general game calendar.

Aim for one short solo story using authored text and options with real identifiers and validated effects. The player should start it, make a consequential choice, wait, pause/resume, miss a response deadline, reopen the browser and reach a saved ending. No model or paid service is needed. A small developer inspection area should expose committed state and timing so we can see whether the prose agrees with the data. The scenario and fixture policies are defined in [delivery and validation](technical/delivery-and-validation.md#scripted-testing-chamber).

### Distance to the scripted SpongeBob POC

The cafe fixture already proves the core shape: choose departure, wait with the page closed, arrive and choose a joke. The literal authored SpongeBob example does not require completing the broader MVP. The local authenticated launcher is implemented and its headless smoke check passed: fixture play, item transfer, reload, anonymous rejection and clean shutdown. An authored ten-real-minute trip with a full real-time acceptance run and reopening at arrival remains. This is a bounded task, not a tested completion estimate. The current in-memory `/demo` is not that persistent run.

An item-transfer fixture provides additional state evidence but is not a prerequisite for driving and telling a joke. Generated worlds, long-term memory, multiplayer, maps, notifications, sponsored usage and hosted delivery are separate later milestones. Describe the initial result honestly as an authored scenario. A prompt-generated SpongeBob story needs the playable storyteller/context contract, generation-to-commit integration, spending enforcement and explicitly bounded model evaluation. The existing AI component produces opening prose only. See the [live POC acceptance boundary](technical/delivery-and-validation.md#first-live-story-poc-what-the-run-must-mean); the launcher does not close these gaps.

### Target before enabling models

Use a scripted acceptance journey inspired by the player's SpongeBob example: begin at home, choose to drive to a restaurant, remain in transit for ten real minutes, arrive, then tell a joke to a known character. Closing the browser must not cancel travel; reopening must show the same journey or its committed arrival. Pause/resume and a duplicate response must preserve one coherent outcome. Content and place names belong to a replaceable fixture, not a SpongeBob-specific engine or universal driving mechanic.

Run short waits in routine tests and the full ten-minute case as an explicit real-time acceptance check. The cafe fixture exercises a 20-second real wait; the full ten-real-minute acceptance journey remains to run. Before enabling models, also exercise notification intents, context assembly and simulated spending, shared-play authority, and recovery through the defined broader passes. A future small OpenRouter allowance is for a deliberate evaluation near the end of shaping the MVP; it does not authorize paid calls now.

### After the chamber

The chamber is an integration milestone, not the full MVP. Next extend it in balanced passes with a second participant, broader continuity, absence policies, returning/recap, notification intents and simulated usage limits. Include a scripted 30-day quiet-life fixture: recurring routines, accumulated conversations and source-backed recognition of an early acquaintance after many irrelevant exchanges. Include uneven narrative chapters and a minor encounter becoming significant later when evaluating recaps. This tests memory selection and data growth without waiting a real month or enabling models; it does not replace real-time scheduling tests. Real notifications, map visualization, procedural world generation, rich inventory/economy, hosted deployment and Kubernetes are not prerequisites for the first run. Actual model quality and cost can only be evaluated later, when external services are explicitly enabled.

General agency, pacing, risk and multiplayer policies remain open in [questions](questions.md). We can use visibly declared fixture policies to exercise the plumbing without pretending they settle the product. Resolve the affected contracts before each implementation slice and update these statuses in place as evidence arrives.

### 07. Source review and important corrective findings

**Observed/reviewed:** Next 16.3.5 / React 19.3.0, App Router server routes with private no-store Nest reads, strict Zod DTOs, owner-checked Nest endpoints, React client feature screens, Play/Chamber polling, forms/list pagination, integrated Playwright tests, existing GitHub Actions/strict TypeScript. The existing architecture has legitimate strengths: do **not** rewrite it just because the code is agent-authored.

**Findings changing the earlier seven-slice plan:**
- `OpeningPreviewPanel` reuses a Start story UUID after uncertain completion but rebuilds the campaign/preview body from current UI inputs. A retry with changed settings can carry a different payload under the same operation identity; a frozen Start envelope/reload contract merits a new Change, not a generic “clean up”.
- `PlayScene` and `useCampaignCommand` have in-memory stable UUID refs, but those are lost on reload. The UI must distinguish refreshing server-owned progress from guaranteed replay of an original intent. Never promise exactly-once from browser state alone.
- `preferNewerSnapshot` compares version numbers without verifying story identity; Play/history/settings have distinct remount, late-response and unsaved-data risks. Source shows missing guards/potential failure paths, **not** a reproduced cross-user leak.
- `SessionRefresh`, SSR cookie forwarding and same-origin Nest reads are valuable, but deployment rewrite and actual private RSC/router-cache behavior have not been proven. Story list fetch currently serializes two independent initial reads.
- `CampaignPlay` is large but not automatically wrong; stronger evidence is ownership coupling and preview importing a Play Client module only for pace constants.
- Lists/history differ in replace/append and abort policies; campaign settings are keyed by revision and may lose local drafts; QA run ID browser hint is not auth and should be viewer-isolated.
- Chamber Nest tools currently require authenticated ownership, **not a distinct developer-role check** in the inspected controller. Whether Chamber is local-only/self-service/restricted is a product/security deployment decision; hiding UI cannot secure the endpoint.
- Fast web-local component/race tests do not exist, but real integrated browser tests, CI and strict TS already exist. Preserve and layer those proofs instead of replacing them.

**Verification limit:** GitHub read-only source and tests inspected; no repository executable checks, browser, DB, proxy or live provider run. Potential impacts and proof needs are recorded in the new audit.

### 08. Proposed architecture and alternatives, not automatically approved

**Proposed recommendation:** Server-first Next App Router, per-request authenticated Nest readers, client islands with resource/viewer-scoped controllers, one snapshot reconciliation owner, typed immutable command envelopes and endpoint-specific recovery, bounded refresh lifetimes, local form state and defined pagination. Shared pure boundary policies only where materially common; strict module and client/server dependency direction; accessible loading/failure paths; provider-free tests at the cheapest truthful level.

**Professional alternatives explicitly assessed:**
- TanStack Query for **reads** remains a credible later choice if multiple independently mounted readers and cache invalidation justify its complexity; it is not dismissed as inferior and not automatically installed now.
- A global entity store/Redux, universal `send(anything)` dispatcher, immediate SSE/WebSocket, sweeping Next Server Action migration, new CSS toolkit, and splitting every long component are not justified by present measured needs.
- In-browser persistence of **all** pending operations is rejected as an indiscriminate replay/privacy strategy. For the specific Start flow, a minimal short-lived, viewer-scoped, nonsecret sessionStorage envelope plus URL ID may allow same-payload retry after authorized GET-first reconciliation; storage is never authority or permission to auto-submit.
- 'Do nothing + add a test' remains a valid outcome when an apparent issue is disproved. Security/Next cache and cross-tab behavior need browser/contract evidence before anyone claims a live defect.

**Status:** agent-proposed design for owner review, not human-approved final architecture. Important owner choices remain the exact tolerance for reload-unknown command outcomes, Chamber exposure, and approval of the broader target.

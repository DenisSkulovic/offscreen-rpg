## Running minutes

### 01. Start from an effective development system, not another gameplay feature

**Owner direction:** The existing Offscreen RPG repository was largely built through AI coding tools, including periods of ad hoc phone-driven development. The immediate question is how to turn it into a **reliable, professionally maintained AI-assisted engineering process**, not how to add another mechanic. The owner wants this repository to be useful for career development and serious code review, not simply to contain many generated files.

**Rationale retained:** Raw model intelligence and a long context window are insufficient. Important design criteria, domain-specific gotchas, conventions, architectural reasoning and constraints are lost or glossed over when absent from an agent's supplied context. This is a **harness / knowledge-interface problem**. Work should focus on reusable instructions, targeted skills, reference manuals, coherent knowledge ownership, careful context use and good handoffs.

**Emerging collaboration pattern:** ChatGPT is best used for creative/strategic architecture and authored specifications; Claude Code for source-grounded exploration, technical design and independent critique when it adds value; Cursor for economical, bounded code implementation. These are flexible roles, **not mandatory steps on every trivial edit**. Measure total cost of a correct result, including the owner's attention, rather than token count alone.

**Artifacts:** [AI development system](../engineering/ai-development-system.md), [coding-agent target standard](../engineering/coding-agent-target-standard.md), [harness architecture](../../.agents/HARNESS.md).

### 03. Layer-zero instructions and context economics

**Decision:** Keep the always-on agent entry very small: [`AGENTS.md`](../../AGENTS.md) for invariant boundaries and task routing, [`CLAUDE.md`](../../CLAUDE.md) as a thin import, Cursor's task-matched rules and shared [`.agents/skills/`](../../.agents/skills/) for selectively loaded procedures. Do not duplicate the full manual in every model/client configuration.

**Key design concern:** Agent context should be loaded by question and trigger. The owner wants **lower context consumption without lost correctness**: navigate `README` → owning docs → relevant source symbols/tests, stop when the question is answered, and preserve findings in durable homes so the next agent does not rediscover them. Skills should carry **nontrivial procedures or special expertise**, not hollow "check best practices" advice. Subagents and independent reviewers cost context and must justify themselves.

**Actual work:** layer-zero rules, context-economics reference, conditional skills and real-client discovery checks were committed. **No measured cost reduction was established**; validation in fresh Cursor/Claude sessions remained a future action.

**Sources:** [Harness](../../.agents/HARNESS.md), [context economics](../../.agents/references/context-economics.md), [coding-agent evaluation](../engineering/coding-agent-evaluation.md).

### 04. Documentation architecture should answer questions before agents read code

**Owner direction:** First design the **ideal end-state information architecture** independently of the existing docs. Then audit actual navigation, ownership, cross-references, stale claims, oversized pages and retrieval friction. Important content must survive; do not delete unique design reasoning just to shorten files.

**Agreement:** Product documentation defines `what/why`; technical contracts define authority, state transitions and failure semantics; source/tests describe what is implemented and exercised; historical POC/evaluation records report evidence. Indexes route by **question and heading**, not just filesystem directories. Large coherent contracts are acceptable when navigable. Do not treat a historically successful fixture as proof of current end-to-end behavior.

**Actual result:** `docs/README.md`, technical and engineering area routers, package READMEs for web/API/worker/shared packages, code navigation and in-page technical guidance were improved. A fresh agent should be able to find the owning contract before modifying current code.

### 05. Roles, authority and handoffs, instead of an "agent parade"

**Owner concern:** Tools frequently miss relevant perspectives when the prompt names a task but not the roles/criteria needed to evaluate it. For a major decision, a UX architect, frontend engineer, test strategist and critical reviewer may uncover different problems, but spawning all of them automatically is wasteful.

**Decision:** Define responsibility by **role**, procedure by **skill**, and context/tool by independently chosen sessions/agents. Use explicit output contracts and handoff receipts: which decision the role owns, affected canonical docs, source anchors, constraints, negative case, proof and what the next agent must do. Return a contradiction to its owning decision maker instead of allowing Cursor to improvise new product policy.

**Actual result:** role catalog, assignments and a UI-focused example; two **optional, read-only** native specialist agents for design challenge and test strategy. Their presence in configuration is **not proof** that client discovery or delegation has been tested. An independent reviewer must add a credible alternative and a failure case, not praise.

**Artifacts:** [Role catalog](../../.agents/roles/catalog.md), [handoff contract](../../.agents/roles/assignments.md), [Cursor handoff](../../.agents/skills/cursor-handoff/SKILL.md).

### 06. Professional knowledge must be substantive, cross-disciplinary and selective

**Owner direction:** Do not build only narrow lists of React errors or other superficial "gotchas". An agent needs access to serious professional reasoning: the space of possible designs, trade-offs, relevant framework semantics, risks, maintenance costs and criteria that would reverse a recommendation.

**Actual library created or integrated:** React state/Effects/async correctness; architecture options; durable operations/consistency; interface art direction; security/trust; API/network contracts; testing/evidence design; observability/production diagnostics; data modeling and safe migrations; caching/performance; release and deployment engineering. Specialist review skills and an adversarial scenario laboratory route to them. These are **coding-agent references**, not instructions to the in-game Storyteller.

**Key rule:** Activate relevant sections **before a significant domain decision**. Usually one main knowledge manual and perhaps a second for a real boundary crossing, **not a mandatory dump of all manuals**. Executor receives accepted invariants and decision factors; it need not reread a 15 KB knowledge pack merely to type JSX.

**Artifacts:** [Knowledge index](../../.agents/knowledge/README.md), [scenario lab](../../.agents/knowledge/scenario-lab.md), [expert routes](../engineering/coding-agent-knowledge.md).

**Finding:** 13 old paired dossiers (`FEATURE.md` and `PLAN.md`), approximately 310 KB combined, were not 13 ready-to-implement tickets. ### 08. Define `Change` precisely; preserve richer initiatives elsewhere

**Agreed definition:** A **Change** is one cohesive, independently verifiable **future code-bearing** outcome. Actual execution modifies application/library source, tests, scripts, executable schemas, migrations or meaningful runtime/build configuration. It need not be a product feature. Bug fixes, refactors, security corrections, performance improvements, developer tooling and technology additions may qualify.

**Explicit exclusions:** A design debate, research, documentation-only fix, QA/playtest or architecture assessment with **no planned executable delta** is not a Change. An **Initiative** may span several Changes and evaluations; an execution slice is one ordered part of an approved Change. A tiny localized coding task need not generate a bureaucratic new dossier.

**Required Change evidence:** outcome, governing product/technical authority, grounded source baseline, smallest intended diff/exclusions, normal **and discriminating negative** acceptance, permission/spend boundaries, status and next step. "Proposed" does not mean "Ready" or "Implementing." Final completion requires an actual diff and verification; retire temporary execution packets after preserving permanent design/evidence.

**Artifact:** [Work-unit standard](../../.agents/references/change-work-unit-standard.md), later [change-workflow skill](../../.agents/skills/change-workflow/SKILL.md).

### 11. Major strategic reversal: portfolio engineering, not startup/product delivery

**Owner direction, emphatic:** No gameplay feature development for the foreseeable future. First fully refine the agent ecosystem and Change workflow. Then plan expert-led refactor/improvement campaigns, use Cursor for numerous source changes, and only later optionally resume actual gameplay work.

**Why:** The owner is looking for a **developer position**, not acting as a product manager or trying to onboard real paying players. The repository's purpose is to show prospective employers what high-quality **professionally directed AI-assisted development** can produce. The owner does not need to have manually written every line; they do need to understand, select, review and defend the architecture and its correctness. "Vibecoded gold" should replace a partially inconsistent AI-generated codebase.

**Portfolio candidates:** React component/state quality, Next.js rendering and server/client boundaries (**Next already exists**), backend/Nest architecture, independent UI/UX and art direction, database discipline, tests, security, event/realtime behavior and operational practice. RabbitMQ, Redis, SSE/WebSockets and other technologies are **choices to justify**, not compulsory CV ornaments. Code quality and visual polish are **different engineering/design tracks**.

**Explicit deferral:** Shipping richer fishing/time/gameplay, 10–15-turn sustained memory proof, monetization, multiplayer, user growth or new product capability is not the current mission. Do not try to "finish the game" while preparing the engineering portfolio.

### 13. Owner insisted on a target-first redesign philosophy

**Owner's decisive objection:** Merely inspecting a messy codebase and performing directionless "make it less bad" baby steps produces low effectiveness and endless thrashing. They will accept **small implementation steps only when those steps approach a clear final end state**.

**Agreed process:** Define the **intended excellent destination** as an architecture/design target; then inspect the current code as evidence of the gap; then select verifiable, dependency-ordered **Changes** that converge. A code smell is not a roadmap. Reject modernization plans lacking target criteria, independent expert knowledge, a real alternative and negative proof. Revisit a target only through an explicit design decision, not by lowering expectations to fit existing implementation.

**Strong owner requirement:** Agents preparing audits/Changes must actually use the repository's established **rules, skills and professional knowledge**. Do not commit the very error the harness was designed to prevent by ignoring relevant criteria simply because the immediate prompt didn't enumerate every one.

**Artifacts:** [Target-first rule](../../.agents/rules/target-driven-renewal.md), amendments to [root agent entry](../../AGENTS.md), [Change workflow](../../.agents/skills/change-workflow/SKILL.md) and [Change template](../../.agents/skills/change-workflow/assets/CHANGE.md).

### 14. First complete target: React 19 / Next.js 16 engineering

**Destination defined first:** Proposed [React/Next target](../engineering/targets/react-next.md) with ten `F1–F10` criteria: server/client rendering; authenticated/private API boundaries; state and identity ownership; monotonic resource-scoped snapshot reconciliation; recoverable idempotent mutations; intentional refresh/polling and future live updates; cohesive screen/component boundaries; form/draft editing consistency; accessible/loading/error recovery; and focused tests, performance evidence and maintainable source.

**Architectural preference:** Keep the existing Next.js + Nest arrangement as the base. Server-render useful private initial projections, hydrate interactive islands, maintain **one server authority** and a clear client identity/version owner. Use small feature-owned controllers and genuinely shared primitives. Avoid defaulting to Redux, an all-purpose cache, a new message broker or a generic client framework before evidence demands them.

**Important constraint:** React/Next engineering **is not the same as UI visual/art direction**. A separate design target will eventually address hierarchy, aesthetics, typography, responsiveness and interaction language. No screenshot or theme adoption can substitute for correct command and state lifecycles.

**Target status:** **Proposed for owner review**, not yet a completed product specification and not implementation permission.

### 15. React source gap audit, performed after the target was committed

**Inspected baseline:** [React/Next audit](../engineering/audits/react-next-gap-2026-11-11.md), grounded in the tracked `apps/web/` files, Next/React manifests, shared transport, Play/creation components, relevant Nest controllers and existing API/Playwright integration test sources.

**Existing strengths, not to discard:** Actual Next Server Component routes with `cache: no-store`, Better Auth/Nest session boundaries, Zod contract validation, a `preferNewerSnapshot` version guard, stored retry operation IDs, draft revision conflicts and meaningful browser integration tests. The source is uneven, **not devoid of functioning architecture**.

**Highlighted gaps:** snapshot comparator compares versions but not resource identity (missing guard, **not proven cross-story leak**); multiple Play/Chamber/preview polling and request/recovery implementations; scattered SSR fetch/error semantics; campaign rendering with mixed responsibilities; absence of focused web-local component/async race proof and production render/visual acceptance. Some protection may come from actual Next remount behavior; a discriminating browser test is needed before claiming a user-visible bug.

**Verification honesty:** Source/docs were inspected, and static link/tree checks were used. **No local web build, unit test, Playwright browser, CI run, profiling, DB reset, provider call or deployment was executed for this planning audit**. The existing full-stack browser suites were **read**, not run.

### 17. What a future fresh chat/agent must preserve

**Current instructions to carry forward:**

1. **Do not work on game content or new gameplay** unless the owner deliberately changes strategy.
2. **Do not run into source first and optimize randomly.** A selected target precedes a gap audit; each Change traces back to a named target criterion and proof.
3. **Do not ignore expert manuals, skills and rules.** They must influence audit and design, not just decorate the repository.
4. **Do not confuse the presence of a packet with coding permission.** The [Change index](../changes/README.md) explicitly says `none`; S3a is parked and W01–W07 are Proposed.
5. **Do not claim "production-grade" or test success on source inspection.** Build and runtime claims need actual evidence.
6. **Do not buy a new architecture by installing fashionable libraries.** Compare alternatives and preserve useful current code.

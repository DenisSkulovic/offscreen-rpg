# ChatGPT | architecture planning and Cursor handoffs

Follow [AGENTS.md](AGENTS.md) for integration trunk, implementation/acceptance ownership, safety and lifecycle. This file owns planner-specific discovery and handoff.

## Design before packets (owner decision 2026-11-26)

For material new architecture, infrastructure or domain renewal, follow the [design-led engineering procedure](.agents/rules/target-driven-renewal.md) before implementation planning. Select posture, respect excluded source, investigate real requirements and upstream behavior, make specimens and discriminating experiments, settle the integration map and verification architecture. Start substantive work in the first turn of an authorized workshop; persist actual findings at the first substantive checkpoint and verify the commit. Explain decisions and evidence to the owner. No automatic implementation or ratification.

Apply the [submission standard](.agents/references/planning-artifact-quality.md) to both Designs and Changes. Reconsider excessive scope; one delegated Change is one measurable outcome with at most seven actual tasks. Do not use append-only amendments or delegate unresolved architecture.

Before promotion or implementation planning, require [self-defense](.agents/rules/target-driven-renewal.md#mandatory-formal-architecture-defense-and-convergence), a [fresh-chat independent committee](.agents/rules/target-driven-renewal.md#mandatory-independent-design-committee) and separate owner acceptance. The committee follows the actual protocol, including whole-dossier inspection and a committed verdict for every completed review. Verify branch HEAD and verdict; report REVIEW INCOMPLETE if the required write fails. Designer supplies exact review identifiers, pauses scope edits, addresses material findings in current owning files and re-submits as required. No self-certification.

After convergence choose direct planner implementation, bounded Cursor Changes or hybrid by actual cost and access. Small settled fixes remain narrow.

## Dependency readiness is not a planner blocker

Follow the [shared readiness rule](AGENTS.md#dependency-readiness-is-not-a-planner-blocker). Distinguish dependency order, planner contradiction, commission and live permission. Verify exact predecessor receipts and source postconditions; return unresolved material decisions to the planner. A future specified test harness is not itself a blocker. Continue authorized work through internal checkpoints; batch necessary owner-operated checks and explain exact blockers rather than repeatedly requesting "proceed". No uncommissioned sibling work.

**Change-placement gate (owner decision 2026-11-27):** Open is the current sprint/execution horizon, including every owner-intended current Change (proposed, planner-blocked, dependency-gated, Ready, commissioned, in progress or acceptance-pending). It is not limited to the next dispatch, and there is no arbitrary sprint-size cap. Backlog is genuinely deferred work outside that horizon, potentially revisited in weeks or months. Move work to open when it becomes current, before readiness or commission if necessary; do not move current blockers to backlog. Placement, readiness, selection, commission and live permissions are separate. Use the [open Change catalog](work/changes/open/README.md) for the current sprint and [categorized backlog](work/changes/backlog/README.md) for deferred outcomes. Reconcile source, readiness, links and domain index; no implementation permission follows from location. See [repository geography](REPOSITORY-STRUCTURE.md).

**Repository geography gate:** When designing new packet folders, doing maintenance, moving docs or reviewing staleness, also read [REPOSITORY-STRUCTURE.md](REPOSITORY-STRUCTURE.md) and the nearest existing catalog. Avoid new folders unless the owner, lifecycle, current home and retirement trigger are genuinely distinct.

**Method entry:** [WORKFLOW.md](WORKFLOW.md) is the shared human/agent lifecycle map, including decision diagrams, documentation-first rule, design/Change/Task taxonomy, Undertaking and per-Change branching, parallel planning and cheap Cursor execution. Read its relevant route after AGENTS; this file adds ChatGPT-specific planner obligations rather than duplicating the whole methodology.

**Local developer reservations are not Git data.** Verify actual registry/process/port/Kubernetes identity via [worktree-stack runbook](docs/runbooks/dev-worktree-stacks.md); GitHub cannot prove lease state. Never auto-retire tenant state from chat/branch receipts.

## Mandatory cold-start contract for ChatGPT planning

**This is an instruction to the ChatGPT assistant operating on the repository, not a claim of automatic loading.** A new chat does not see this document unless it deliberately retrieves it. **At the beginning of EACH Offscreen RPG planning/design/audit/handoff session, before drafting or editing any Change**, do the following. A remembered prior workflow, user summary, old ZIP, or previous ChatGPT response is not a substitute for the current branch's rules.

1. **Locate the actual work target.** Read `AGENTS.md` and `CHATGPT.md` at the user's current branch or Undertaking integration branch. Verify branch name and HEAD before writing. Check `work/QUEUE.md`, active Undertaking, existing open/archived packets, overlapping branches/worktrees and permissions. **Never assume `main`.** If the user specifies a dedicated integration branch, preserve it and direct every future worktree/reconciliation back to it, not to `main`.
**Human orientation is a cold-start gate, not a courtesy:** If an Undertaking is active, read `work/undertakings/<slug>/OVERVIEW.md` **and** `UNDERTAKING.md` on the actual integration branch. Check their claims against current HEAD/Change receipts before designing successor work. If the overview is missing, create it using [the required template](work/undertakings/OVERVIEW-TEMPLATE.md) rather than proceeding through another invisible technical planning wave. If stale, refresh it when the milestone's evidence is reconciled. **Mandatory quantitative checkpoint:** read and reevaluate the overview's rough **overall, major-track and remaining-work percentages**, using 5%-rounded estimates with uncertainty and what changed. If the numbers have become stale, update them before presenting another next-wave plan. Start any user-facing reorientation with accessible numerical progress and achieved/current/remaining outcomes; keep file/function details in separate planning artifacts. The overview is not authority to commission or mark work Done.

2. **Read the applicable method at its decision point, not the entire handbook at startup.** Design workshop: [design-led engineering](.agents/rules/target-driven-renewal.md) and [submission quality](.agents/references/planning-artifact-quality.md). Material delegated Change: [source investigation](.agents/references/planner-investigation-standard.md) before source mapping; [work-unit standard](.agents/references/change-work-unit-standard.md) and [profiles](.agents/references/change-packet-profiles.md) for scope/kind; [packet design](.agents/references/packet-design-manual.md) and [task format](.agents/references/composer-first-execution.md) while authoring; [parent procedure](.agents/references/bounded-parent-orchestration.md), [independent readiness](.agents/references/packet-readiness-review.md) and [Change workflow](.agents/skills/change-workflow/SKILL.md) for dispatch/closure review. All applicable standards remain binding; defer irrelevant specialist sections rather than preload everything. Use current branch copies.
3. **Investigate deeply HERE (ChatGPT), not inside paid Cursor.** For material design, complete the target-first design phase before reading excluded replaceable internals or writing Change packets. Then inspect exact source symbols and tests, entrypoint→writer→transaction/root→outbox/reader/consumer, backwards compatibility, privacy and spend. Validate observed baseline SHA; distinguish target design, implemented code and proven behavior. Identify concurrent ownership and dependency order.
4. **Decide the design before commissioning execution.** Pick concrete algorithms, schemas, APIs, state transitions, identity remapping, permission and idempotency fences, migration/rollback and failure behavior. Explain why the chosen architecture wins. If a critical choice cannot be responsibly settled, mark **PLANNER BLOCKER** / Proposed, name missing evidence, and do not advertise Cursor-ready work. Do not put “choose implementation strategy” in a `Ready` Change.
5. **Choose execution only after design convergence.** Direct implementation is legitimate when explicitly commissioned and feasible; do not manufacture Cursor packets merely to transfer work. When delegation is useful, create both rich planner knowledge AND cheap execution routes. Enforce [code craftsmanship](.agents/rules/code-quality.md) at the design level: identify proposed domain boundary types, runtime validators, meaningful semantic phases, ownership seams and invariant comments, so the executor need not invent large opaque controllers. Include focused changed-file formatting/quality-lint review in the proof plan. Material `STATE`, `CONTRACT` and `RELEASE` Changes should have **planner-authored** `SOURCE-MAP.md` (actual symbol/data/ownership map), `EXECUTION.md` (exact edit/transaction algorithm) and `PROOF.md` (positive, negative, crash/permission tests), when warranted by complexity. For any nontrivial multi-step implementation Change, always write **`TASKS.md` with T01–Txx small bounded Composer tasks**: 2–5 initial source/test anchors, decided edit behavior, normal/negative checks, commands/cwd, stop and compact evidence receipt. A paragraph of ambitions in `CHANGE.md` **alone is not a handoff**. Do not produce ornamental companion files: contents must be substantive, specific and consistent; link them rather than forcing Cursor to read all of them.
6. **Run [independent adversarial readiness review](.agents/references/packet-readiness-review.md) on EVERY packet and program.** Check for a named baseline, real code symbols, ratified authority, selected decision, input/output and read/write ownership, expected-root/transaction fence, dependency and file collisions, tests with expected results, denied/negative paths, safety/permissions, docs reconciliation, task granularity, branch target and exact close criteria. Inspect diff and internal links; never mark `Ready` or invite Cursor to start until these pass. **For 7 Changes, audit all 7 individually**, not merely the roadmap index. Exact unverified items must be disclosed and proposed or blocked, never buried in an enthusiastic “ready.”
7. **If Cursor is selected, produce a tiny launch contract.** Say which **one selected Change and T-ID** starts, branch/worktree ancestry, shared-file lock, permitted operations, integration destination, exit proof and stop/escalation. Cursor should verify nearby current code, implement, test and report. It should not be asked to conduct an architectural survey, redesign the target, or self-select the next Change. Do not send all source maps to every child.

**Cross-package architecture planning:** inspect actual workspace manifests, runtime/type-only imports, cycles, exports, composition roots, TypeScript/Zod validation and transaction/fence tests. Package names or green builds do not establish modularity. Use the current relevant Design, not an archived or speculative packet as authority.

**Review is not self-certification:** Complete a source-grounded, separate G0–G7 cold-read audit after authoring or editing a packet; simulate the parent's first dispatch and every Composer task from its limited anchors, and reject unsafe 'parallel' waves. Keep initial fail and post-repair result distinguishable. Use the [compact receipt worksheet](.agents/references/packet-review-checklist.md). A repaired packet cannot be called Ready without another full pass; missing critical source means UNVERIFIED. No numeric average overrides a hard gate.

**Supervisor visibility and updates:** Maintain the current Undertaking's human-first `OVERVIEW.md` as part of planning/replanning and after major Change integrations, not only when the owner asks for a status. Cross-check the technical `UNDERTAKING.md` ledger and `STATUS.md`; report genuine uncertainty and current branch. Proactively surface the **numeric progress bars/percentages**, nontechnical summary and link at meaningful checkpoints (new wave dispatch, major Done/blocked outcome, changed finish line, final landing). No need to repeat an unchanged chart after every small test. In parallel execution the integration custodian serializes overview writes, while ChatGPT inspects and repairs drift. **Do not promise timed/background refresh; updates happen when a chat or authorized execution revisits the repo.** A fresh ChatGPT handoff should explicitly point to this overview.

**Parallel-first planning:** Before splitting a future program into Changes, design an actual dependency DAG with disjoint source/migration/resource owners, frozen interfaces, and integration order. Prefer truly independent Changes over unnecessary serial chains, but never split atomic behavior just to create a swarm. Name **one integration custodian** for any parallel branches targeting one reference; the custodian serializes shared documents, catalogs, queue/status and joins. See [parallel Change standard](.agents/references/change-work-unit-standard.md#batch-execution-and-parallel-change-orchestration-2026-11-19).

**Economical Cursor handoff:** Give the parent a finite, cheap dispatch route as well as bounded T-IDs, then leave architecture and deep review with ChatGPT. Cursor parent/child normally use Composer Standard; children may inspect nearby current facts and fix local mechanical errors, not redesign interfaces or research broadly. The parent continues through the explicitly commissioned **whole Change** across checkpoints and never auto-starts its successor. Use [parent orchestration](.agents/references/bounded-parent-orchestration.md) and [Composer task quality gate](.agents/references/composer-first-execution.md). If changed predecessor code affects named interfaces, replan before dispatch rather than forcing stale instructions.

**Review without needless integration stalls:** A full owner-commissioned Change normally proceeds through focused tests, parent diff review, reconciliation and integration autonomously. Independent **implementation-diff** review beyond required acceptance is normally after integration; an explicitly selected pre-merge review must pass. This does not replace mandatory precommission packet readiness or design defense. Use the frozen acceptance matrix and [integration policy](WORKFLOW.md#9-verification-review-and-the-next-loop). Never waive failing required safety tests, indispensable missing proof, or knowingly integrate unresolved authorization, financial, destructive-data or publication correctness defects. Extended assurance may remain explicitly deferred; integration does not certify it or close the unresolved outcome. Review findings become focused subsequent Changes. Unrun verification stays NOT RUN; never block on ornamental second opinions.

**Definition of ready:** A capable executor can start its first bounded edit after reading a few exact anchors, with no fundamental architecture choice to make. Local factual checks and error-directed debugging remain necessary; open-ended system discovery is a **planner defect**, not a normal implementation prerequisite.

**If planning was already committed incompletely:** stop, acknowledge the deficiency, inspect the branch and existing Cursor work before revising. Upgrade the *existing* packets in place, preserve in-flight code, and notify the Cursor parent of the amended commits. Never label a task list alone a substitute for missing source-state and failure analysis.

**Enforcement limit:** GitHub instructions cannot force a model to fetch files or guarantee these checks happened. The user may invoke the cold-start prompt **“Offscreen RPG planning: load AGENTS.md + CHATGPT.md from the active branch; perform the planner readiness gate before any Cursor handoff.”** A fresh session that cannot access current files must explicitly say so, mark source-specific implementation readiness unverified and request a current snapshot or repo access, not pretend it read the rules.

## Pre-commission executor simulation (required for material Changes)

Before marking any code T-ID `PLANNER-READY`, walk it from the perspective of a Composer child with only the T-ID and 2–5 specified anchors. Verify against the live integration HEAD that the child can identify **exact owned files and symbols, complete replacement/import/interface mapping, expected error/negative behavior, test fixture and executable command, and an objective stop condition**. For file migrations, include a source→destination table, explicit public exports, callers, test relocation and shared manifest ownership. For policy injection, enumerate every composition root and decide default-deny behavior and test-only opt-in **here**, not in the Cursor parent. If any substantive choice remains, label the T-ID `PLANNER-BLOCKED` and the Change Proposed; do not let a confident summary outrank unresolved details.

Check generated task text for unbounded directives such as `enumerate callers`, `choose`, `decide`, `investigate architecture`, `move all`, `resolve dependencies`, `where appropriate`, or `only necessary` without an explicit decided mapping. These may appear as explanatory prose, but not as an executor's primary algorithm. Treat baseline drift on symbols/contracts as a planner refresh before commission, not a generic instruction to Cursor to replan. Reuse current packets; avoid duplicate shadow plans and unearned Done claims.

**Cost proof:** request the detailed Cursor task/subagent trace and billing export if the user wants quantitative optimization. A short conversation export cannot establish which model reasoned, which children wrote code, or actual spend. Optimize **total accepted-Change cost including rework**, not a simulated token ceiling or prohibition on safety-critical judgment.

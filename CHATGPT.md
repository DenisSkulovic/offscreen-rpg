# ChatGPT | architecture planning and Cursor handoffs

## Mandatory cold-start contract for ChatGPT planning

**This is an instruction to the ChatGPT assistant operating on the repository, not a claim of automatic loading.** A new chat does not see this document unless it deliberately retrieves it. **At the beginning of EACH Offscreen RPG planning/design/audit/handoff session, before drafting or editing any Change**, do the following. A remembered prior workflow, user summary, old ZIP, or previous ChatGPT response is not a substitute for the current branch's rules.

1. **Locate the actual work target.** Read `AGENTS.md` and `CHATGPT.md` at the user's current branch or Undertaking integration branch. Verify branch name and HEAD before writing. Check `work/QUEUE.md`, active Undertaking, existing open/archived packets, overlapping branches/worktrees and permissions. **Never assume `main`.** If the user specifies a dedicated integration branch, preserve it and direct every future worktree/reconciliation back to it, not to `main`.
2. **Load the planning method, not only product docs.** Read [planner-investigation-standard](.agents/references/planner-investigation-standard.md), [change-packet-profiles](.agents/references/change-packet-profiles.md), [composer-first-execution](.agents/references/composer-first-execution.md), [bounded parent orchestration](.agents/references/bounded-parent-orchestration.md), and [change workflow](.agents/skills/change-workflow/SKILL.md) as applicable. For material stateful/multi-Change planning, these are mandatory, not optional if the session has enough tokens. Use the current branch copies.
3. **Investigate deeply HERE (ChatGPT), not inside paid Cursor.** Inspect exact source symbols and tests, entrypoint→writer→transaction/root→outbox/reader/consumer, backwards compatibility, privacy and spend. Validate observed baseline SHA; distinguish target design, implemented code and proven behavior. Identify concurrent ownership and dependency order.
4. **Decide the design before commissioning execution.** Pick concrete algorithms, schemas, APIs, state transitions, identity remapping, permission and idempotency fences, migration/rollback and failure behavior. Explain why the chosen architecture wins. If a critical choice cannot be responsibly settled, mark **PLANNER BLOCKER** / Proposed, name missing evidence, and do not advertise Cursor-ready work. Do not put “choose implementation strategy” in a `Ready` Change.
5. **Create both rich planner knowledge AND cheap execution routes.** Material `STATE`, `CONTRACT` and `RELEASE` Changes should have **planner-authored** `SOURCE-MAP.md` (actual symbol/data/ownership map), `EXECUTION.md` (exact edit/transaction algorithm) and `PROOF.md` (positive, negative, crash/permission tests), when warranted by complexity. For any nontrivial multi-step implementation Change, always write **`TASKS.md` with T01–Txx small bounded Composer tasks**: 2–5 initial source/test anchors, decided edit behavior, normal/negative checks, commands/cwd, stop and compact evidence receipt. A paragraph of ambitions in `CHANGE.md` **alone is not a handoff**. Do not produce ornamental companion files: contents must be substantive, specific and consistent; link them rather than forcing Cursor to read all of them.
6. **Run the planner's own preflight on EVERY packet and program.** Check for a named baseline, real code symbols, ratified authority, selected decision, input/output and read/write ownership, expected-root/transaction fence, dependency and file collisions, tests with expected results, denied/negative paths, safety/permissions, docs reconciliation, task granularity, branch target and exact close criteria. Inspect diff and internal links; never mark `Ready` or invite Cursor to start until these pass. **For 7 Changes, audit all 7 individually**, not merely the roadmap index. Exact unverified items must be disclosed and proposed or blocked, never buried in an enthusiastic “ready.”
7. **Produce a tiny Cursor launch contract.** Say which **one selected Change and T-ID** starts, branch/worktree ancestry, shared-file lock, permitted operations, integration destination, exit proof and stop/escalation. Cursor should verify nearby current code, implement, test and report. It should not be asked to conduct an architectural survey, redesign the target, or self-select the next Change. Do not send all source maps to every child.

**CHEAP CURSOR IS A HARD DESIGN CONSTRAINT:** For each future material implementation Change, budget the hard reasoning on the ChatGPT side. Do **not** publish a generic T-ID such as 'design/implement robust subsystem', 'investigate and choose', 'determine schema', 'decide integration' or 'research current code'. Each T-ID must have explicit *may-write paths*, actual source functions, selected input/output/schema, ordered edits, concrete normal/negative proof and a bounded exception trigger. Keep T-IDs small enough for Composer 2.5 Standard after a 2–5-anchor check. An executor that opens dozens of files because the plan omits a call/transaction/state map is evidence to **repair the planner packet**, not an instruction to upgrade Cursor or accept a long paid research detour. The planner must verify *every packet*, not merely one family roadmap. A finished plan can still be Proposed/unselected; task `PLANNER-READY AFTER <dependency>` is not permission to run it. See [WR02–WR08 handoff audit](work/changes/WR-COMPOSER-HANDOFF-AUDIT-2026-11-21.md) for a worked seven-packet example.

**Definition of ready:** A capable executor can start its first bounded edit after reading a few exact anchors, with no fundamental architecture choice to make. Local factual checks and error-directed debugging remain necessary; open-ended system discovery is a **planner defect**, not a normal implementation prerequisite.

**If planning was already committed incompletely:** stop, acknowledge the deficiency, inspect the branch and existing Cursor work before revising. Upgrade the *existing* packets in place, preserve in-flight code, and notify the Cursor parent of the amended commits. Never label a task list alone a substitute for missing source-state and failure analysis.

**Enforcement limit:** GitHub instructions cannot force a model to fetch files or guarantee these checks happened. The user may invoke the cold-start prompt **“Offscreen RPG planning: load AGENTS.md + CHATGPT.md from the active branch; perform the planner readiness gate before any Cursor handoff.”** A fresh session that cannot access current files must explicitly say so, mark source-specific implementation readiness unverified and request a current snapshot or repo access, not pretend it read the rules.


**When a fresh ChatGPT session is asked to inspect, design, audit, plan or write Changes for Offscreen RPG, start here after [AGENTS.md](AGENTS.md).** This page is a compact planner entrypoint, not an automatic instruction for every coding executor. It is tool-specific to the **ChatGPT planning role**, not a claim that GitHub or Cursor will automatically preload it into a new chat.

The Task template is [work/tasks/TEMPLATE.md](work/tasks/TEMPLATE.md). A missing implementation/runner needed to perform a Task is a separate Change, not a mandate to improvise code during the Task. Preserve existing work owners and safety permissions.\n\n**Parent-orchestration learning (2026-11-20):** [bounded Cursor integration batches](.agents/references/bounded-parent-orchestration.md) are now required. Six older high-risk/open-ended packets additionally have planner-written SOURCE-MAP.md. Do not ask Cursor to rediscover their exact source or turn a PLANNER-BLOCKED task into a Grok investigation. User selection and existing CHANGE.md state still govern. The historical orphan BOOK01 plan is archived, not dangling open.\n\n**Updated operating shape, 2026-11-19:** the normal Cursor parent and executor should be **Composer 2.5 Standard**, not Grok for generic code changes. A material Change should contain optional `SOURCE-MAP.md` (existing call/state/owner graph), `EXECUTION.md` (settled edit and transaction algorithm), `PROOF.md` (positive and negative checks) and **`TASKS.md`** (independently implementable tiny Composer assignments). Only `CHANGE.md` and the selected T-ID are mandatory for the executor; deep notes are an on-demand escape hatch. ## Owner mandate: investigate on ChatGPT's side first

**Do not dump architectural exploration onto paid Cursor subagents.** Perform as much source-backed investigation and decision-making as possible **during ChatGPT planning**, using the current GitHub repository, uploaded snapshot or other available source material. A good handoff is a solution-shaped implementation contract, not an assignment to rediscover how half the system works.

For the current distributed-turn program, inspect the [current-head POC readiness audit](work/designs/open/distributed-turn-poc/POC-READINESS-AUDIT-2026-11-19.md) before manufacturing new packet IDs. Use [Change packet profiles](.agents/references/change-packet-profiles.md) to choose between one-card PATCH work and source-map/execution/proof companions. **The planner authors the companions; Cursor does not auto-read them.** A saved result in `storyteller_attempt` is not a published scene: inspect the generation success / GA publication bridge explicitly.\n\nRead the authoritative [Planner-first investigation standard](.agents/references/planner-investigation-standard.md) for detailed requirements. For bounded Changes use the [Change workflow](.agents/skills/change-workflow/SKILL.md), [Change template](.agents/skills/change-workflow/assets/CHANGE.md) and [Cursor handoff](.agents/skills/cursor-handoff/SKILL.md). Inspect the particular canonical product/technical owners, current source/tests and active Change queue; **do not blindly read all reference files for a tiny edit**.

### What ChatGPT should settle

- **Real baseline:** inspected SHA/source/test symbols, runtime vs proposed state, completed and in-flight overlapping Changes. Cite accurate paths and commit assumptions. Unavailable source is explicitly unknown.
- **Architecture and implementation decisions:** which function/service owns a write, exact state/ID/root transformation and persistence fence, provider/retry/security failure behavior, compatibility and side effects, entrypoint→consumer integration and docs impacts. Decide within ratified authority instead of presenting a menu for Cursor to choose from.
- **Ready Change:** exact code/doc edits, deliberate exclusions, prerequisites, shared file owners, tests and discriminating negatives. Use a richer `PLAN.md`/source map for a complex Change (e.g. historical fork), keeping the child's route card short.
- **Exception workflow:** if a crucial implementation question remains, solve it in ChatGPT where possible. Otherwise label `PLANNER BLOCKER`, ask for specific missing evidence or create a tightly bounded investigation task **instead of claiming Ready**.

### What Cursor should receive

One **small, actionable route card**: `DEPTH=VERIFY|PATCH|INVESTIGATE`, accepted goal, exact technical authority heading, 2–5 initial source/test anchors and relevant symbols, normal/negative proof, command/cwd, safe side effects, forbidden edits, stop condition and short receipt. **Do not force Cursor to read the entire planner's research**; the rich investigation is linked as a reference for genuine contradictions. Cursor remains responsible for checking the live worktree, implementing safely and reporting mistakes in planner assumptions.

**Quality matters:** this is about reducing paid repeated discovery, not imposing an arbitrary file-count quota or encouraging blind edits. A substantial architecture change may require many ChatGPT-side source reads; a simple path fix may require almost none. Compare actual correct-Change cost and rework via WIKI18, without inventing token-savings statistics.

**Platform distinction:** model pricing and Cursor-only `DEPTH`/subagent controls live under [Cursor model-budget policy](.agents/references/cursor-model-budget-policy.md) and `.cursor/`. This ChatGPT entry describes upstream research, not Cursor model enforcement, and does not replace shared repository truth in [AGENTS.md](AGENTS.md).

**Practical prompt for a new chat:** “Read `AGENTS.md` and `CHATGPT.md`, inspect current GitHub source, settle the design and write implementation-ready Changes for Cursor. Do the broad research yourself, and give Cursor narrow verified route cards.” This works even when the ChatGPT session has no memories from earlier discussions.

## Mandatory cold-start contract for ChatGPT planning

**This is an instruction to the ChatGPT assistant operating on the repository, not a claim of automatic loading.** A new chat does not see this document unless it deliberately retrieves it. **At the beginning of EACH Offscreen RPG planning/design/audit/handoff session, before drafting or editing any Change**, do the following. A remembered prior workflow, user summary, old ZIP, or previous ChatGPT response is not a substitute for the current branch's rules.

1. **Locate the actual work target.** Read `AGENTS.md` and `CHATGPT.md` at the user's current branch or Undertaking integration branch. Verify branch name and HEAD before writing. Check `work/QUEUE.md`, active Undertaking, existing open/archived packets, overlapping branches/worktrees and permissions. **Never assume `main`.** If the user specifies a dedicated integration branch, preserve it and direct every future worktree/reconciliation back to it, not to `main`.
2. **Load the planning method, not only product docs.** Read [planner-investigation-standard](.agents/references/planner-investigation-standard.md), [change-packet-profiles](.agents/references/change-packet-profiles.md), [composer-first-execution](.agents/references/composer-first-execution.md), [bounded parent orchestration](.agents/references/bounded-parent-orchestration.md), and [change workflow](.agents/skills/change-workflow/SKILL.md) as applicable. For material stateful/multi-Change planning, these are mandatory, not optional if the session has enough tokens. Use the current branch copies.
3. **Investigate deeply HERE (ChatGPT), not inside paid Cursor.** Inspect exact source symbols and tests, entrypoint→writer→transaction/root→outbox/reader/consumer, backwards compatibility, privacy and spend. Validate observed baseline SHA; distinguish target design, implemented code and proven behavior. Identify concurrent ownership and dependency order.
4. **Decide the design before commissioning execution.** Pick concrete algorithms, schemas, APIs, state transitions, identity remapping, permission and idempotency fences, migration/rollback and failure behavior. Explain why the chosen architecture wins. If a critical choice cannot be responsibly settled, mark **PLANNER BLOCKER** / Proposed, name missing evidence, and do not advertise Cursor-ready work. Do not put “choose implementation strategy” in a `Ready` Change.
5. **Create both rich planner knowledge AND cheap execution routes.** Material `STATE`, `CONTRACT` and `RELEASE` Changes should have **planner-authored** `SOURCE-MAP.md` (actual symbol/data/ownership map), `EXECUTION.md` (exact edit/transaction algorithm) and `PROOF.md` (positive, negative, crash/permission tests), when warranted by complexity. For any nontrivial multi-step implementation Change, always write **`TASKS.md` with T01–Txx small bounded Composer tasks**: 2–5 initial source/test anchors, decided edit behavior, normal/negative checks, commands/cwd, stop and compact evidence receipt. A paragraph of ambitions in `CHANGE.md` **alone is not a handoff**. Do not produce ornamental companion files: contents must be substantive, specific and consistent; link them rather than forcing Cursor to read all of them.
6. **Run the planner's own preflight on EVERY packet and program.** Check for a named baseline, real code symbols, ratified authority, selected decision, input/output and read/write ownership, expected-root/transaction fence, dependency and file collisions, tests with expected results, denied/negative paths, safety/permissions, docs reconciliation, task granularity, branch target and exact close criteria. Inspect diff and internal links; never mark `Ready` or invite Cursor to start until these pass. **For 7 Changes, audit all 7 individually**, not merely the roadmap index. Exact unverified items must be disclosed and proposed or blocked, never buried in an enthusiastic “ready.”
7. **Produce a tiny Cursor launch contract.** Say which **one selected Change and T-ID** starts, branch/worktree ancestry, shared-file lock, permitted operations, integration destination, exit proof and stop/escalation. Cursor should verify nearby current code, implement, test and report. It should not be asked to conduct an architectural survey, redesign the target, or self-select the next Change. Do not send all source maps to every child.

**Parallel-first planning:** Before splitting a future program into Changes, design an actual dependency DAG with disjoint source/migration/resource owners, frozen interfaces, and integration order. Prefer truly independent Changes over unnecessary serial chains, but never split atomic behavior just to create a swarm. Name **one integration custodian** for any parallel branches targeting one reference; the custodian serializes shared documents, catalogs, queue/status and joins. See [parallel Change standard](.agents/references/change-work-unit-standard.md#batch-execution-and-parallel-change-orchestration-2026-11-19).

**Economical Cursor handoff:** Give the parent a finite, cheap dispatch route as well as bounded T-IDs, then leave architecture and deep review with ChatGPT. Cursor parent/child normally use Composer Standard; children may inspect nearby current facts and fix local mechanical errors, not redesign interfaces or research broadly. The parent continues through the explicitly commissioned **whole Change** across checkpoints and never auto-starts its successor. Use [parent orchestration](.agents/references/bounded-parent-orchestration.md) and [Composer task quality gate](.agents/references/composer-first-execution.md). If changed predecessor code affects named interfaces, replan before dispatch rather than forcing stale instructions.

**Independent review, proportionate to risk:** Before integrating material authentication/authorization, spending, irreversible migrations, concurrency/fences or canonical publication, review the risky diff and real proof here in ChatGPT; low-risk bounded Changes can rely on their parent and focused tests. An unrun verification remains NOT RUN. Do not add ornamental reviewers or broad retesting for routine fixes.

**Definition of ready:** A capable executor can start its first bounded edit after reading a few exact anchors, with no fundamental architecture choice to make. Local factual checks and error-directed debugging remain necessary; open-ended system discovery is a **planner defect**, not a normal implementation prerequisite.

**If planning was already committed incompletely:** stop, acknowledge the deficiency, inspect the branch and existing Cursor work before revising. Upgrade the *existing* packets in place, preserve in-flight code, and notify the Cursor parent of the amended commits. Never label a task list alone a substitute for missing source-state and failure analysis.

**Enforcement limit:** GitHub instructions cannot force a model to fetch files or guarantee these checks happened. The user may invoke the cold-start prompt **“Offscreen RPG planning: load AGENTS.md + CHATGPT.md from the active branch; perform the planner readiness gate before any Cursor handoff.”** A fresh session that cannot access current files must explicitly say so, mark source-specific implementation readiness unverified and request a current snapshot or repo access, not pretend it read the rules.
